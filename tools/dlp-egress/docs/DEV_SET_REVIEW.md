# 1000 条模拟测试集：质量评估与第二轮规则改进

数据：`dlp-gold-v1-simulated-1000`（用户 2026-11-18 提供，sha256 `c89ab7aa…`，**不入库**）。
用法见 [决策记录 D-014](../../../docs/DECISIONS.md#d-014)：作为开发集使用，按编号固定拆成两部分，开发 70%（727 条）用来调规则，验证 30%（273 条）只用来报告结果。

## 1. 数据质量评估

### 1.1 结论

**可以用作开发集，但不能当作上线验收依据。** 主要问题：句式来自模板，多样性低；有明显的合成痕迹；标注和复核都由 AI 完成。

### 1.2 做得好的地方

- 格式完全符合标注规范：1000 条全部通过校验；标注的期望决策与按策略推导的决策**没有一条不一致**。
- 分布达到规范要求：通道各约 20%；ALLOW 19%，ANONYMIZE 39%，REVIEW 22%，BLOCK 18%；`internal` 12%，`unknown` 8%；困难样本 34%。
- 实体名几乎不重复（客户 214 个、人名 163 个各不相同），覆盖了无后缀公司名（如“霁霁”）、无称谓人名等困难情况。
- 凭证全部使用 `DEMO-NOT-A-REAL-*` 这类明显的假值，符合安全要求。

### 1.3 问题

| 问题 | 表现 | 影响 |
|---|---|---|
| 句式来自模板 | 每句由开头套话（如“请在周五前回执。”）+ 核心句式 + 结尾附注（如“附注：OEE-v2 / 2026-Q4。”）随机拼接；去掉套话后核心句式很少 | 开发部分和验证部分共用句式，验证结果偏乐观 |
| 合成痕迹明显 | 机密信息带编号（“…方案第15版”“…assumptions #6”）；项目名、厂区名带数字（“项目岚舟1”“岚舟3厂”）；电话为 `010-5550-1000` 这类连号 | 真实文本中较少见，规则可能学到这些痕迹 |
| 生产指标重复 | 108 处指标只有 10 种取值（如“一次合格率96.7%”出现 17 次） | 指标识别的结果参考价值低 |
| 干净负例偏少 | `clean` 场景只有 24 条（另有 120 条内部目的地的 ALLOW） | 误报（把正常内容判为敏感）测得不充分 |
| 凭证上下文单一 | 每条凭证都是“键=值”出现一次，再在后文原样重复一次 | 覆盖不到其他写法（例如只出现在 URL、配置块里的凭证） |
| 标注无人工参与 | `annotator` / `reviewer` 都是 `AI_SIMULATED_*` | 标注口径未经业务人员确认 |
| 语言标签 | 22 条中英混排被标为 `en`，规范要求标 `zh` | 只影响分语言统计；评测时已在副本中改正，原文件未改 |

### 1.4 建议（下一版测试集）

1. 由业务人员编写或改写至少 300 条，不用模板拼接；去掉编号、连号等合成痕迹。
2. 增加干净负例到 15% 以上，并且要包含“内部培训”“项目管理”“工厂安全”这类容易误报的词。
3. 凭证写法多样化：URL 里的令牌、配置块、日志片段、只出现一次的值。
4. 至少 10% 双人独立标注，计算一致率。

## 2. 第二轮规则改进

### 2.1 失败归因（只看开发部分）

| 类别 | 原因 | 处理（通用规则，不针对数据集） |
|---|---|---|
| 凭证漏放 | 键名不在固定列表里（如 `private_key_sample=`、`credential_value=`）；同一个值在后文再次出现时没有识别 | 键名改为“包含 password / secret / token / credential / api_key 等词即可”，并支持 密码 / 口令 / 密钥 / 令牌 / 凭证；值一旦被认定为凭证，文中所有出现都按凭证处理 |
| 凭证被当成工单号 | `DEMO-NOT-A-REAL-TOKEN-00001` 被“前缀-编号”规则切出 `TOKEN-00001` | 凭证识别出来后优先级最高，自然覆盖 |
| 机密信息漏识别 | 只认固定的概念词 | 改为“机密修饰语（内部、未公开、限制传播、仅限内部、confidential、restricted…）+ 至多 8 个字 + 商业文件名词（方案、阈值、矩阵、协议、playbook…）+ 可选版本号” |
| 电话漏识别 | `010-5550-1000` 这种分段写法 | 增加 `0区号-3~4位-4位` 格式 |
| 指标边界 | “一次合格率”只认出“合格率” | 增加一次合格率、报废率、可用率、first-pass yield、availability 等名称 |
| 厂区 / 项目 | “临港3厂”“项目青松2”“Project Falcon-7” | 支持阿拉伯数字编号；厂区前缀排除“完成、做、次、巡”等动词，避免“完成工厂巡检”误报 |
| 评测口径 | 目的地未登记的请求根本不做识别，却被算作漏识别 | 不计入实体指标（[D-015](../../../docs/DECISIONS.md#d-015)） |

所有新规则都先用**新编的例子**写测试（`tests/test_detection_v2.py`，34 项，不取自数据集），确认失败后再实现。

### 2.2 结果

| 部分 / 口径 | 实体 F1 | 决策准确率 | 危险放行 | 凭证漏放 |
|---|---|---|---|---|
| 开发 70% · 带名单（改进前 → 后） | 0.758 → 0.944 | 0.846 → **1.000** | 102 → **0** | 128 → **0** |
| 开发 70% · 不带名单 | 0.487 → 0.817 | 0.762 → 0.946 | 102 → **0** | 128 → **0** |
| **验证 30% · 带名单** | 0.791 → 0.951 | 0.854 → **1.000** | 39 → **0** | 24 → **0** |
| **验证 30% · 不带名单** | 0.514 → 0.823 | 0.784 → 0.952 | 39 → **0** | 24 → **0** |

- 改进前的数字已按 D-015 修正口径重新计算，所以与 PR #94 中报告的略有不同。
- 700 条评测集和 36 条留出集的结果**完全没有变化**（没有回退）。
- 不带名单时，剩余的决策错误都是“应脱敏却放行”（人名、厂区、项目名没识别出来），属于 GLiNER 要补强的部分，不是危险放行。
- 机密信息的实体 F1 只有约 0.70，主要是边界和标注不一致（例如数据把“…方案第1版”整体标为机密）。**决策已经正确**（都判为需要审批）。

### 2.3 如何解读

验证部分的“危险放行 0”**不代表**真实环境中不会漏。这份数据的句式来自模板，验证部分与开发部分共用句式（例如“限制传播的良率恢复方案第N版”这一句式，开发部分有 16 条、验证部分有 5 条）。
真实能力需要用第 1.4 节建议的人工测试集来衡量。

## 3. gold-v3（第二份模拟集）与第三轮规则改进

数据：`dlp-gold-v3-candidate-1000`（用户 2026-11-19 提供，评测 JSONL sha256 `81b36f5f…`，**不入库**）。
原定为候选正式测试集；按 [D-018](../../../docs/DECISIONS.md#d-018) 改作开发集，同样按编号拆分：开发 698 条、验证 302 条。

### 3.1 用 PR #101 规则重跑（全 1000 条，只看汇总）

用户本地 T3 报告用的是 `843df8e`（不含 PR #101 的第二轮规则）。用 PR #101 合并后的规则重跑（不开 GLiNER，口径 B）：

| 指标 | 843df8e（用户报告） | PR #101 规则 |
|---|---|---|
| 凭证漏放 | 17 | **0**（共 110） |
| 危险放行 | 267 | 222 |
| 实体 micro F1 | 0.626 | 0.727 |

剩下的 222 条危险放行**全部**是“应转审批的机密信息没识别出来”：293 处机密标注中 263 处与任何识别结果都不重叠。

### 3.2 数据观察（只看开发部分）

- 机密信息写法与 v1 不同：中文是“密级 / 流转限制标记 + 长名词短语”（如“限 X 查看的…”“机密等级的…”“公告前暂不披露的…”，以“上限 / 区间 / 边界 / 条件 / 路线”收尾）；
  英文是密级标记直接放在名词短语前（如 `need-to-know the …`、`controlled-access the …`）。
- 同样是模板拼接：机密信息几乎都嵌在“××讨论稿中的关键内容是…，这部分尚未批准公开”这类固定句式里。**规则没有使用这些句式**，只用标记词和名词收尾。
- 干净样本中有普通词被当成实体：“所有材料 / 确认材料”被当成公司名（“材料”是公司后缀），“项目编码 / 项目代号”被当成项目名。
- 生产指标只有“首检通过率”“first-pass yield”两种名称。

### 3.3 改进内容（通用规则，例子全部新编，先 Red 后 Green）

| 类别 | 处理 |
|---|---|
| 中文机密短语 | `[限定语（…的/时/后/前）] + 1~3 个密级标记 + 至多 20 字 + 机密类名词收尾`。标记：涉密、保密、机密等级、未公布、未宣布、暂不披露、禁止外发、未经批准、不得引用、不得转…的、限…查看/流转 等。限定语不得含“是、为、涉及、有…”等前文动词，避免把前文吞进实体 |
| 英文机密短语 | 密级标记（need-to-know、controlled-access、embargoed…、restricted to…、non-public 等）+ `the` + 至多 8 词，遇标点或谓语/连词结束；或 `the … unannounced/undisclosed/unapproved/internal… … 机密类名词` |
| 谈判底线概念 | 最低净价、最低可接受价、让步区间、议价授权（范围）、谈判底线；lowest acceptable / net price、walk-away price |
| 指标 | 首检通过率、一次通过率、通过率；pass rate |
| 误报修复 | 公司名的两字前缀不能是“所有、确认、转发、此段…”等普通词；“项目”后接“编码、代号、成员、进度…”不算项目名 |

测试：`tests/test_detection_v3.py`（33 项，分两批先写：第一批 25 项中 20 项正例失败、5 项负例通过；第二批误报修复 8 项中 7 项失败、1 项正例对照通过）。

### 3.4 结果

| 部分 / 口径 | 实体 F1 | 决策准确率 | 危险放行 | 凭证漏放 | 过度拦截 |
|---|---|---|---|---|---|
| 开发 · 带名单（前 → 后） | 0.842 → 0.985 | 0.748 → 0.969 | 152 → 22 | 0 → 0 | 0 → 0 |
| 开发 · 不带名单 | 0.733 → 0.892 | 0.738 → 0.959 | 152 → 22 | 0 → 0 | 0 → 0 |
| **验证 · 带名单** | 0.851 → 0.978 | 0.738 → **0.960** | 70 → **12** | 0 → 0 | 0 → 0 |
| **验证 · 不带名单** | 0.712 → 0.857 | 0.715 → **0.934** | 70 → **12** | 0 → 0 | 0 → 0 |

- 700 条评测集、v1 开发 / 验证、36 条留出集的结果**完全没有变化**。
- 单条延迟 P95 仍在 7 ms 以内。

### 3.5 剩余问题

- 开发部分剩下的 22 条危险放行来自 5 种**没有任何密级标记**的写法，例如“试产失败后拟调整的配比阈值”“待董事会批准的生产线迁移方案”“the supplier ranking used only in negotiations”。
  要识别它们，只能把“拟…”“待…批准”这类很弱的词当作信号，那样“待领导批准的请假安排”也会被转审批。所以**没有用规则硬凑**，留给语义模型（见 3.6）。
- 不带名单时人名召回只有 0.2～0.3、客户 0.4～0.6、厂区 0.5～0.6，靠规则已经很难再提高。

### 3.6 关于 GLiNER（依据用户 T3 报告）

- 结论与 T3 一致：jieba 分词（J 组）明显提升客户 / 人名召回，whitespace 帮助有限。
- **GLiNER 不能替代机密 / 凭证规则**：凭证漏放在所有配置下都不变。它有“confidential business information”标签，J-0.3 的危险放行降到 177 应来自这个标签，但低阈值同时带来更多误报（F1 降到 0.60），不宜为此调低阈值。
- **建议（待用户决定）**：维持默认关闭；需要“不带名单也能识别人名 / 客户”的部署，启用 `gliner_multi-v2.1` + jieba 分词 + 阈值 0.5（T3 中 F1 与召回最均衡；留出集 F1 0.92）。
  代价是每次评估约 +110 ms（P95）。外发检查默认超时是 2000 ms，可以接受；但对流式 LLM 调用的首字延迟有影响。
- T3 的数字基于旧规则；在新规则上需要用户本地重跑一次 J-0.5（本环境下载不了模型）。

### 3.7 J-0.5 在新规则上的本地复测（用户 2026-11-19，代码 `06eb76b`）

gold-v3 全 1000 条，口径 B（无词典）：

| 指标 | 不开 GLiNER | J-0.5 |
|---|---|---|
| 实体 micro P / R / F1 | 0.978 / 0.803 / 0.882 | 0.896 / 0.905 / 0.901 |
| 客户 P / R | 0.85 / 0.51 | 0.94 / 0.80 |
| 人名 P / R | 0.98 / 0.23 | 0.70 / 0.93 |
| 决策准确率 | 0.951 | 0.903 |
| 危险放行 / 过度拦截 / 凭证漏放 | 34 / 0 / 0 | 33 / **23** / 0 |
| P95 延迟 | 2.2 ms | 113 ms |

留出集（36 条，口径 B）：F1 0.862 → 0.924，客户召回 0.43 → 0.86，人名召回 0.71 → 1.0；危险放行、过度拦截、凭证漏放都是 0；P95 1.5 → 48 ms。

- 不开 GLiNER 的 34 条危险放行，与本环境按开发 / 验证拆分的结果（22 + 12）一致，说明两边环境可以复现。
- 过度拦截 23 次来自 GLiNER 的机密标签（唯一会让决策升级的标签），处理见 [D-019](../../../docs/DECISIONS.md#d-019)：默认不再请求这个标签。
- 人名精度从 0.98 降到 0.70：GLiNER 会把一些普通词当成人名。这些词只会被替换，不会被拦，但会降低准确率。
  下一步可以考虑按标签设阈值（例如人名用 0.7），需要再次本地评测。
- **待用户决定**：是否在部署中启用 GLiNER。建议按 3.6 节的建议执行，并先用 D-019 之后的代码复跑一次 J-0.5，确认过度拦截回到 0。
