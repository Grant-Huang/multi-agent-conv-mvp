1. **快速搭建完整前端**（里程碑 A）。

## 1. 交付顺序

近期第 1、4 线从首页正常入口接通真实委派，第 2 线独立复跑丢回执和重连。用户能打开实际 Task 并回到原会话后，再验人工验收和结果回传。T-64 已在恢复面板验证游标 SSE，首页路径复用该能力。T-70 个人设置和 T-71/72 服务端夹具记忆列表、纠错和撤回已接入。第 5 线的资料来源、预览和编辑入口按[分层记忆计划](../features/conversation-memory/PLAN.md)逐段接入。共同出口见[集成计划](../INTEGRATION_PLAN.md#研发线与近期汇合)。

**首个交付快速搭建完整前端。** 先贯通产品入口、S1/S2/S3 和 SMT-03（A 阶段允许纯 Mock 种子 `TASK-2026-018`），再并行补齐其余已确认功能。A 的出口要求所有已确认前端流程均可通过正常入口使用。后端暂缺能力由 Mock 驱动，移动语音和跨设备流程也可模拟。每个后续交付均运行同一套完整前端。服务替换按能力逐项进行（MOCK_REGISTRY）。A1 **一次换壳**，不保留旧一级页签双轨。

| 里程碑 | 工作顺序 | 出口 |
|---|---|---|
| A 完整前端与测试底座 | A1 壳层与导航，A2 草稿、阅读与上下文，A3 证据与历史，A4 助理、设置、交互与响应式，A5 异步、协作、审批、移动及跨设备流程。各模块由真实现有接口或注册的 Mock 驱动 | **A5 整体已收口（2026-11-20）**：`desktop.spec` 15/15；证据 `docs/testing/evidence/ai-desktop-a5.md`。Mock 替换门槛见 MOCK_REGISTRY；真实可靠受理等自 **B1** 起 |
| B 服务端连续性 | B1 可靠受理，B2 Run 与事件恢复，B3 关联、检索、个人配置及同步 | A 全回归；新增真实 HTTP/SSE/SQLite 集成，含重复提交、断线、重启与版本冲突。按能力切换运行时来源 |
| C 组织与受控执行 | C1 组织身份、对象及来源权限、频道与检索，C2 动作审批、网关和消息投递 | A/B 全回归；验证跨角色撤权、审批版本、实际副作用、结果核对与通知去重 |

A 的交付开发顺序：

1. 在同一前端入口完成桌面、工作区、面板与移动布局。现有会话、任务、运营入口按兼容协议接入。
2. 用两个独立 Task 和 Conversation 数据种子验证路由、草稿、阅读位置、异步响应归属，并立即补可执行红绿记录。
3. 接入统一的有状态 Mock，补齐证据、设置、异步任务、审批、权限、语音等路径。每接一个能力就增加其 Feature Map 步骤和自动化。
4. 从干净浏览器上下文执行完整场景矩阵，修复卡片、键盘、语言输入、窄屏和返回路径问题，再完成里程碑验收。

## 2. Mock 开发和替换

细则、混合模式与状态列见 **[MOCK_REGISTRY.md](MOCK_REGISTRY.md)**（本表为摘要，以注册表为准）。

Mock 由应用数据边界提供，前端组件、用户操作与请求契约保持一致。优先使用测试 harness 内的有状态 HTTP/SSE 服务；浏览器路由拦截用于少量故障注入。每次运行初始化独立种子，测试可推进时钟、延迟或丢弃响应、重放和乱序事件。系统公开可观测的请求计数与业务状态供断言。模拟和真实数据模式明确标注。生产配置禁用 Mock 及测试控制入口；**真实模式禁止静默回退 Mock**。

| Mock 记录 | A 阶段开发 | 预定替换及验收 |
|---|---|---|
| M1 对话、任务、上下文、历史与卡片 | 种子含 SMT-03（可纯 Mock）、产品改进、独立会话；受理/拒绝/延迟/误关联/纠正 | **B1/B3**：可靠受理与关联持久 |
| M2 Run、进度、产物与事件 | 状态机、受控时钟、等待/取消/失败/重试；重复与过期游标 | **B2**：真实执行与重启对账 |
| M3 助理配置、记忆、偏好与已读 | 保存失败、版本冲突、未读行为 | **B3→C2**：配置持久与投递 |
| M4 频道、RelOS、MOM 和证据权限 | 两角色、撤权；可挂现有真实 MOM desk | **C1**：组织 ACL |
| M5 动作审批、业务写入与提醒 | 版本绑定、超时、副作用计数；可衔接真实 OpsCase 批准 | **C2**：动作网关 |
| M6 语音及跨端 | 脚本化麦/转写/插话；双上下文 | **混合收口**：fixture + 真机 + ASR stub + 双 context D01（第二物理机另验） |

每项替换：冻结契约 → Mock/真实对测 → 混合模式全量 Playwright → 验持久性/副作用 → 移除替身 → 更新 MOCK_REGISTRY。替换失败只在明确测试/演示模式切回 Mock。

## 3. 严格验收与回归

1. 在 A 开发前，以原始清单章节和条款文本建立逐条追溯记录。字段包含原文锚点、Feature ID、Case ID、覆盖层、所需环境、当前状态和证据位置。包括全部已确认、待实现及已演示行为；开放问题与建议记录决议，其落地部分纳入用例。章节覆盖表只是索引。
2. 功能实现前定义用例并取得符合预期的 Red 证据。环境失败不算 Red。已存在行为先记基线。场景包含正常、失败、恢复与受限行为，不随代码修改已冻结的断言。
3. 每个里程碑都运行三层检查。全前端 Playwright 在受控环境跑完整 Feature Map。集成套件跑前端、HTTP/SSE、数据和事件契约以及交叉模块流程。真实服务套件验证已替换能力的身份、存储、恢复及业务侧效果。
4. 沿用仓库 `npm run test:map`、`npm run verify` 和现有 CI 门禁。将具体路径和用例登记在 `docs/testing/features.json`、`CASES.md`，由 `docs/feature-map/COVERAGE.md` 记录覆盖证据。实现前的计划状态与证据状态独立。
5. Release 要求每条必验清单有对应自动化结果和环境标签。若限定为 Mock，保留真实服务的待验记录。任何必验失败、跳过、无法复现或清单无映射都阻断里程碑。保存 commit、Case ID、运行模式、退出码、trace/日志、状态断言和清理记录。

每次交付邀请未参与实现的验证者从 Feature Map 独立复跑 SMT-03 和至少一个失败恢复场景。发现步骤缺失、定位歧义或判据不可观察时修订地图，保留固定输入与断言后复跑。
