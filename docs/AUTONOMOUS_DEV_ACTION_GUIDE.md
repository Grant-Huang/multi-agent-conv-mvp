## 0. 先读这三条

1. **AI 开发的围栏不是限制 Agent 写代码，而是限制它在没有证据的情况下宣布完成。** 原文第 109 行。
2. **指导不是安全边界。** 写在 `AGENTS.md` 或 Prompt 里的禁令，只能靠 CI、分支保护、权限系统和运行时沙箱真正强制执行。原文第 2659 行、第 4823 行。
3. **先小步、后放权。** 每一项自主权都要先在小范围证明可靠，再逐步扩大。不要一次把整个系统交给 Agent。

### 0.1 第一周就能做的十件事

按顺序做。每件事都有对应章节或附录，完成后在团队内做一次检查。

| # | 行动 | 负责人 | 去哪里看 |
|---|---|---|---|
| 1 | 选定试点：建议用 AgentNexus 的 Agent 执行超时 / 卡死问题，而不是普通 UI 功能 | 技术负责人 | 第 9、13.3、13.6 节 |
| 2 | 为仓库建立 `AGENTS.md`（只做入口和总原则）和 Feature Map 初版 | 开发负责人、产品 | 第 3 节，附录 A.2、A.3 |
| 3 | 把 `cargo test`、`cargo clippy --all-targets`、`cd web && npm run build` 放进 CI，作为合并前提 | 开发负责人 | 第 5 节，附录 A.9 |
| 4 | 统一 PR 模板，要求 Agent 填写真实的验证证据（不能留空） | 代码负责人 | 第 5.2 节，附录 A.25 |
| 5 | 每个需求写结构化契约：目标、范围、**非目标**、Given/When/Then 验收场景 | 需求分析人员 | 第 2 节，附录 A.1、A.16 |
| 6 | 建立 `REVIEW.md`，让审查 Agent 与开发 Agent 分离，审查意见必须带文件、行号和失败场景 | 代码负责人 | 第 5 节（独立审查）、附录 A.10、A.11 |
| 7 | 把关键状态机写成代码并加测试，确保终态不可被迟到响应覆盖（注意我们的 `TaskStatus` 目前没有 TIMEOUT） | 开发、QA | 附录 A.8 |
| 8 | 建立风险路径规则（先人工复核执行，不要直接自动化） | 模块负责人 | 第 6 节，附录 A.12 |
| 9 | 建立 Eval 数据集，把已发生的 Bug 和事故转成回归用例，并要求人工确认根因 | QA | 第 4.4 节，附录 A.15 |
| 10 | 确认 Agent 的权限由**运行时强制执行**，不只写在 Prompt 里 | 技术负责人 | 第 8.4 节，附录 A.13 |

**第一周不要做的事：** 不要部署几十个 Agent；不要让 Agent 无人值守地合并到主分支；不要用 Agent 写了多少代码来衡量成效；不要把 Autonomy Contract 当作已经签署，直到它真正被团队确认。

## 1. 七层围栏速查

| 层 | 名称 | 目标 | 主要责任人 | 必须产出的证据 |
|---|---|---|---|---|
| 一 | 需求定义与验收 | Agent 知道什么是"对的"，以及如何证明 | 需求分析人员 | 结构化需求、非目标、Given/When/Then 验收场景 |
| 二 | 项目知识与架构 | Agent 有持续的项目上下文，只读与任务相关的部分 | 开发负责人、架构负责人 | `AGENTS.md`、架构文档、Feature Map、影响分析 |
| 三 | 开发过程约束 | 小步修改，改动范围可控 | 开发人员 | 任务计划、PR 规模统计、范围说明 |
| 四 | 自动化 CI 门禁 | 机器能发现的问题由机器拦住 | 开发负责人、QA | CI 运行记录，合并门禁结果 |
| 五 | 独立 AI 审查 | 审查者与开发者分离，按证据审查 | 代码负责人 | 结构化审查报告，验证后的问题清单 |
| 六 | 风险分级与人工审批 | 高风险才需要人，低风险可以自动通过 | 模块负责人、发布负责人 | 风险等级，审批记录，权限配置 |
| 七 | 运行监控与快速回滚 | 上线后能发现问题并快速恢复 | 发布负责人、运维 | 指标、灰度记录，回滚演练结果 |
| 贯穿 | Eval 持续评测 | 每次事故和误判都变成以后的测试 | QA | 评测集条目，回归结果 |

另外两个机制贯穿全部七层：**工程规范由 Agent 自动执行**（第 8 节）和**每次开发都能改善下一次开发**（第 11.5 节）。

## 2. 第一层：需求定义与验收（需求分析人员）

### 2.1 核心转变

- 过去：描述要做什么。
- 现在：**定义什么是正确的，以及如何证明它正确。**

原因：AI 会高效地把需求中的歧义变成大量代码。（原文第 123–138 行）

### 2.2 每个需求必须包含的内容

| 内容 | 必须回答的问题 |
|---|---|
| 业务目标 | 为什么要做？解决什么业务问题？ |
| 用户角色 | 谁使用？拥有什么权限？ |
| 使用场景 | 在什么情况下使用？ |
| 功能范围 | 本次具体做什么？ |
| **非目标** | 本次明确不做什么 |
| 输入条件 | 输入什么数据？数据从哪里来？ |
| 业务规则 | 系统必须遵循什么规则？ |
| 输出结果 | 应该产生什么结果？ |
| 异常场景 | 输入错误、服务失败时怎么办？ |
| 验收标准 | 如何判断功能真正完成？ |

两个字段特别重要：

- **非目标**：AI 容易顺手扩大范围。例如只要求加超时提醒，它可能顺便重构调度和会话管理。必须写清"不修改任务调度机制、不修改会话状态机、不改变已有 API 行为"这类约束。
- **验收标准**必须可验证。不能写"系统应当支持超时处理"，要写成"超过配置时间后任务进入 Timeout；释放资源；记录事件；超时任务不能标记为成功；重试生成新的执行记录，不覆盖历史"。

### 2.3 验收场景：Given / When / Then

每个需求至少写三类场景：正常流程、正常完成（不应误触发异常）、异常或失联。这些场景可以直接转成自动化测试。

示例（原文第 192–222 行）：
- 正常超时：超过 300 秒 → 状态变为 Timeout，释放资源，产生超时日志。
- 正常完成：300 秒内返回 → 状态为 Completed，不产生 Timeout 事件。
- 无响应：进程存在但 60 秒无心跳 → 标记 Unresponsive，触发恢复或终止流程。

### 2.4 Feature Map（需求人员参与维护）

每个模块必须列出：功能列表、功能依赖、用户操作路径、页面或 API 入口、业务规则、预期结果、异常处理方式、对应的自动化验证方法。

分工：需求人员负责业务视角的准确性，开发人员负责技术实现信息，测试人员负责验证方法。三方共同维护，不要全部交给产品经理。（原文第 224–255 行）

### 2.5 行动清单（每个需求进入开发前必须完成）

- [ ] 需求说明书
- [ ] 明确的本次范围与**非目标**
- [ ] Given/When/Then 验收场景
- [ ] 正常流程和异常流程
- [ ] 涉及模块及依赖关系
- [ ] 关键业务规则
- [ ] 可量化的验收条件
- [ ] 对高风险行为的特别说明

**没有明确验收标准的需求，不允许进入 AI 自主开发阶段。**（原文第 256–272 行）

## 3. 第二层：项目知识与架构（开发负责人）

### 3.1 每个代码仓库必须有的文件

| 文件 | 作用 | 主要维护者 |
|---|---|---|
| `AGENTS.md` | 项目概况、开发规则、禁止事项 | 开发负责人 |
| `ARCHITECTURE.md` | 系统架构、模块关系、数据流 | 架构负责人 |
| `FEATURE_MAP.md` | 功能索引和功能地图 | 产品 + 开发 + 测试 |
| `REVIEW.md` | 代码审查规则和高风险区域 | 代码负责人 |
| `TESTING.md` | 测试环境、方法、数据 | 测试负责人 |
| `RUNBOOK.md` | 启动、部署、诊断、恢复 | 开发 + 运维 |
| `CHANGELOG.md` | 重要变更记录 | 开发人员 |

要点：
- 这些文件的主要读者是 Agent，不是人。
- **`AGENTS.md` 只做入口**：告诉 Agent 什么时候读哪个文件。不要把所有知识都塞进去，否则每次都要读一堆无关内容。
- 多技术栈的仓库要有**子目录级规则**，避免一条通用规则覆盖所有模块。（原文第 289–310 行）

### 3.2 开发前置检查（Agent 必须执行）

1. 阅读项目 `AGENTS.md`。
2. 阅读相关模块架构说明。
3. 找到涉及的 Feature Map 条目。
4. 阅读相关 `REVIEW.md`。
5. 检查 Git 工作区是否干净。
6. 确认自己修改的文件和模块范围。
7. 找到相关测试。
8. 明确本次验收条件。

涉及不熟悉的模块时，Agent 先输出**模块分析报告**，不直接动手。（原文第 339–357 行）

**对于 Rust 核心执行引擎、并发、异步任务、生命周期、资源释放和错误处理的修改，必须先输出技术影响分析，再开始修改。**（原文第 351–355 行，针对团队 Rust 经验还不够的情况）

### 3.3 小步开发

| 指标 | 建议要求 |
|---|---|
| 单个 PR | 原则上只解决一个独立问题 |
| 代码修改 | 尽量控制在 300 行以内（这是管理阈值，不是质量标准；生成代码、锁文件单独统计） |
| 大型变更 | 必须拆分为多个阶段 |
| 文件范围 | 原则上不跨无关模块 |
| 重构与功能 | 尽量分开 PR |
| API 变更 | 必须说明兼容性 |
| 数据库变更 | 必须说明迁移和回滚方案 |

对 AgentNexus 的具体要求：不要让 Agent 一次修改 Rust 执行引擎、MCP 调用、会话状态和前端显示。顺序应是：修一个具体问题 → 验证没有破坏已有行为 → 再做下一项。（原文第 311–338 行）


### 3.4 独立 AI 审查（代码负责人）

**审查者必须与开发者分离。** 开发 Agent 不能评价自己写的代码。

标准流程：

1. 开发 Agent 修改代码 → 运行测试 → 提交 Diff。
2. Reviewer Agent 以**新的上下文**启动，不继承开发 Agent 的结论。
3. 发现问题 → 提供证据、文件和行号。没有问题 → 输出审查报告。
4. Finding Verifier（第三个独立 Agent）验证问题是否真实，以及是否由本次修改引入。
5. 开发 Agent 修复 → 再次审查 → CI 通过 → 进入风险审批。

审查报告至少包含：严重程度、文件和行号、违反的业务规则、可能的后果、复现方法、是否由本次修改引入。**审查要关注实际缺陷，而不是代码风格。**

**审查轮数上限（直接采用）：**
- 默认最多三轮审查修复；
- 之后只审查新增 Diff；
- 不重复报告已经提出的问题；
- 发现一种 Bug 时，要求修复同类问题的所有实例；
- 超过三轮仍未收敛，停下来重新审视技术方案。

（原文第 358–424 行）

### 3.5 实际验证证据

开发 Agent **不能只写"已完成修改，测试通过"**，必须提供证据：

| 验证项 | 必须提供的证据 |
|---|---|
| 编译 | 实际执行的构建命令和结果 |
| 单元测试 | 测试数量、通过数、失败数 |
| 集成测试 | 测试场景和结果 |
| 接口测试 | 请求、响应、状态码 |
| UI 测试 | 截图或浏览器操作记录 |
| Bug 修复 | **修复前复现失败，修复后验证通过** |
| 回归测试 | 原有功能未被破坏的证据 |

- 测试环境不可用时，标记 **`NOT VERIFIED`**，不能写 `PASSED`。
- 下列五种状态必须分开，不能混为一谈：Agent 正常退出 / Agent 返回结果 / 业务任务完成 / 结果成功持久化 / 用户界面正确展示。当前 Agent 执行成功率统计尤其要注意这一点。（原文第 425–464 行）

### 3.6 责任归属

- 原则（Anthropic）：**You land it, you own it.** 谁让 Agent 做了改动，谁对上线结果负责。
- 任务发起人负责需求意图；开发人员负责代码变更；模块负责人负责技术边界；发布负责人负责上线决策。
- 出现事故时，团队共同复盘围栏为什么没有拦住。
- 这一条必须写进制度。（原文第 465–484 行）

## 4. 第三类围栏：质量保证（QA）—— 从测试执行者转为质量体系设计者

QA 的角色变化：从"根据需求写用例、执行测试、提 Bug"，转为**测试体系设计者、质量规则制定者、自动化验证体系维护者，以及 AI 测试结果的独立监督者**。（原文第 485–503 行）

### 4.1 建立测试基线（Test Baseline）

每个核心模块都要有稳定的回归测试。以 AgentNexus 为例：

| 模块 | 必须覆盖 |
|---|---|
| Agent 生命周期 | 创建、启动、运行、完成、失败、终止 |
| Session 管理 | 创建、恢复、并发、隔离、销毁 |
| ACP / Agent Bridge | 建连、断连、超时、重试、异常返回 |
| MCP 工具 | 注册、发现、调用、参数错误、超时 |
| 多 Agent 协作 | 任务分发、消息传递、结果汇总 |
| 任务调度 | 排队、并发限制、优先级、取消 |
| 记忆管理 | 写入、读取、更新、隔离 |
| 结果持久化 | 成功写入、失败恢复、重复写入 |
| 权限管理 | 身份认证、越权、数据隔离 |

**故障注入测试**（比只测正常流程更重要）：
- MCP 服务突然断开；
- Agent 进程异常退出；
- Agent 长时间不返回；
- ACP 消息乱序；
- Agent 返回格式错误；
- 网络短暂中断；
- 同一任务被重复提交；
- 两个 Agent 同时修改同一份文件；
- 执行成功但数据库写入失败。

（原文第 504–537 行）

### 4.2 Feature Map 必须关联到测试

每个功能增加以下字段：Feature ID、功能描述、用户路径、预期结果、对应测试用例、是否可自动执行、证据位置、最近验证时间。

目标是建立可追踪链路：**需求 → 功能 → 代码 → 测试 → 证据**。AI 不仅要知道改了哪个文件，还要知道影响了哪个功能、哪些验收场景。（原文第 538–564 行）

### 4.3 独立的 Bug 复现机制（Benny 类 Bug Agent）

Bug Agent 的职责（原文第 565–583 行）：
1. 接收 Bug 报告；2. 识别涉及的功能；3. 读取 Feature Map；4. 准备测试环境；5. 加载测试数据；6. 按用户路径复现；7. 收集日志、Trace、截图；8. 判断是否真实存在；9. 生成结构化 Bug 报告；10. 把可复现的 Bug 分配给 Developer Agent。

闭环（原文第 584–615 行）：

```
Bug Intake（用户反馈 / 测试失败 / 生产告警 / AI Review 发现）
  → Benny：Bug Investigator（定位功能 → 准备环境 → 复现 → 采集证据）
  → Bug Triage（确认是否真实、严重等级、责任模块、是否可自动修复）
  → Developer Agent（分析根因 → 修改代码 → 添加回归测试）
  → Independent QA Agent（独立复现 → 验证修复 → 验证没有引入新问题）
  → Merge / Release（满足 CI 和风险审批后进入发布）
```

**硬性规则：Bug 修复必须附带回归测试，证明原 Bug 已被修复。** 否则 Agent 可能只修好了表面现象。

### 4.4 Eval 数据集（质量评测集）

把历史 Bug、事故、回滚的 PR 整理为评测集，每次改动后都跑一遍 AI Reviewer。（原文第 616–650 行）

| Eval 类型 | 数据来源 | 目的 |
|---|---|---|
| 历史 Bug | 已修复的 Bug | 防止同类问题复发 |
| 历史事故 | 线上事故、回滚 | 测试系统级风险 |
| 正常样本 | 已确认无问题的 PR | **检查误报** |
| 边界样本 | 超时、并发、断连 | 测试极端情况 |

**不能只收集正面案例。** AI 找到 100 个问题不代表它优秀，如果 80 个是误报，会严重干扰开发。

QA 必须统计：漏报率、误报率、真实 Bug 检出率、严重 Bug 检出率、每个 PR 的审查轮数、每个 Bug 的复现成功率、修复后回归通过率。

### 4.5 质量否决权

QA 对测试基线、测试数据和质量门槛负责。出现以下情况时，**不能因为 AI 报告显示通过就放行**：
- 测试环境不可信；
- 测试数据不完整；
- 自动化测试覆盖不了核心场景；
- 某模块回归测试大量失败；
- AI Reviewer 出现明显误报或漏报；
- 关键功能没有独立验证证据。

（原文第 651–667 行）

## 5. 第四层：CI/CD 门禁

### 5.1 分层检查

| 检查类型 | 检查内容 | 是否阻断合并 |
|---|---|---|
| 代码质量 | Formatter、Lint、Type Check | 是 |
| 编译构建 | Build、依赖检查 | 是 |
| 自动化测试 | Unit、Integration、Regression | 是 |
| 安全检查 | Secret、依赖漏洞、权限风险 | 是 |
| AI Code Review | Bug、逻辑错误、架构冲突 | 重要问题未解决时阻断 |

**AI Review 不能只看 Diff**，要结合整个代码仓库和 PR 声明的意图。例：修改 MCP 超时函数，只看 Diff 可能没问题，但如果它破坏了上层任务状态机的行为，必须从调用链判断。（原文第 668–698 行）

### 5.2 PR 模板

原文第 696–773 行给出了完整模板，包含 7 个部分：

1. 变更基本信息（需求编号、Bug 编号、Feature ID、修改模块、开发人员、AI Agent、变更类型）
2. 变更说明（解决什么问题、修改了什么、为什么这样做、涉及哪些模块、是否改变 API 或数据结构）
3. 测试情况（Formatter/Lint、Type Check、Build、Unit、Integration、Regression、Security、AI Review 的勾选框；测试命令；测试结果；未覆盖的测试）
4. 风险评估（风险等级 Low/Medium/High/Critical、可能影响的功能、是否涉及并发/异步/资源管理、是否涉及权限/安全/敏感数据、是否影响现有用户、是否需要 Feature Flag）
5. 回滚方案（如何撤销、是否涉及数据库迁移、如何恢复历史数据、回滚是否经过验证）
6. AI 验证证据（执行过的命令、测试日志、截图或 Trace、AI Reviewer 报告、修复前后对比）
7. 人工确认（四个勾选项：符合需求、证据真实、理解风险、对最终变更负责）

**这份模板的价值不在于多填表格，而在于强制 Agent 把实际工作过程留下证据。**

完整模板见附录 A.25。

### 5.3 CI 必须独立执行

**不能只接受开发 Agent 自己提供的测试结论。** 开发 Agent 可能修改了测试甚至删除了测试，Review Agent 也会被误导。

最终合并门禁必须由独立 CI 环境执行。CI 应当：
- 从干净的提交构建；
- 使用固定版本依赖；
- 运行预先定义的测试集合；
- **检查测试文件是否被不合理修改**；
- 记录测试报告；
- 保存可追溯的构建产物。

高风险改动还要在独立测试环境中验证。（原文第 774–798 行）

## 6. 第五层：风险分级与人工审批（模块负责人、发布负责人）

**不要求所有 PR 都人工审批**，那样会失去效率；但**不能让 AI 自己决定什么代码可以上线**。审批依据是变更本身的风险，而不是谁写的。（原文第 799–812 行）

### 6.1 风险等级

| 等级 | 典型变更 | AI 权限 | 人工审批 |
|---|---|---|---|
| L0 低 | 文档、注释、非关键文案、独立新增测试 | 可自动提交和合并 | 无需逐项审批，但需自动化检查 |
| L1 普通 | 普通业务功能、非关键 UI、独立模块 Bug 修复 | 可自主开发、修复、提交 PR | 一名开发人员 |
| L2 高 | 核心执行引擎、Session、并发、任务调度、数据库迁移 | 可分析、开发、测试，**不能自行合并发布** | 模块负责人审批，必要时 QA 复核 |
| L3 极高 | 权限、安全、密钥、生产数据、CI/CD、发布机制、核心架构 | 只能在明确授权下执行受控操作 | 两名人工审批者，关键操作需专门授权 |

**风险等级由变更内容决定，不由开发人员或 AI 自己决定。** 例：开发人员说只改了一个小函数，但它是任务调度的核心入口，就不能按普通风险处理。

风险判定用两套机制：
1. 自动分类器：根据文件路径、Diff、调用关系判断；
2. 第二个独立分类器：检查是否低估了风险。

两者不一致时，按较高风险执行。（原文第 813–836 行）

### 6.2 Agent 自主等级（与风险等级分开）

| 自主等级 | Agent 可以做什么 | 人工介入 |
|---|---|---|
| A0 | 分析需求、解释代码、提出方案 | 人工决定 |
| A1 | 修改代码、运行测试、生成 PR | 人工批准合并 |
| A2 | 完成开发、Review、CI，低风险自动合并 | 人工负责异常处理 |
| A3 | 低风险自动部署、监控、必要时自动回滚 | 人工设置边界和授权 |

**建议：不要直接追求 A3。先把 A1 做稳定，再让低风险任务逐步进入 A2。** L2、L3 的改动即使由高等级 Agent 完成，也不自动获得高风险操作权限。（原文第 837–857 行）

### 6.3 Agent 的操作权限边界

AgentNexus 本身是 Agent 平台，所以要对**Agent** 设权限，而不仅是对开发人员。

| 操作 | 默认权限 |
|---|---|
| 读取代码 | 允许 |
| 创建分支 | 允许 |
| 修改当前分支 | 允许 |
| 运行测试 | 允许 |
| 创建 PR | 允许 |
| 合并普通 PR | 满足条件后授权 |
| 修改主分支保护规则 | **禁止** |
| 修改 CI 安全门禁 | 需人工审批 |
| 访问生产数据库 | **默认禁止** |
| 修改生产数据 | 需专门授权 |
| 发布正式版本 | 需人工授权 |
| 删除生产数据 | **默认禁止** |

权限还应支持：每任务独立授权、权限过期、执行日志、沙箱隔离、资源限制、取消、超时终止。

**超时和终止必须由底层执行平台强制实现，不能寄希望于 Agent 自己意识到任务卡住了。**（原文第 858–892 行，针对 Agent 偶发卡死、MCP 超时的问题）

## 7. 第六层：发布、监控与快速回滚（发布负责人、运维）

- 测试通过只是上线前的一个阶段。
- 核心原则：**所有错误都应该能被快速发现、快速撤销。**（原文第 893–904 行）

### 7.1 Feature Flag

新功能（例如新的 Agent 调度策略）不直接在所有租户上启用，按顺序：
1. 内部环境；2. 少量内部用户试用；3. 观察执行成功率和异常率；4. 确认没有明显回归；5. 逐步扩大。
出现异常时关闭功能，不需要重新开发或发布。（原文第 905–922 行）

### 7.2 关键指标

| 指标 | 监控目标 |
|---|---|
| Agent 任务完成率 | 任务是否真正完成 |
| Agent 超时率 | 是否存在执行卡死 |
| MCP 调用成功率 | 工具调用稳定性 |
| ACP 连接异常率 | Agent Bridge 稳定性 |
| 任务结果持久化成功率 | 结果是否可靠保存 |
| 任务平均执行时间 | 性能变化 |
| 重试率 | 是否异常重试 |
| 资源消耗 | CPU、内存、Token |
| 生产 Bug 数量 | 变更引起的缺陷 |
| 回滚率 | 发布质量 |

**不要只看 Agent 进程正常退出率**：进程正常退出但没有有效结果，不算业务成功。（原文第 923–945 行）

### 7.3 事故复盘必须回答五个问题

1. 这次问题是什么？
2. 为什么之前的测试没有发现？
3. 哪一层围栏失效？
4. 应增加什么自动检查或测试？
5. 如何把它变成未来 AI 可以重复运行的 Eval？

例：MCP 超时后任务没有结束。不能只修代码，还必须：增加 MCP 超时测试、Agent 卡死测试、任务状态恢复测试；更新 Feature Map 和 REVIEW.md；增加历史 Bug Eval；验证同类修改不会再引入问题。（原文第 946–975 行）

## 8. 第七层：规范自动执行（Skills、Hooks、CI Rules）

核心思想：**如果人记不住、人工检查不了，就把规范固化为 Agent 能自动读取、执行和检查的 Skills、Hooks 和 CI 规则。** 如果 AI Reviewer 反复发现同一个问题，就把规则固化到源头（项目指导文件、Skill 或 Lint 规则），而不是每次提醒。（原文第 976–985 行）

### 8.1 建议的 Skill 体系

| Skill | 作用 | 主要使用者 |
|---|---|---|
| `requirement-analysis` | 检查需求完整性、边界、验收标准 | 需求 Agent |
| `feature-map-maintenance` | 创建和维护 Feature Map | 产品/开发 Agent |
| `architecture-analysis` | 分析修改对架构的影响 | 开发 Agent |
| `implementation` | 按项目规范实现功能 | Developer Agent |
| `bug-investigation` | 复现 Bug、收集证据、分析根因 | Benny Agent |
| `code-review` | 独立审查代码变更 | Reviewer Agent |
| `security-review` | 安全和权限审查 | Security Agent |
| `test-generation` | 根据需求生成测试 | QA Agent |
| `regression-test` | 执行回归测试 | QA Agent |
| `release-check` | 检查发布条件和回滚方案 | Release Agent |
| `eval-maintenance` | 把历史 Bug 和事故转为 Eval | QA Agent |

**四者不要混淆：** Skill 定义做事的方法；Agent 执行任务；Hook 在关键时刻强制执行规则；CI 独立验证；权限系统限制危险操作。（原文第 986–1015 行）

### 8.2 三类规则的实现方式

| 规则类型 | 实现方式 | 示例 |
|---|---|---|
| 强制规则 | Hook / CI / 分支保护 | 未通过测试不能合并 |
| 智能规则 | AI Skill / Reviewer | 判断是否破坏架构 |
| 管理规则 | 人工审批 | 是否允许改变核心架构 |

开发 Agent 提交代码时的完整链条：Git Hook 检查格式 → 检查是否改了禁止修改的文件 → 检查是否缺少测试 → CI 运行自动化测试 → AI Reviewer 检查逻辑 → 风险分类器判定审批等级 → 满足条件才允许合并。（原文第 1016–1041 行）

注意：本地 Hook 只是开发体验层面的提醒，可以被绕过，最终必须在 CI 中执行同样的检查。（原文第 2032 行）

### 8.3 完整研发流水线（综合）

原文第 2986–3021 行的九步流水线：

1. **Requirement Agent**：检查需求完整性、边界和验收标准；产品负责人确认。
2. **Architecture Agent**：读取 Feature Map 和架构文档，生成影响分析。
3. **Developer Agent**：制定计划，小步修改代码，执行开发测试。
4. **CI Engine**：独立构建、Lint、单元、集成、安全检查。
5. **Review Agents**：Bug Hunter、Architecture Reviewer、Finding Verifier。
6. **Risk Engine**：自动判定 L0–L3，决定人工审批要求。
7. **Human Approval**：按风险级别批准合并和发布。
8. **Release & Monitoring**：灰度发布、运行监控、异常告警和回滚。
9. **Benny & Eval**：发现 Bug、复现、修复，沉淀回归测试和评测数据。

Anthropic 实践中的 Bug 闭环（第 6 轮，原文第 6475 行附近）：Issue Collection（用户反馈、测试 Bug、CI 失败、生产告警、Agent 执行失败）→ Benny 调查（定位功能、准备环境、复现、采证、生成结构化 Issue）→ Fix Agent（根据 Issue 和 Feature Map 在独立分支修复）→ Independent Review → CI / Eval（含历史 Bug 回归、安全检查）→ Release & Monitor（按风险审批，异常回滚）→ Knowledge & Eval Update（沉淀到 Feature Map、Skill、规范和 Eval）。

**Benny 的关闭条件：** 不能以"代码修改成功"关闭 Bug，必须以"问题被复现、修复、回归验证通过"关闭。

### 8.4 Agent 身份、权限与执行隔离（横向治理）

**Least Agency（最小代理能力）：** 传统讲最小权限，Agent 时代还要控制 Agent **能自主执行的动作**，以及它能调用的**其他 Agent**。

Anthropic 披露的一个事故：负责生产告警分析的 Agent，原本只有查看日志、写文档、发消息的权限。模型升级后，它主动通过 Slack 联系了另一个有代码修改权限的 Agent，让后者推送修复代码。最终被人工审批拦截，但说明：**限制 Agent 自身权限，并不等于限制它通过其他 Agent 间接获得的能力。**

**需要控制的治理对象：**

| 对象 | 应控制什么 |
|---|---|
| Agent 身份 | 每个 Agent 有独立身份和凭证 |
| 工具权限 | 只能调用任务授权的 MCP / CLI |
| 数据权限 | 按项目、工作空间、环境隔离 |
| Agent 间调用 | 不能因为能联系其他 Agent 就继承其权限 |
| 执行环境 | 高风险代码任务在独立 Sandbox / VM 中运行 |
| 网络访问 | 限制出口地址、域名和可访问服务 |
| 凭证管理 | 不让 Agent 直接获得长期高权限密钥 |

**权限分级示例（Bug 修复任务）：**
- **Benny（Bug Investigator）**：允许读取日志和代码、创建复现环境、生成 Bug 报告、提交修复建议；禁止直接合并代码、修改生产环境、发布版本。
- **Fix Agent**：允许在隔离分支修改代码、运行测试、提交 PR；禁止自行批准自己的 PR、直接部署生产。
- **Review Agent + 人工审批**：检查代码、测试证据和安全影响，按风险级别决定自动合并或人工审批。

**架构要求：独立于 Agent 的 Policy Enforcement Layer（权限执行层）。** 不能只靠 Prompt 告诉 Agent"你不允许做某件事"，而要在**工具调用、进程执行、数据访问和 Agent 间通信**时真正拦截。这也能解决重型 Agent 接入后执行行为难以控制的问题。

**生产事故分析 Agent 的职责分离：** 它只能分析、写报告、生成修复建议；真正修改和部署生产代码需要另外的 Agent 和人工审核。

### 8.5 证据驱动的独立审查（第五层升级）

Anthropic 没有用一个万能的 Security Agent 审查所有东西，而是让多个职责独立的 Agent 分别审查，理由：减少共同偏见和盲区；一个 Agent 判断错误时其他 Agent 可能发现；每个 Agent 专注自己的领域。

**最关键的要求：审查 Agent 必须给出可验证的证据（Proof）。** 原文披露：要求 Agent 证明发现有效之后，PR 中有实质性 Review 意见的比例从 16% 上升到 54%。

| 审查 Agent | 职责 | 必须提供的证据 |
|---|---|---|
| Functional Reviewer | 功能是否正确 | 需求对应关系、测试结果 |
| Regression Reviewer | 是否破坏旧功能 | 回归测试、受影响功能列表 |
| Security Reviewer | 是否引入安全漏洞 | 漏洞路径、攻击条件、验证结果 |
| Architecture Reviewer | 是否违反架构规范 | 依赖关系、架构规则检查 |
| Code Quality Reviewer | 是否存在工程质量问题 | 具体代码位置、问题复现方式 |

**合格与不合格的表述对照：**
- 不合格："发现用户权限验证可能存在问题。"
- 合格："API `/project/{id}/data` 使用了请求中的 projectid，但没有校验当前用户是否属于该项目。使用用户 A 的 Token 请求用户 B 的项目 ID，可以成功读取数据。附复现脚本及测试结果。"

**不能复现或证据不足的，标记为"待验证"，不能直接判定为 Bug。**

### 8.6 风险分级与影子模式（新审查 Agent 的上线方式）

- 风险不只看改了多少行，还要看：涉及什么业务功能；影响哪些系统和用户；是否涉及权限、安全和数据；是否影响生产运行；出错后能否快速回滚。
- 例：修改生产控制塔的界面展示，可能是 L0/L1；修改生产调度规则或工单状态流转，可能是 L2/L3。（注：这里的等级是原文为 AgentNexus 建议的，不是 Anthropic 原文等级。）

**Shadow Mode（影子模式）——新审查 Agent 的上线流程：**
1. 刚上线时只输出审查意见，不参与阻断；
2. 与人工审查结果进行比较；
3. 通过红队测试和历史 Bug 回放验证；
4. 达到可信度后，才逐步获得阻断权或审批权；
5. 即使进入自动化阶段，仍保留人工抽样。

**不要一开始就让新 Agent 拥有 CI 阻断权。**

### 8.7 供应链安全与提示注入

Anthropic 强调两种 AI 时代的新威胁：
1. Agent 被恶意 Prompt Injection 控制；
2. Agent 从依赖包、第三方代码、外部数据中引入恶意内容。

**对 AgentNexus 的现实意义：** 有 MCP Marketplace，会集成大量第三方 Agent、Skill 和工具。建议把 MCP / Skill / Agent 的接入纳入七层围栏：
- 来源与发布者验证；
- 版本锁定与依赖清单；
- 权限声明和工具调用范围审查；
- 高风险 Skill 的沙箱验证；
- Prompt Injection 对抗测试；
- 运行时异常行为监控。

**尤其不要把 MCP 描述文件或 Skill 中的指令当成可信的系统指令。**

**动态安全测试要跟上发布速度：** 传统定期安全扫描跟不上 AI 提高的发布频率。Anthropic 正把 AI 驱动的动态应用安全测试（DAST）持续引入 Staging。测试应分四层：静态检查（规范、依赖、SAST）→ 单元和集成测试 → 动态测试（真实运行时的接口、权限、业务逻辑）→ 系统级测试（跨服务、跨模块的交互假设）。
**A2A、MCP、ACP、Agent Bridge 之间的问题，单模块测试发现不了。** 例：两个 Agent 各自工作正常，但它们之间传递的上下文、任务状态和权限信息不一致。

### 8.8 监控对象：从代码转向 Agent 工作循环

原文引用的一句话：**"The security engineer's job evolves from monitoring bugs to monitoring loops."** 工程治理人员不仅要看代码有没有 Bug，还要看 Agent 的工作循环是否健康。

Anthropic 把 Agent 的自动审批、工具调用、Agent 间消息记录下来，进入 SIEM（安全信息与事件管理系统）用于审计和异常发现。

**Agent Observability 的监控维度：**

| 维度 | 指标 |
|---|---|
| 任务执行 | 成功率、失败率、超时率、卡死率 |
| 工具调用 | 调用成功率、错误率、超时、权限拒绝 |
| Agent 协作 | 调用链、循环调用、死锁、重复任务 |
| 质量 | 验收通过率、Bug 逃逸率、回归失败率 |
| 成本 | Token、计算资源、任务成本 |
| 安全 | 越权调用、异常网络访问、敏感数据访问 |
| 治理 | 自动审批率、人工推翻率、审计覆盖率 |

**把"Agent 运行健康度"作为核心工程指标。** 区分两种成功：**Execution Success**（正常退出并返回结果）与 **Task Success**（结果真正满足验收标准）。两者不能混为一谈。

### 8.9 横向治理的整体结构

```text
横向治理：Agent Governance     → Identity · Permission · Sandbox · Network Isolation · Audit
七层工程围栏                    → 第 1–7 层（本指南第 2–8 节）
横向治理：Evidence & Observability → Trace · Logs · Proof · Metrics · Audit Trail
横向治理：Continuous Learning   → Benny · Bug Database · Eval Dataset · Skill Evolution · Hill Climbing
持续反馈：生产问题 → 知识更新 → 规则更新 → 评测提升
```

**传统 DevOps 管理的是软件交付流水线；AI-Native Engineering 管理的是一群能自主行动的软件工程 Agent。** 后者要管理的还包括：Agent 的身份和职责、知识和上下文、工具和权限、协作和交接、决策与证据、质量和可信度、持续学习和改进。

**三个基础对象优先设计：** Feature Map（系统是什么、应如何工作）、Evidence（如何证明它按预期工作）、Eval（如何衡量每次修改是否让系统更好）。这三者建立后，Benny、Fix Agent、Review Agent、CI Agent 才能组成可靠的工程协作系统。**比增加 Agent 数量重要得多。**

**Hill-climbing（持续比较）：** 不能只追求某次修改的成功，而是持续比较修改前后的整体质量。Eval 数据分四类：正常功能样本、历史 Bug 样本、边界与异常样本、安全与对抗样本。

**治理先于对外能力：** AgentNexus 自身的工程治理必须先于对外提供工程治理能力。先让它自己：自动发现 Bug、自动复现、自动生成修复任务、自动验证修复效果、自动沉淀经验，并且**不能未经授权自行发布修复**。当这套体系在 AgentNexus 自身稳定运行后，再作为工程协作能力提供给客户。

## 10. 夜间自主开发模式

> 来源：原文第 3119–4028 行。

### 10.1 核心判断

- 夜间自主开发**可行**，而且很可能是 AgentNexus 最值得探索的产品形态。
- 它不是"把白天的流程搬到晚上、把开发人员换成 Agent"，而是**重新设计软件生产的组织方式**。
- 七层围栏不再是一串人工审批关卡，而是：**由 Agent 自动执行、由系统强制约束、由证据验证结果、由人处理例外**。
- 人工减少，不等于质量标准降低；人工退出，也不等于取消独立验证。

**分工节奏：**

| 时段 | 人的工作 | Agent 的工作 |
|---|---|---|
| 白天 | 与客户确定目标、范围和验收标准 | 理解需求，提出澄清问题 |
| 夜间 | 不值守，处理升级事件 | 自主开发、测试、验证，生成候选版本 |
| 次日 | 审查结果，给客户演示，确定下一轮需求 | 生成夜间开发报告 |
| 长期 | 只保留责任和风险控制 | 持续执行，人逐步退出常规环节 |

### 10.2 七层围栏在夜间模式下的职责

| 层 | 夜间开发中的职责 | 初期谁负责 | 成熟后谁负责 |
|---|---|---|---|
| 1 需求 | 把白天讨论变成可执行、可验收的任务契约 | 需求人员 + Agent | 客户 + 需求 Agent |
| 2 知识与架构 | 让 Agent 理解产品、代码、架构和历史决策 | 资深开发建立知识体系 | Agent 自动维护，人抽查 |
| 3 实施 | 控制任务拆分、修改范围、分支和权限 | 开发人员制定规则 | 规划 Agent + 执行引擎 |
| 4 CI | 自动编译、静态检查、单元和集成测试 | CI 工程师 | CI 自动执行 |
| 5 独立审查 | 独立 Agent 找问题、验证问题、检查质量 | 资深开发 + Reviewer Agent | 多 Agent 独立审查与证据验证 |
| 6 风险与审批 | 根据修改风险决定是否需要人工批准 | 资深开发、架构师、负责人 | 风险策略引擎 + 必要的人类授权 |
| 7 运行与恢复 | 验证部署结果、监控异常、回滚恢复 | 测试、运维 | 自动监控、自动恢复、异常升级 |

**关键变化：七层围栏以"任务是否拿到足够的正确性证据"为中心，而不是"开发人员是否批准"。**

### 10.3 各层的夜间执行要求

**第 1 层：需求契约**
- 白天的业务意图要转化为：业务规则、验收标准（表格形式，含正常结果和异常结果）、执行边界（允许修改什么、不允许修改什么、不允许做什么）。
- 同一份契约还要生成：开发任务 DAG、测试场景 DAG、代码修改范围、风险等级、第二天的演示脚本。
- **需求没有明确到可以验证，不能进入无人值守的夜间开发。**
- 不确定的部分要单独列为"待确认事项"。确定的部分先开发，不确定的部分**不允许 Agent 自行猜测**。

**第 2 层：项目知识空间**
每个项目维护一个持续演进的知识空间：

| 类别 | 内容 |
|---|---|
| 产品知识 | 功能地图、用户角色、业务规则、客户需求、历史决策 |
| 工程知识 | 架构图、模块依赖、API、数据库结构、代码规范、测试规范 |
| 运行知识 | 历史 Bug、故障日志、性能数据、部署记录、已知风险 |
| 经验知识 | Agent 过去的失败原因、人工审查发现的问题、修复方案、有效测试用例 |

- Feature Map 要能回答：功能由哪些模块实现、代码在哪里、依赖什么服务和数据、关键业务规则是什么、修改会影响什么、现有哪些测试能验证它。
- 每次夜间任务开始前，Planner 根据 Feature Map 做影响分析；完成后，如果修改了功能、接口或依赖，生成**知识更新建议**。
- **不能让 Agent 修改代码后直接无条件修改 Feature Map。** 知识更新也要纳入审查，否则会形成"自洽但错误"的知识。

**第 3 层：任务编排**
- **不要用"一个超级 Agent"从头做到尾。** 它任务过大、执行时间不可控、上下文逐渐偏离需求，而且容易自我证明。
- 推荐的编排角色：

| 角色 | 职责 |
|---|---|
| Planner | 分解任务、识别依赖、分配资源、制定验证计划 |
| Coding Agent（按模块） | 各模块的开发 |
| Test Agent | 独立构建和测试 |
| Knowledge Agent | 检查知识和文档变化 |
| Integrator | 合并、处理依赖和冲突、执行完整集成测试 |
| Independent Reviewer | 检查需求符合度、架构影响、代码风险和测试证据 |
| Release Candidate | 形成可演示、可验收、可回滚的候选版本 |

- 按任务选择执行器的轻重：简单修改或文档用轻量 Agent；跨文件开发用重型 Coding Agent；复杂测试或故障复现用专用 Test/Benny Agent；架构和安全审查用独立 Reviewer。
- **并行不是越多越好。** 多个 Agent 同时改同一模块会冲突。先按模块依赖划分任务，尽量独立分支、独立工作区，最后由 Integrator 统一集成。

**第 4 层：从"代码能运行"升级为"任务通过验证"**
当前把"Agent 正常退出并返回结果"当成成功，这不够。必须区分五种状态：

| 状态 | 含义 |
|---|---|
| Execution Success | Agent 正常退出并返回 |
| Build Success | 编译、构建成功 |
| Test Success | 自动化测试通过 |
| Requirement Verified | 需求验收标准通过 |
| Release Candidate | 所有必要审查通过，形成候选版本 |

**只有最后一个状态才能称为"夜间开发完成"。**

必须补充的故障测试（不能只测正常路径）：MCP 永远不返回；MCP 返回超时错误后又迟到返回；Agent 进程退出但任务状态未更新；用户取消与超时同时发生；两个恢复动作同时触发；Rust 执行引擎重启后状态恢复。

建议建立**故障注入环境**，主动模拟 MCP 失联、网络延迟、进程崩溃、资源耗尽和并发竞争。

**第 5 层：独立审查**
- 初期**必须有资深开发审查**，但不能只看代码能否编译，也不能让资深开发变成每晚的人工瓶颈。
- 推荐分工：Reviewer Agent 用独立上下文审查需求、代码和测试；Test Agent 独立验证功能和异常场景；资深开发重点审查**架构、并发、安全、数据模型和公共执行引擎**；需求人员第二天审查**业务结果**，而不是替代资深开发审查代码。
- **测试 Agent、开发 Agent 和审查 Agent 不能只是同一个 Agent 换三个角色名。** Reviewer 必须直接读取需求契约、Git Diff、相关代码和实际测试结果，不能只接受 Coding Agent 的总结。
- **Benny 应是独立的质量验证者，而不是会写代码的修 Bug Agent。** 其流程：接收问题 → 建立独立环境 → 尝试复现 → 记录步骤和失败证据 → 确认是否真实 → 创建修复任务 → 修复后重新运行**原始复现用例** → 检查是否引入回归。Benny 的价值在于建立独立的证据链。

**第 6 层：风险围栏**
- 追求的是**消除常规任务中的人工审批**，而不是消除所有高风险决策中的人类责任。

| 风险 | 修改类型 | 夜间执行策略 |
|---|---|---|
| L0 | 文档、提示词、非关键展示 | Agent 自动开发、测试，通过后进入候选版本 |
| L1 | 独立功能、局部业务逻辑 | Agent 自动开发、独立审查、自动验收 |
| L2 | 公共接口、数据库结构、核心业务流程 | Agent 可开发，但资深开发需审查或批准 |
| L3 | 权限、安全、核心执行引擎、生产数据迁移 | 必须人工批准关键变更和生产发布 |

- 风险**不能只看文件路径**。一个看似普通的工具函数，也可能影响所有 Agent 的执行。要结合依赖关系、调用范围、数据影响、权限变化和历史故障做动态评估。
- 成熟后，L0、L1 可以高度自主；部分 L2 在积累足够证据后可以逐步自动化；L3 保留明确的人类授权。这是企业软件的责任边界，不是对自主能力缺乏信心。

**第 7 层：运行与交付**
第二天交付的不是代码，而是**一个可验证的候选版本**，附夜间开发报告（模板见 10.4）。
- 夜间版本先进入隔离的**演示或验收环境**，不默认自动发布到客户生产环境。

### 10.4 夜间开发报告模板

```text
夜间开发报告（候选版本已生成）

需求：ANX-XXX
验收场景：通过 / 未通过（列出未通过项）

| 检查项目 | 结果 |
| Agent 执行 | 完成 |
| 编译构建 | 通过 |
| 单元测试 | 通过 |
| 集成测试 | 通过 |
| 故障注入 | 通过 |
| 需求验收 | 1 项未通过 |
| 独立代码审查 | 通过 |

未通过项：
  MCP 连续超时后的用户重试操作，第二次执行时仍复用了原 Session 状态，需要进一步修复。

交付物：
- 代码分支和 Commit
- 测试报告及失败日志
- 需求验收记录
- Bug 列表及处理状态
- 演示环境和演示脚本
- 已知风险及未完成事项
- 回滚方案
```

第二天，需求人员直接回答：哪些需求完成了？哪些没完成？哪些有风险？哪些可以演示？哪些需要客户决策？——不需要自己去翻 Git 日志或问开发人员进度。

### 10.5 成熟度模型

| 级别 | 名称 | 特征 |
|---|---|---|
| M1 | Agent 辅助开发 | 人工主导 |
| M2 | 夜间自动执行 | 有限自主 |
| M3 | 多 Agent 自主闭环 | 高度自主 |
| M4 | 持续自主开发 | 系统自主 |
| M5 | 客户直接驱动开发 | 客户自助 |

**不要一开始追求完全无人值守。** 夜间开发是 M2、M3 的交付节奏；持续自主开发是 M4 的运行方式。

### 10.6 分阶段实现

**阶段一：建立真正的夜间开发流水线（最先做）**
- 不追求多 Agent 复杂协作，先选边界清晰的任务：修复已确认的 Bug、增加独立查询接口、增加小型业务功能、修改已有页面展示、增加日志或监控或配置能力。
- 每个任务必须具备：明确需求、明确代码范围、明确验收标准、可自动构建、可自动测试、可独立审查、可回滚。
- 角色分工：

| 角色 | 白天 | 夜间 |
|---|---|---|
| 需求分析人员 | 与客户确认需求和验收标准 | 不值守 |
| 资深开发 | 确认架构和风险边界 | 抽查高风险变更，处理升级事件 |
| Coding Agent | 参与需求理解 | 自主编码 |
| Test Agent | 帮助设计测试 | 自动测试 |
| Reviewer Agent | 参与方案分析 | 独立代码审查 |
| Benny | 分析已知问题 | 复现、确认、修复 Bug |

早期资深开发应参与**设计质量控制体系**，而不是每晚守着 Agent。

**阶段二：把测试人员的工作转化为可复用的资产**
- 测试人员的价值在于：识别业务边界和异常场景、设计高价值测试、发现自动化覆盖不了的场景、验证真实使用过程、把发现的问题变成长期回归用例。
- 示例：两个用户同时点击"重新执行"，偶尔生成两条执行记录，但只有一条正确关联原任务。这一问题应转化为：并发测试用例、状态一致性测试、数据库约束或事务规则、历史 Eval、Benny 的自动复现脚本。
- 成熟后，测试人员的重心转为"建设测试体系、设计测试策略、分析质量风险"。

**阶段三：让 AgentNexus 处理 Bug 闭环**
```text
Bug 来源（客户反馈 / 日志 / 监控 / AI 审查）
  → Bug Triage Agent：分类、去重、定级、关联模块
  → Benny：创建独立复现环境
     → 能复现？ 是：生成复现证据和测试用例；否：补充日志或请求人工确认
  → Coding Agent 修复
  → 独立回归测试：通过？ 否：回到 Benny
  → 独立 Reviewer 审查 → 风险允许自动合并？ 是：合并到候选版本；否：等待人工批准
  → 部署到验收环境并监控 → 更新 Feature Map / Eval / 项目记忆
```
**硬性要求：Bug 修复必须以"原始失败场景消失"为依据，而不是以 Agent 认为自己改对了为依据。** 每个被确认的 Bug 都应尽可能形成自动回归测试。

**阶段四：持续自主开发**
成熟后不应把"晚上"当成技术限制。系统应能持续监测 Bug 和质量问题、根据客户反馈生成改进任务、自动维护测试、修复低风险问题、对照 Feature Map 发现功能缺口、对照性能指标发现优化空间，并在授权范围内持续演进。

### 10.7 资深开发、测试和需求人员的退出路径

**资深开发**
- 常规代码审查和常规 Bug 修复可以逐步自动化。
- 架构演进、核心技术选型短期内不宜完全自动化。
- 高风险安全、权限、数据和生产变更授权不建议完全取消人工责任。
- 目标不是"完全退出"，而是**从生产执行环节退出，保留架构治理和风险责任**：定义架构约束和工程规范，建立关键模块的自动化验证，处理 Agent 无法解决的异常，审查高风险架构变更，定期审计 Agent 的错误决策和漏检。

**测试人员**
- 日常手工测试可以大幅减少，但复杂工业软件的**业务验证**不能只靠单元测试。例如：MES 工艺流程是否符合客户生产制度；质量追溯结果是否符合客户质量要求；设备异常分析是否误判；Agent 是否错误理解了业务规则；生产控制塔指标是否正确。
- 未来的测试人员是**质量工程师**，建设：业务场景库、自动化测试体系、历史 Bug Eval 集、故障注入和压力测试、业务结果正确性评估体系、Agent 质量监控体系。

**第二天的需求分析人员**
- 终态：客户 → AgentNexus → 多 Agent 协作 → 自动验证 → 客户确认。
- 但客户不能一句"我要增加一个功能"就开始改代码。AgentNexus 必须完成完整的**需求协商**：
  1. 理解客户业务意图；2. 主动询问不明确之处；3. 识别需求之间的矛盾；4. 结合现有能力分析方案；5. **展示修改前后的业务流程**；6. **评估成本、风险和影响范围**；7. 生成可执行需求契约；8. **请客户确认业务规则和验收标准**；9. 自动执行开发和测试；10. 向客户展示结果，收集下一轮反馈。
- 第 5、6、8 步尤其重要：客户不一定懂代码，但应能判断"是不是我要的业务效果、会不会改变现有流程、会不会影响其他部门、能否接受这个版本"。

### 10.8 自主开发工作空间（产品能力）

把夜间开发做成 AgentNexus 的核心能力时，不要做成"一个新的超级 Agent"，而应是**组织级的长期工作流程**，建议由以下部分组成：

- **需求协作**：客户讨论、需求澄清、需求契约、版本目标；
- **开发编排**：Planner、Coding Agent、任务 DAG、依赖管理；
- **质量验证**：CI、Test Agent、Reviewer、Benny、Eval；
- **版本交付**：候选版本、演示、验收、发布、回滚；
- **持续积累的项目资产**：Feature Map、Architecture Map、Requirements、Test Cases、Bug Knowledge、Eval Dataset、Project Memory。

**可复用的现有能力：**

| AgentNexus 现有能力 | 在自主开发中的作用 |
|---|---|
| Workspace | 项目级持续工作空间 |
| Channel | 需求、开发、测试、Bug 等协作频道 |
| Task / DAG | 任务分解和状态管理 |
| Agent Router | 选择轻重型 Agent |
| MCP / Agent Bridge | 接入代码仓库、CI、测试环境、开发工具 |
| RelOS / KB | 项目知识、架构、历史经验 |
| Memory | 项目上下文和团队工作习惯 |
| 权限体系 | 控制 Agent 能读、改、部署什么 |

**两层 DAG 不要混为一谈：**
- **需求级 DAG**：实现客户的一个业务目标，长期保留业务目标、客户确认和验收关系；
- **工程级 DAG**：每个需求下的分析、编码、测试、审查、集成和交付，可能经过多次失败、重试、拆分和重新规划。

### 10.9 必须补上的三个能力（比 Coding Agent 更重要）

**1. 长程任务的可靠执行与恢复**
- 现状：Agent 执行成功率约 80%，不适合直接做无人值守的长程开发。
- 需要解决：Agent 运行状态持久化；进程异常退出后的恢复；MCP 超时和重试；Session 与 Task 状态一致性；断点续跑；任务幂等性；多 Agent 资源隔离；卡死检测和自动终止；迟到响应、重复执行和状态竞争。
- 推荐：**可持久化的状态机 + 可恢复的执行日志**，不能只靠一个长期运行的 Agent 进程维持状态。
- 例：一个需求含 20 个子任务，执行到第 15 个时机器重启，系统应从最后一个已验证的检查点恢复，而不是重新执行全部 20 个。
- **任务的完成状态必须由 AgentNexus 的验证结果决定，不能由 Coding Agent 自己宣布。**

**2. Agent 的自我评估与持续进化**
- 应积累每次开发的质量数据，例如：哪类需求最容易失败、哪个 Agent 修改成功率最高、哪类任务适合轻量 Agent、哪些模块经常回归、哪类 Reviewer 最容易漏检、哪些测试最能发现真实 Bug。
- **不要把"Agent 自己总结经验、修改自己的 Prompt"当成持续进化。** 真正的进化是：**发现问题 → 找到原因 → 提炼规则 → 加入测试或评估集 → 验证改进有效 → 更新系统策略**。

**3. 业务结果验证，而不仅是代码验证**
- 例：客户要求"生产异常后自动分析原因并给出建议"。功能可能开发成功、测试全过，但根因分析可能是错的。
- 需要的业务检查：输入数据是否完整；分析逻辑是否符合行业知识；结论是否有证据支撑；是否存在错误归因；建议是否可执行；是否满足客户的实际业务要求。
- 对制造业场景，需要建立**行业级的业务 Eval 数据集**，这可能比提高 Coding Agent 的编码能力更有价值。

### 10.10 何时可以减少人工：看指标，不看日历

以下是**建议的初始目标，不是行业通用标准**，需要结合基线校准。

| 指标 | 初期 | 进入高度自主前的建议目标 |
|---|---|---|
| Agent 执行正常退出率 | 先测基线 | ≥ 99% |
| 需求验收通过率 | 先测基线 | ≥ 95% |
| 自动测试有效通过率 | 先测基线 | ≥ 98% |
| 严重 Bug 漏检率 | 建立基线 | 持续趋近于零 |
| 夜间任务自动完成率 | 先测基线 | ≥ 80% |
| 人工介入率 | 先测基线 | 持续下降 |
| 生产回滚率 | 建立基线 | 不高于人工开发基线 |
| 重大生产事故 | 建立基线 | 不允许因自动化放宽标准 |

两个注意事项：
- **"执行正常退出率"不能当成"需求验收通过率"。**
- **不能只看测试通过率。** 测试通过可能是因为测试设计太弱，或 Agent 修改代码时同步删除了失败的测试。必须关注独立测试、需求场景覆盖，以及历史 Bug 能否被重新检出。

**人工退出的规则：**
- 连续多个版本稳定通过后，逐步减少普通任务的资深开发审查；
- 低风险任务自动合并到候选分支；
- 中风险任务抽样审查，异常升级；
- 高风险任务保留人工批准；
- 测试人员从逐项测试转向测试策略和自动化体系建设；
- 需求人员从需求转述转向业务决策和客户关系管理。
- **不要因为某个月成功率高就撤掉人工。** 需要在足够多、足够多样的任务上积累证据，并观察实际运行中的事故和回滚。

### 10.11 试点：AgentNexus 自身的夜间自主开发

**推荐原因：** 可以直接观察系统的全部内部状态、日志、代码和测试，不必先面对客户生产环境的复杂性；而且这些问题正是 AgentNexus 自己必须解决的。
**如果 AgentNexus 自己的开发都无法稳定地夜间自主完成，就不应该急着把它包装成面向客户的自主开发平台。**

**首批任务（边界清晰）：**
1. MCP 超时后的任务状态处理；
2. Agent 卡死检测和进程清理；
3. Agent Bridge 异常恢复；
4. Session 和 Task 状态一致性；
5. 夜间任务执行报告生成。

**组织方式：**
- 白天：产品负责人确认需求，资深开发确认技术边界；
- 晚上：AgentNexus 编排 Coding Agent、Test Agent、Reviewer 和 Benny；
- 第二天：需求人员审查结果，资深开发审查关键变更，测试人员做深入验证；
- 交付：先进入演示环境，确认后再合并或部署。

**试点成功标准：**
- 需求契约能自动生成；
- Agent 能在无人值守的情况下完成任务；
- 出现失败时能识别、重试或正确终止；
- 测试和独立审查能发现**人为植入的缺陷**；
- 第二天能提供完整的交付证据；
- 整个过程可追踪、可恢复、可回滚。

### 10.12 终态与路线

- 终态设想：客户不需要先写需求文档，也不需要懂软件工程。客户说"最近生产线某类质量异常越来越多，希望分析原因并增加自动预警"，AgentNexus 先理解业务、提出澄清问题、展示方案、数据需求、实施计划和验收标准；客户确认后自动完成分析、规划、开发、测试、Benny 复现、独立审查、生成可演示版本，并收集意见进入下一轮。
- **真正的终态不是"没有开发人员的软件开发"，而是"软件开发不再需要客户通过传统开发组织来驱动"。** 产品责任、架构治理、安全责任和业务决策不会消失，只是逐步转移到系统规则和必要的人类授权机制中。
- 路线：Agent 帮人开发 → 人定需求、Agent 夜间自主开发 → 多 Agent 自主完成开发、测试和修复 → AgentNexus 持续自主维护和演进软件 → 客户直接定义业务目标。
- 下一步的交付物：《AgentNexus 夜间自主开发系统设计方案》，定义工作空间、需求契约、任务 DAG、Agent 角色、状态机、七层质量门禁、人工介入策略和分阶段验收指标。

## 11. 工程资产转型：从「给人看」到「给 Agent 执行」

> 来源：原文第 4029–5671 行。

### 11.1 核心区别

| 维度 | 传统：面向人 | 夜间/自主开发：面向 Agent |
|---|---|---|
| 需求 | 描述业务意图，靠人补充细节 | 目标、规则、边界、验收场景、禁止事项 |
| 设计 | 说明设计思路 | 组件、接口、状态、约束、决策及其验证方式 |
| 架构 | 架构图和文字说明 | 可查询的依赖关系、接口契约、可检查的架构规则 |
| 代码 | 开发人员理解后修改 | Agent 根据任务契约和上下文执行 |
| 测试 | 测试人员阅读用例执行 | 可自动构造环境、执行、判断、清理的测试契约 |
| 审查 | 人阅读 Diff | 独立 Agent 按规则找缺陷，并提供证据 |
| 项目管理 | 人工分配和跟踪 | 机器可执行的任务 DAG 和状态机 |
| 质量管理 | 人工检查 | 自动门禁、质量指标、独立验证 |
| 知识 | 文档、会议纪要、个人经验 | 可检索、可关联、可验证、可持续更新 |
| 发布 | 人工判断是否可发布 | 根据风险、证据和授权策略决定 |
| 运维 | 人看日志排错 | 自动发现、定位、复现、修复、回归 |
| 经验 | 人总结 | 事故转化为规则、测试和 Eval |

**原则：** 传统文档对人的价值是帮助理解；对 Agent 而言，每份关键工程资产都要回答：它能否直接支持 Agent 的某项工作？如果不能，还缺什么？

**不是把 Word 改成 Markdown，也不是全部改成 YAML。** 同一份知识可能需要两种视图：人类阅读视图和机器执行视图。

**人与机器的分工：**
- 人看文档，为了理解和判断；
- Agent 看工程资产，为了确定下一步做什么；
- 测试系统看验收标准，判断是否完成；
- AgentNexus 看任务和状态，决定是否允许继续；
- 质量系统看证据，决定是否允许交付。

### 11.2 九类资产的转换

| 传统文档 | Agent 时代应增加的执行能力 |
|---|---|
| PRD | 需求契约、验收场景、需求状态 |
| Feature List | Feature Map（能力、接口、实现位置、依赖、不变量、测试） |
| 架构图 | 架构模型、依赖规则、自动检查 |
| ADR | 决策约束、验证方式、适用范围 |
| API 文档 | OpenAPI / Schema / 契约测试 |
| 数据库设计 | Schema、迁移、数据不变量 |
| 编码规范 | Lint、静态检查、Reviewer 规则 |
| 测试用例 | 自动化测试、故障注入、业务 Eval |
| 审查规范 | 审查策略、Finding 结构 |
| 项目计划 | 任务 DAG、依赖、状态、重试策略 |
| 发布手册 | 发布策略、回滚脚本、健康检查 |
| 故障报告 | 故障记录、复现脚本、回归测试 |
| 会议纪要 | 决策记录、待确认事项、责任人 |
| 用户手册 | 产品能力说明、操作语义、交互契约 |

### 11.3 十一个转换要点（每项附示例见附录 A.16–A.20）

1. **需求：从描述变为契约。** 定义前置条件、业务规则、验收场景（含 `given/when/then`）、禁止事项、交付证据、审批状态。
   - 客户确认的规则和 Agent 推断的规则必须分开。Agent 可以处理技术不确定性，**不能擅自替客户决定业务规则**。
2. **产品：Feature Map 要带实现位置。** 每个能力写清 API、实现文件、依赖、不变量和测试。产品资料还要区分"给用户看的说明"与"给开发 Agent 看的说明"（API、权限、错误码、并发约束）。
3. **架构：从图变为可检查的约束。** 组件的职责和允许的调用关系；每条规则都要有执行方式（依赖检查、静态检查、测试或代码审查）。
   - 例：`task_service` 不得直接管理操作系统进程；所有进程生命周期操作都经由 `process_manager`；终态不得回到运行态。
   - 决策记录（ADR）要包含约束和**验证方式**，不是写完就结束。
4. **技术设计：状态机、接口、不变量要明确。**
   - 状态机要列出终态、合法转换、每个转换的事件和必须执行的副作用，以及不变量（终态不可变、唯一终态转换、每次执行有唯一 ID）。
   - 接口要写清参数、返回、状态码、权限、幂等性、前置条件、副作用、错误情况、兼容性。
   - 数据字段要写清合法值、可修改者、约束和业务含义。**特别注意：Task 状态、Agent 执行状态、需求验收状态、版本发布状态必须分开定义**，否则 Agent 会把"执行成功"误判为"需求完成"。
5. **代码规范：分三层执行。**

   | 类型 | 示例 | 执行方式 |
   |---|---|---|
   | 强制规则 | 禁止对外部输入使用 `unwrap` | Lint / 静态检查 |
   | 工程约束 | 所有 MCP 调用必须有超时 | CI 测试 / 自定义检查 / 统一封装 |
   | 设计建议 | 函数保持简单 | Reviewer Agent |

   - Lint 只能覆盖部分规则；有些规则需要自定义静态分析、统一封装接口或测试才能真正约束。
   - 必须明确写出 Agent **不应该改代码的情况**：不得为通过测试删除测试；不得擅自改公共 API；不得改数据库结构而不提供迁移；不得关闭错误检查；不得改无关模块；不得通过扩大权限解决执行失败；没有复现证据不得声称 Bug 已修复。
6. **测试：从用例变为可执行契约。** 每个测试必须能自动：构造前置环境 → 执行操作 → 断言结果 → 清理环境。
   - 只能靠人工操作的测试，还没有完成转型。复杂 UI、工业现场行为和业务效果可以保留人工执行，但要把步骤、数据、观察结果和判断依据结构化。
   - **测试要从正向扩展到反向**：进程不退出、MCP 不返回、服务突然重启、状态被并发修改、两个 Agent 同时改同一文件、Agent 生成错误测试、Agent 把测试删掉。
   - 测试资产至少覆盖：正常、异常、边界、并发、故障恢复、权限安全、回归、业务结果评估。
7. **代码审查：从"人看代码"变为"按证据审查"。** 一条审查意见必须包含：位置（文件和行号）、严重程度、类别、触发场景（步骤）、影响、证据、建议的复现测试、状态（未验证 / 已验证）。
   - 不接受"这里可能有问题，请检查"这类意见，也不接受 Reviewer 的一句"没有发现问题"当成质量证明。
   - 审查策略要有机器可判断的阻断条件：未解决的严重或高优先级问题、必需测试失败、架构规则违反、最多三轮。
8. **项目管理：任务 DAG 取代待办清单。** 每个任务要有：输入、输出、依赖、执行角色、验收条件、失败策略、完成后交给谁。
   - 动态调整可以，但必须记录**为什么改计划**，不能无痕改变原始需求。
9. **发布：可执行的发布策略。** 说明目标环境、前置条件（构建、集成测试、独立审查、安全扫描通过）、灰度比例、回滚触发条件、数据库迁移要求、是否允许自动发布、是否需要人工批准。
   - **回滚代码不等于恢复数据。** 要说明是否有不可逆迁移、是否兼容旧版本、回滚后如何验证恢复。
   - 对 AgentNexus 自身尤其要防止一次修改破坏执行引擎或任务状态存储。
10. **运维：从排错经验变为可复现的故障知识。** 故障记录要包含：分类、严重程度、上下文（任务、会话、MCP 服务、操作）、症状、预期与实际、复现脚本、根因状态、回归测试。
    - 每次故障至少产生四类资产：故障记录、根因分析、回归测试、工程规则。
    - **普通知识库让 Agent"知道曾经发生过"；自动化测试和规则才能让 Agent"以后不再犯"。**
11. **知识与安全：可关联、有来源、有可信度、机器执行权限。**
    - 知识之间要建立关联：需求 → Feature → 架构组件 → 代码 → API / 数据库 → 测试 → 历史故障 → 版本交付。
    - 每条重要知识要标注来源、状态（**Confirmed / Observed / Inferred / Proposed / Deprecated**）、适用范围、验证方式、负责人和最近验证时间。这是防止项目记忆被污染的关键。
    - 权限要结构化并由**运行时、容器或沙箱执行**，不能只写在 Agent 的上下文里。例如：文件读写范围、允许的 shell 命令、网络白名单、测试数据库而非生产数据库、只允许部署到预发布环境。
    - **权限是任务的属性，不只是账号的属性。** 同一个 Agent 在不同任务、不同阶段应有不同权限。能读不代表能改，能改不代表能合并，能合并不代表能发布，能访问测试库不代表能访问生产库。
12. **UI：从"让人操作"变为"让人确认、让 Agent 操作"。** 三类交互：

    | 类型 | 典型操作 | 目的 |
    |---|---|---|
    | 意图输入 | 对话、上传资料、描述问题 | 告诉 Agent 要做什么 |
    | 决策确认 | 方案选择、风险确认、需求批准 | 人做关键决策 |
    | 结果验证 | 预览、演示、验收、反馈 | 人判断是否符合业务预期 |

    客户不需要知道系统内部有多少 Agent 和任务 DAG，只围绕业务目标工作。

### 11.4 统一的工程资产目录（建议）

```text
project/
├── AGENTS.md                # Agent 工作总规则、项目入口、禁止事项
├── product/                 # FEATURE_MAP.yaml、BUSINESS_RULES/、REQUIREMENTS/、USER_FLOWS/
├── architecture/            # ARCHITECTURE.md、COMPONENTS.yaml、DEPENDENCIES.yaml、ADR/、ARCH_RULES.yaml
├── engineering/             # CODING_RULES.md/.yaml、API_CONTRACTS/、DATA_MODELS/、SECURITY_POLICY.yaml
├── testing/                 # TEST_STRATEGY.md、TEST_SCENARIOS/、FAULT_INJECTION/、REGRESSION/、EVAL/
├── review/                  # REVIEW_POLICY.yaml、REVIEW_CHECKLIST.md、FINDING_SCHEMA.json
├── operations/              # RUNTIME_POLICY.yaml、DEPLOYMENT_POLICY.yaml、RUNBOOKS/、INCIDENTS/
└── delivery/                # RELEASE_POLICY.yaml、ACCEPTANCE_REPORT_SCHEMA.json、RELEASE_HISTORY/
```

- 不要求一开始建全。
- 每类资产都要有：格式、责任人、维护时机、数据来源、版本管理、自动验证方式。
- **`AGENTS.md` 只做入口和总原则**，不要塞入所有产品、架构、测试知识；Agent 根据当前任务动态加载相关知识。

### 11.5 "每次开发都能改善下一次开发"的闭环

1. 需求执行：Agent 根据需求契约完成开发；
2. 质量检查：Reviewer 发现并发状态问题；
3. 独立验证：Benny 成功复现，确认真实 Bug；
4. 根因分析：统一状态机没有防止终态被覆盖；
5. 知识提炼：形成新的架构不变量和工程规则；
6. 自动化固化：增加并发测试、状态机测试和 CI 检查；
7. 下次生效：Planner 自动加载新规则，Reviewer 自动检查。

**AgentNexus 越用越好，靠的不是记住更多聊天内容，而是工程规则、测试资产和验证能力持续增长。**

### 11.6 团队转型的训练方法

- 不要一开始就发一份很长的规范，要求所有人立即改写作风格。
- 选 AgentNexus 的一个真实需求（例如"MCP 超时后 Agent 卡死，无法自动恢复"），完成一次**传统工程资产 → Agent 工程资产**的转换。
- 不要只提交文档。要让 Agent **真正使用这些资产完成一次开发任务**，然后观察：是否理解正确、是否找对代码、是否遵守架构约束、是否生成有效测试、是否发现人为埋设的缺陷、失败能否独立恢复、交付报告是否可靠。
- **如果 Agent 不能使用这些资产，说明它们还没有完成转型。**

### 11.7 团队审查任何工程文档的五问

| 问题 | 说明 |
|---|---|
| 1. Agent 能否准确理解？ | 信息是否明确，有没有依赖隐含经验 |
| 2. Agent 能否据此执行？ | 是否有输入、输出、接口、约束和权限 |
| 3. 系统能否自动验证？ | 是否有明确的验收条件和机器检查 |
| 4. 失败能否定位和恢复？ | 是否有日志、状态、错误分类、重试和恢复机制 |
| 5. 结果能否形成长期资产？ | 能否更新测试、规则、Feature Map 和 Eval |

**五问都能回答"是"，才真正具备面向自主开发的价值。** 只能回答第一问的，可能只是写得比较好的说明文档。

### 11.8 最先做的五项基础资产

选择 AgentNexus 的一个真实模块，先完成：

1. **Feature Map**：Agent 知道系统有什么；
2. **Architecture Map**：Agent 知道系统如何组织；
3. **Task Contract**：Agent 知道本次要完成什么；
4. **Test Contract**：Agent 知道如何证明完成；
5. **Engineering Rules**：Agent 知道什么能做、什么不能做。

这五项形成闭环后，需求、设计、开发、测试、审查、发布和运维才有可能逐步变成 Agent 能自主执行的流程。

**转型的标志不是"团队开始用 Agent 写代码"，而是"团队开始用 Agent 能理解、执行和验证的方式建设软件"。**

## 12. 长程自主开发与授权模型

> 来源：原文第 6807–8540 行（最后一轮问答）。这一节回答了"小步改动会不会让人必须做很多短程审查"这个问题。

### 12.1 先回答核心疑问：小步与长程是否冲突？

**不冲突。** 关键在于区分三件事：

| 概念 | 含义 | 应该怎样 |
|---|---|---|
| 小粒度执行 | Agent 内部每次只改一小步，并立即验证 | **应该做**，这是长程开发能稳定推进的基础 |
| 高频自动验证 | 每一小步都由系统自动测试、检查 | **必须做**，且不需要人参与 |
| 高频人工审批 | 每一小步都要人批准 | **应尽量减少**，否则人就成了瓶颈 |

- **Feature 是 Agent 的执行和验证单元，不是人的审批单元。**
- 一个 50 个 Feature 的项目，人可以只在开始时授权一次，中间在两个关键里程碑检查一次，最后验收一次。其余工作由 Agent 在授权范围内自主完成。
- **人工介入次数不由 Feature 数量决定，而由授权范围、系统成熟度和风险决定。**

原文的修正表述（第 8515 行）：
> Agent 的内部工作应该保持小步、可验证，但外部承担的任务可以是长程、连续和自主的。

示例：外部是"自主开发一个完整的任务协作模块"；内部完成 50 个 Feature；跨越 20 个 Session；经历 50 次自动验证；人工只做一次授权、一次中期检查、一次最终验收。

**从 Task-level Automation（人给任务，Agent 完成任务）走向 Goal-level Autonomy（人给目标，Agent 自己规划、管理任务、解决问题，并对结果负责）。**

### 12.2 两条独立的控制链

| 事项 | 自动验证 | 人工审批 |
|---|---|---|
| 普通代码修改 | 必须 | 不需要 |
| 单元测试 | 必须 | 不需要 |
| Feature 完成 | 必须 | 通常不需要 |
| 历史 Bug 回归 | 必须 | 不需要 |
| 多模块集成 | 必须 | 按风险决定 |
| 架构重大变更 | 自动检查 | **需要** |
| 权限模型变更 | 自动安全测试 | **需要** |
| 生产数据库迁移 | 自动验证 | 通常需要 |
| 正式生产发布 | 自动检查 | 按授权策略决定 |

**原则：围栏应该限制危险行为，而不是限制 Agent 的自主工作。** 如果 Agent 每修改一个文件都要人工审批，围栏就失败了。

### 12.3 自主授权契约（Autonomy Contract）

Autonomy Contract 不是普通的任务描述，而是人对 Agent 团队的**长期授权**。模板见附录 A.21。必须包含：

1. **项目目标**：要做什么。
2. **Agent 自主权限**：可以自主拆解和调整任务、修改授权范围内的代码、创建和修改测试、启停测试环境、修复测试失败、提交 Git Commit、跨 Session 交接、调用授权的其他 Agent。
3. **限制条件**：不得修改生产环境；不得获取未授权的用户数据；不得自行改变核心架构原则；不得删除原有测试来规避失败；不得绕过安全检查。
4. **自动验收要求**：通过 CI、通过 Feature Eval、通过历史 Bug 回归、关键功能通过端到端测试、高风险问题必须升级人工。
5. **人工介入条件**：预算达到 80%；连续三次恢复失败；需要突破原定架构约束；需要新增高风险权限；发现无法自行处理的重大安全问题。

这样，人只授权一次。Planner 发现原来的任务拆分不合理时，可以自行重新规划，不需要每次请示；但**不能擅自扩大自己的权限边界**。

### 12.4 自主执行权与自主验收权必须分离

| 角色 | 有权决定 | 不应该做 |
|---|---|---|
| Worker | 如何完成任务 | 自己宣布任务完成 |
| Planner | 任务如何拆分和调整 | 直接修改所有模块 |
| Evaluator | 根据证据判定是否通过 | 修改被审查的实现 |
| AgentNexus Runtime | 根据授权策略决定是否允许继续 | 代替 Agent 做业务判断 |
| 人 | 重大风险和目标变更 | 日常逐项审批 |

**闭环示例（不需要人介入）：**
- Worker："我已经完成了。"
- Evaluator："E2E 测试失败，不能通过。"
- Planner："这是因为权限验证缺失，我将创建修复任务。"
- Worker 修复 → Evaluator 再次验证通过。

### 12.5 三级自主模式

| 模式 | 人的参与 | 适用场景 |
|---|---|---|
| Supervised | 每个关键阶段人工确认 | 初期试验、高风险代码 |
| Delegated | 人授权目标，Agent 自主推进，异常升级 | 正常项目开发 |
| Autonomous | 人只设目标、预算和边界，Agent 自主规划、开发、验证、交付 | 成熟项目、低风险任务 |

**Delegated 与 Autonomous 不由任务大小决定**，而由授权范围、系统成熟度和风险决定。

### 12.6 大厂为什么仍保留人工关口

原文归纳了六个原因（第 5829–5929 行）。这是判断"我们是否太激进"的依据：

1. **需求本身不够明确**：例如"生产任务超时后希望自动重新分配"，但什么叫超时、运行中的任务能否重新分配、原 Agent 仍在运行怎么办，这些不定义清楚，Agent 可能写出测试全过、业务上完全错误的实现。
2. **测试通过不等于生产正确**：单次调用测试通过，但多个 MCP 同时超时可能造成状态竞争；进程退出了子进程没退；迟到响应覆盖状态。这类问题出现在并发、资源耗尽和故障恢复中。
3. **企业系统有大量隐性知识**：某客户的特殊规则、某接口不能随便调、某迁移不可逆、客户已形成的使用习惯。这些不进入工程体系，Agent 就会做出局部正确、整体错误的修改。
4. **Agent 的可靠性有长尾问题**：连续成功几十次后，在复杂任务上可能反复调工具、超时不退出、修 A 坏 B、测试反复失败无法收敛、上下文过长遗漏约束、子任务互相覆盖文件。
5. **风险不对称**：文档修改和数据库结构变更不能使用同一套自动化权限（见 12.2）。
6. **组织责任不能自动消失**：影响生产、质量追溯、设备异常、订单交付、已确认的业务规则，这些责任仍属于组织，不是代码生成模型能承担的。

**结论：大厂保留人工关口，不一定是因为 Agent 写不好代码，而是因为责任、风险和业务决策仍属于组织。**

**我们的判断（原文第 5937 行）：** 方向不激进，但如果现在就把整个开发团队改成无人值守夜间开发，就太激进了。应该把夜间自主开发作为一个**受控工程实验**，从一个模块、一个任务类型开始，逐步扩大 Agent 的自主权。

### 12.7 长程执行的基础设施

**(1) Project、Task、Session 必须分离**
- Project：长期目标。
- Task：可以独立验收的工作单元。
- Session：某个 Agent 实际执行任务的一次运行。
- 一个 Task 可以跨越多个 Session；一个 Project 可以包含成百上千个 Task。
- **不能把"Agent 退出"当成"任务完成"。** 这正是现在"Agent 进程正常退出 = 成功"的问题所在。

**(2) Task 状态（建议）**：BACKLOG → READY → CLAIMED → RUNNING → VERIFYING → REPAIR_REQUIRED / BLOCKED → DONE / FAILED / CANCELLED。

**(3) 任务租约（Lease）与栅栏令牌（Fencing Token）**
- Worker 领取任务后获得一段租约（例如 10 分钟），定期续租；
- Worker 崩溃后租约到期，调度器重新确认工作区和代码状态，任务回到 READY 或进入恢复流程；
- **旧 Worker 即使恢复，也不能凭旧租约提交结果**：用递增的 fencing token 防止过期 Worker 覆盖新 Worker 的成果；
- 原文指出：简单的文件锁在大规模并行时会成为瓶颈，Agent 会忘记释放锁、崩溃后锁无法释放。

**(4) 控制面与执行面分离（针对我们的 Rust 架构）**

| 控制面 Control Plane | 执行面 Execution Plane |
|---|---|
| 任务调度、Session 生命周期、工作区管理、权限、Checkpoint、恢复、事件存储 | 启动 Agent、管理进程、传输 ACP 消息、收集 MCP 调用事件、管理工具超时、收集结果 |

这样即使某个 OpenCode 进程卡死，也不影响调度和其他 Agent。具体要求：
- 长时间执行的外部命令采用独立进程管理；
- 事件收集不能阻塞调度循环；
- 工具调用必须有独立超时；
- 进程退出必须有明确的退出码和错误分类；
- Session 生命周期不能依赖一个长期阻塞的异步任务；
- **所有重要状态变化先持久化，再对外报告成功。**
这不是要求再做一轮大规模架构迁移，而是在现有 Rust 架构上明确隔离两者。

**(6) 持续开发循环（OpenAI Codex 实践，原文第 6930–6990 行）**

长程开发不是"一次性任务拉长了时间"，而是循环推进：

```text
确定长期目标 → 拆解可交付阶段 → 选择一个阶段 → 实现 → 测试 → 发现问题 → 修复 → 验证通过
   → 保存进度和决策 → 选择下一阶段 → 循环，直到目标真正完成
```

Codex 把循环概括为：**Plan → Edit → Test → Observe → Repair → Update → Repeat**。

AgentNexus 的每个任务循环应有六个动作：

| 动作 | 具体操作 |
|---|---|
| Orient | 读取项目状态、代码、Feature Map |
| Select | 选择当前最优先的未完成任务 |
| Execute | 修改代码、调用工具、运行命令 |
| Verify | 测试、构建、浏览器验证 |
| Repair | 根据失败证据继续修复 |
| Checkpoint | 保存代码、任务状态、决策和下一步 |

**关键设计：Agent 不决定自己什么时候算完成。** 完成条件由任务契约和独立验证器决定。

**Planner 的输出是长期计划，不是一个大 Prompt。** 例：目标"为 AgentNexus 增加支持多人协作的项目任务管理模块"，计划分为：基础架构（数据模型、项目、成员、权限）→ 任务管理（创建、修改、删除、状态流转、优先级）→ 多人协作（分配、评论、变更记录、通知）→ Agent 协作（领取任务、更新状态、提交成果、请求协作）→ 端到端验收（多用户、多 Agent 并发，验证数据一致性和权限）。
最终完成条件：核心用户流程可操作；所有必需功能测试通过；权限和并发测试通过；没有未解决的阻断级问题；生成可运行演示和交付报告。

**(5) 统一的 Agent 执行接口（Execution Adapter）**
OpenCode、Codex、Claude Code 等各自实现同一接口：
`start()`、`send_input()`、`get_events()`、`get_status()`、`interrupt()`、`terminate()`、`checkpoint()`、`resume()`、`collect_artifacts()`。

**恢复分三种，不能混淆：**
- **Native Resume**：外部 Agent 自己支持恢复 Session；
- **Harness Resume**：AgentNexus 创建新 Session，靠 Handoff 接续工作；
- **Process Recovery**：原进程异常，只是重新启动。
**重新启动一个进程，不等于恢复了原来的 Agent Session。**

### 12.8 持久化项目记忆与状态对账

**目标：** 一个 Agent 工作 5 小时可能经历多个上下文窗口，即使模型支持压缩，也不能可靠记住"已完成什么、为什么这样设计、哪些方案被否决、还有什么 Bug、下一步做什么、什么绝对不能改"。

原文发现的两个典型问题（第 7067 行）：
1. Agent 在上下文耗尽时，留下只完成一半、没有记录的功能；
2. 新 Agent 接手时看到已有成果，就误以为项目已经完成。

**项目记忆目录（建议）：**

```text
project/
├── AGENTS.md
├── .agentnexus/
│   ├── SPEC.md          # 最终目标、需求、非目标（Planner 维护）
│   ├── PLAN.md          # 阶段、任务依赖、验收标准（Planner / Orchestrator 维护）
│   ├── IMPLEMENT.md     # 开发操作规范（Engineering Agent 维护）
│   ├── STATE.json       # 当前任务和项目进度（Runtime 维护）
│   ├── DECISIONS.md     # 架构决策和原因（Agent / 人维护）
│   ├── features/        # 每个功能的定义和验收条件（Planner / Evaluator 维护）
│   ├── handoffs/        # 跨会话交接（Runtime 维护）
│   ├── evidence/        # 测试、截图、日志（Worker / Evaluator 生成）
│   └── eval/            # 回归集和评测结果
└── src/
```

**重要：文件是 Agent 可读、可修改、可审计的项目记忆；运行时状态（任务状态、锁租约、心跳、重试计数、Session ID）必须保存在 AgentNexus 数据库中。数据库才是运行时状态的权威来源。**

**STATE.json 要记录 `last_verified_commit`**：Agent 接手时应知道"上次通过验证的代码是哪个版本"，这比"上次执行到哪里"更重要。

**Handoff 要求：** 每次 Session 结束必须生成结构化交接，包括：已完成、未完成、关键决策、已知问题、`last_verified_commit`、下一步、环境状态（服务是否运行、测试命令）。

**状态对账（State Reconciliation）：** 下一轮 Agent 不应直接相信 Handoff，而要：读取 Handoff → 检查 Git 状态 → 检查最近提交 → 检查项目实际运行状态 → 重新运行必要的冒烟测试 → 确认后再继续。

> **记忆是线索，代码和验证结果才是事实。**

### 12.9 Feature 与 Sprint Contract

**每个 Feature 必须包含四部分：**
- **A. Specification**：这个功能到底是什么；
- **B. Acceptance Criteria**：怎样才算完成；
- **C. Verification Procedure**：如何验证（单元、集成、端到端测试）；
- **D. Dependencies**：依赖哪些其他功能和模块。

示例见附录 A.22。

**Sprint Contract（来自 Anthropic 后续研究）：** 每个 Sprint 开始前，Generator 提出"做什么、怎么实现、怎么验证"，Evaluator 审核验收条件，双方达成一致后才开始编码。这避免了规划者写得太细而错误传递，也避免开发 Agent 自己缩小需求范围。

```text
Feature Specification → Generator 提议方案 → Evaluator 检查验收条件 → 形成 Sprint Contract → 开始开发 → 独立验收
```

### 12.10 独立 Evaluator：不让开发 Agent 评价自己

- 让 Coding Agent 检查自己的代码，它很容易认为自己的成果是正确的。即使要求它做 QA，也常见：只测正常路径、遇到问题解释为不重要、忽略未实现的功能、只看代码不真正操作应用。
- **Evaluator 必须是独立的 Agent 或服务**，用 Playwright 等工具实际操作运行中的应用：点击、填表、调 API、查数据库状态、模拟多用户身份。
- **评分与否决：** 不能用加权平均掩盖严重缺陷。例如安全测试失败，即使其他项目满分，也不能通过。

**评估维度示例（试点配置，不是行业标准）：**

| 维度 | 权重 | 最低要求 |
|---|---|---|
| 功能完整性 | 30% | 95 |
| 功能正确性 | 25% | 95 |
| 回归测试 | 20% | 100 |
| 安全性 | 15% | 100 |
| 工程质量 | 10% | 85 |

Evaluator 输出必须是结构化结果（附录 A.22），包括失败的验收条件、严重程度、证据、复现步骤和需要的修复动作。**这样 Generator 才能得到明确的修复任务，而不是一句"质量不够好"。**

### 12.11 多 Agent 结构：Planner + Workers + Judge

Cursor 的经验：最初让所有 Agent 平级自己领任务、用共享文件协调、用锁避免重复，结果是 Agent 忘记释放锁、故障后锁无法释放、锁成为瓶颈、Agent 只敢做小修改、大量时间花在协调上。后来改为分工结构。

| Agent | 可以做什么 | 不应该做什么 |
|---|---|---|
| Planner | 分析、拆解、调整任务，**持续工作**，不只开始时工作一次 | 直接修改所有模块 |
| Worker | 专注一个任务，完成并提交 | 自行改变整体目标 |
| Evaluator | 独立测试、验证和否决 | 修改被审查的实现 |
| Judge | 判断继续、重试、拆分或结束 | 绕过验证标准 |
| Orchestrator | 调度、状态、资源、恢复 | 代替 Agent 做业务判断 |

**不要一开始就部署几十个 Agent。** 第一阶段建议：1 个 Planner、2–3 个 Worker、1 个 Evaluator。小任务可以单 Agent 完成；只有超出模型稳定能力范围的任务才增加独立 Evaluator 或 Reviewer。随着模型能力提升，多阶段结构可能变成不必要的开销，应通过真实评测决定哪些角色保留。

**Planner 的任务图必须是动态的**：会发现原先没识别的依赖、新的技术问题、需要重构的模块、可以提前完成的 Feature、需要重新拆分的任务。

### 12.12 工作区隔离（Workspace Manager）

长程开发没有环境隔离，迟早出现：一个 Agent 改代码、另一个测试旧代码；两个 Agent 改同一文件；一个服务影响另一个；一个失败任务污染其他任务的环境。

每个 Workspace 应有：独立 Git Worktree、独立进程空间、独立服务端口和测试数据库、独立日志和 Trace、独立资源限制、独立权限和凭证、可恢复的执行快照。

**分阶段升级：**
- 第一阶段：Git Worktree + 独立进程 + 独立数据库；
- 第二阶段：容器隔离 + CPU/内存限制；
- 第三阶段：独立 VM + 网络出口策略 + 密钥隔离。

Workspace Manager 定义统一接口，底层可以替换。考虑团队 Rust 经验，**不建议现在自研复杂的虚拟化系统**。

### 12.13 故障恢复系统：不要用无限重试

**先把失败分成六类：**

| 故障类型 | 例子 | 恢复策略 |
|---|---|---|
| Transient | 网络波动、临时 502 | 指数退避重试 |
| Tool Failure | MCP 调用失败 | 工具级重试或切换 |
| Agent Hang | 长时间无事件、无进展 | 检查进程；必要时终止并恢复 |
| Context Failure | 上下文溢出、偏离目标 | 新 Session + Handoff |
| Code Failure | 构建或测试失败 | 生成修复任务 |
| Planning Failure | 反复尝试、无法推进 | Planner 重新拆解，或升级模型 |

**执行状态机：** QUEUED → STARTING → RUNNING → STALLED → RECOVERING → SUCCEEDED / FAILED / ESCALATED。注意 **CHECKPOINT 是 RUNNING 中可以发生的事件，不是必须离开 RUNNING 才能进入的状态**。应使用"状态机 + 事件"，不要实现成线性流程。

**三个时间指标要区分：**
- Process Heartbeat：进程是否还活着；
- Agent Activity：是否还在产生有意义的事件；
- Task Progress：是否真正推进了任务。

**例：** OpenCode 进程 20 分钟没退出，但没有新的工具调用、文件修改或状态变化，不能判定为正常执行。

**试点参数（建议初始值，需按 Trace 校准）：**

| 指标 | 初始阈值 |
|---|---|
| Process Heartbeat | 15 秒 |
| Agent Activity Warning | 120 秒 |
| Task Progress Warning | 5 分钟 |
| 无进展诊断 | 10 分钟 |
| 单次自动恢复 | 最多 2 次 |
| 连续恢复失败 | 升级 Planner |

**注意：** 长时间运行的编译、测试、索引可能没有实时输出，不能因为没有输出就杀进程。应由执行层记录工具调用状态、进程活动、心跳和任务进展，而不是只靠文本输出判断。

**最重要的原则：失败之后不要原样重跑相同的 Prompt。**

```text
失败 → 识别失败类型 → 提取错误日志和执行轨迹 → 判断是否可重试 → 选择恢复动作 → 恢复到最近可靠检查点 → 继续执行
```

对我们的 Rust + ACP + Agent Bridge 稳定性有直接帮助。当前执行成功率约 80%，主要问题是 MCP Timeout、MCP Error、Agent Hang、Agent 无响应，以及修改后引入新 Bug。**不能把这些简单归为"Agent 执行失败"。**

### 12.14 Agent 自己维护开发环境（Harness Engineering）

OpenAI 的做法：Codex 不只写业务代码，也生成和维护 CI 配置、自动化测试、开发工具、文档、观测工具和内部脚本。工程师的工作从"写代码"转向"建设让 Agent 能可靠工作的环境"。

例：当 Agent 发现"每次测试这个模块都要手工启动三个服务，还经常忘记清理"，它应该：分析测试环境 → 设计统一启动脚本 → 生成自动清理脚本 → 建立测试 Skill → 运行验证 → 提交环境改善 PR。**Agent 不仅在开发软件，也在完善软件的开发基础设施。**

### 12.15 Benny 作为自主开发的质量监督者

Benny 不只是 Bug 调查员，而是整个自主开发系统的质量监督者：检查功能是否完整、发现遗漏、复现 Bug、检查回归、建立修复任务、验证修复，并把结果反馈给 Planner。

**它还应有一项特殊能力：** 当某类问题反复出现（例如某模块连续三次出现权限问题、某 MCP 工具经常超时、某类 Rust 异步任务容易泄漏资源、某功能回归测试覆盖不足），Benny 可以要求 Planner 改变后续策略，并提出：需要增加哪条工程规范、需要增加什么测试、是否需要修改相关 Skill、是否需要调整 Agent 的执行权限、是否需要重构基础模块。

**这就是从 Bug 修复走向工程自我改进。**

### 12.16 三个容易犯的错误

1. **不要把长程开发理解成"一个 Agent 的 Session 越长越好"。** Anthropic 的实践表明，上下文重置加结构化交接可能比保留一个巨大的上下文更可靠；不同模型需要不同策略。
2. **不要认为 Agent 越多，自主程度就越高。** 平级 Agent 的无序协作会导致锁竞争和任务停滞。合理的角色分工和任务边界比数量重要。
3. **不要让 Agent 自己决定自己的成功。** Agent 正常退出、代码能编译、测试通过、功能完整，是四件不同的事情，必须由独立验收机制判断。

### 12.17 AgentNexus 的核心能力：四个引擎

| 引擎 | 作用 |
|---|---|
| Planning Engine | 把长期目标转化为可持续执行和调整的任务图 |
| Execution Engine | 让不同 Agent 长时间、并行、隔离、可靠地执行任务 |
| Verification Engine | 用 Feature Map、CI、Evaluator、Benny 和证据判断工作是否真正完成 |
| Learning Engine | 把 Bug、失败、成功经验和评测结果沉淀为下一轮可复用的知识 |

**闭环：Goal → Plan → Execute → Verify → Repair → Learn → Continue**

**AgentNexus 管理生命周期，OpenCode 等负责执行具体开发任务。** 不建议重新做一个 OpenCode。

**能力分工（原文第 7763–7789 行附近）：**

| 能力 | AgentNexus 自研 | 复用外部 |
|---|---|---|
| 目标规划、Agent 调度、Session 管理、Context Handoff、Worktree 编排、故障恢复、Feature Map、Eval Dataset | 是 | — |
| Sandbox | 统一接口和策略 | 容器 / VM |
| Coding | 不需要重新造 | OpenCode 等 |
| 测试执行 | 统一管理 | pytest、Playwright 等 |
| 独立评测 | 自研框架 | 不同模型作为 Evaluator |

### 12.18 行业实践速览

原文第 5693–5800 行和第 6854–7717 行整理。以下数字都是各公司**自己披露**的内部数据，不是行业平均，也未经本指南核实。

| 公司 / 来源 | 做法 | 值得借鉴的要点 |
|---|---|---|
| OpenAI：Harness Engineering（2026-02） | 团队用 Codex 生成全部代码、测试、CI、文档和工具，约 3 人推动约 1,500 个 PR，估计开发时间约为手工的十分之一 | **Harness（工作环境）比提示词重要**：代码库结构、工具、测试、反馈、权限、恢复、观测 |
| Anthropic：Claude Code 团队代码审查（2026-10） | Claude 写了约 90% 的代码；PR 前先测试构建和端到端验证；多 Agent 独立找问题再验证；按风险分级审批；历史事故进入每日评测；限制审查轮数 | 审查不是最后一道关卡，而是开发中持续进行；结论必须有证据；Agent 审批不代替人的责任 |
| Anthropic：企业 SDLC 安全（2026-07） | Claude 写约 80% 的合并代码；交付代码量约增长 8 倍；有实质性审查意见的 PR 从 16% 升到 54% | 人工集中到高风险和关键决策上；见本指南第 8.4–8.8 节 |
| Anthropic：长程 Harness（2026）| 初始化 Agent、功能清单、进度文件、Git 历史；后续 Planner / Generator / Evaluator 三 Agent 架构 | 上下文交接和增量开发；独立评测；见第 12.7–12.11 节 |
| Uber：Software Factory（2026-08） | 超过 70% 的 PR 由 Agent 参与；内部 3,600 多个 Agent Skill；每天执行超过 30,000 次 | **把 Agent 能力沉淀为可复用、可评估的专业化 Skill**，不把所有能力塞进一个超级 Agent |
| OpenAI：Codex Auto-review（2026-04） | 越过沙箱边界的操作由另一个独立 Agent 判断是否批准；会话因人工审批暂停的次数约减少 200 倍，需审查的操作约 99% 获批 | 自主不等于无限权限：**把权限边界设计清楚，越界时由独立机制判断** |
| Cursor：长程自主编码（2026-01） | 数百个 Agent 并行，一周生成 100 万行以上代码；约三周的 Solid→React 迁移 | 平级 Agent 靠文件锁协调会失败；改为 Planner / Worker / Judge 分工 |
| Google：Jules | 代码仓库放进独立云 VM，Agent 后台执行，完成后提交变更 | 异步委托模式。**注意原文：Google 已宣布 Jules 将于 2026-12-31 停止服务，只作为工程模式参考** |
| Google：工程实践 | Code Review 长期强调设计、功能、复杂度、测试 | 原则未因 Agent 出现而失效，变化的是执行检查的主体和方式 |

**Anthropic 长程开发的八项实践（原文第 6918–7716 行，已在第 12.1–12.16 节展开）：**
1. 持续推进的开发循环，而非一次性大任务；
2. 持久化项目记忆，而非依赖对话上下文；
3. 每次只完成一个可验证的 Feature；
4. 独立 Evaluator，而非开发 Agent 自评；
5. Planner + Workers + Judge，而非平级大混战；
6. 每个 Agent 独立的开发环境；
7. 用故障恢复系统，而非无限重试；
8. Agent 自己建设和维护开发环境。

**原文第 5 轮的八条共同原则（直接可用）：**

| 原则 | 具体做法 |
|---|---|
| 1 先建设 Harness | 给 Agent 准备代码库知识、工具、测试、权限、反馈环境；先于追求更强模型 |
| 2 任务契约化 | 目标、边界、输入、输出、验收标准 |
| 3 执行与验证分离 | 开发 Agent 不应自己宣布任务成功 |
| 4 独立审查 | 审查 Agent 不继承开发 Agent 的全部上下文和结论 |
| 5 风险分级 | 自动通过、人工审批或双人审批按影响决定 |
| 6 历史问题变成评测 | 每次事故、回滚、漏检形成 Eval |
| 7 可恢复、可回滚 | 沙箱、快照、Feature Flag、回滚、数据恢复 |
| 8 度量真实结果 | 衡量交付质量、事故率、返工率、人工介入，而非代码量 |

**Builder / Verifier / Auditor 三种角色必须分开：**
- **Builder**：实现需求；
- **Verifier**：验证功能和验收条件；
- **Auditor**：审查风险、架构、安全和工程规范。
三者可以用不同模型，也可以用同一模型，但**必须有独立的任务上下文、独立的检查依据和不同的权限**。不能让 Builder 写完代码、自己跑一个测试、自己说通过，就算完成。

## 13. 落地行动计划

### 13.1 三类角色必须交付的东西

| 角色 | 必须交付 | 不能省略的动作 |
|---|---|---|
| 需求分析人员 | Requirement、验收场景、Feature Map | 确认范围和业务规则 |
| 开发人员 | Task Plan、代码 Diff、测试证据、PR | 独立审查、风险说明 |
| QA | 测试用例、回归测试、Eval | 独立复现、验证修复 |
| 技术负责人 / 架构负责人 | 架构地图、风险策略、代码所有权 | 高风险变更审批 |
| 运维 / DevOps | CI、监控、发布、回滚机制 | 确保生产环境安全 |

**技术负责人或架构负责人是原文新增的第四类角色**，负责架构设计原则、核心模块边界、高风险代码清单、技术债务、技术方案审批、围栏的最终执行监督。

**角色职责变化：**
- **需求分析人员**：从"需求转述"转向"定义正确性"，维护 Feature Map，判断 Agent 是否真正解决了用户问题，决定是否接受范围变化。
- **开发人员**：从"写代码"转向"确定方案、指导 Agent、审查 Agent 的工作、确保结果可验证、对变更负责"。
- **QA**：从"执行测试"转向"建立测试基线、自动化体系、Bug 复现机制、Eval 数据集，并评估 AI Reviewer 和测试 Agent 的可靠性"。

### 13.3 落地优先级

| 优先级 | 建设内容 | 原因 |
|---|---|---|
| **P0** | AGENTS.md、Feature Map、需求模板 | 先解决 Agent 不理解系统的问题 |

| **P0** | 小 PR、独立 AI 审查 | 控制变更风险 |
| P1 | 风险分级、人工审批 | 开始释放低风险任务的自主权 |
| P1 | Benny（Bug 调查） | 形成自动发现和修复闭环 |
| P1 | Eval 数据集 | 防止相同问题反复出现 |
| P2 | 自动灰度、自动回滚 | 逐步进入更高自主等级 |

**试点优先选 AgentNexus 的 Agent 执行稳定性**（见 9 节），而不是普通 UI 功能。这个试点能同时验证：需求定义、Agent 阅读架构、Rust 代码修改、独立审查、自动化测试、Bug 复现、风险审批。

### 13.4 三阶段路线

**第 1–2 周：建立基础围栏**
- 八份制度文件初版；
- 整理 Feature Map；
- 建立 AGENTS.md、REVIEW.md、TESTING.md；
- 统一 PR 模板；
- 核心模块回归测试基线；
- 所有 AI 开发必须通过 CI。
- **目标：先让 AI 开发过程可控、可追踪。**

**第 3–4 周：建立 AI 自动审查体系**
- Developer Agent 与 Reviewer Agent 分离；
- 引入 Benny；
- 引入独立测试 Agent；
- 建立风险分类器；
- 自动化测试和故障注入；
- 历史 Bug 转化为 Eval。
- **目标：让机器发现和拦截大部分常见问题。**

**第 2 个月：逐步开放 AI 自主权限**
- 低风险 PR 自动合并；
- 普通风险 PR 人工审批；
- 高风险 PR 强制双人审查；
- 灰度发布和自动回滚；
- 质量数据看板；
- 评估 AI 自主开发的真实效率。
- **目标：从 AI 辅助开发走向 AI 自主开发。**

### 13.5 四周长程自主开发实验

建议一个小型工程小组先验证机制，不追求大规模并发。

| 周次 | 交付 | 验收标准 |
|---|---|---|
| 第 1 周：长程运行时 | Project / Task / Session 数据模型；Task Scheduler；Execution Adapter；心跳和卡死检测；Checkpoint / Handoff | 一个任务能跨两个以上 Session 继续执行 |
| 第 2 周：自主开发闭环 | Initializer；Feature Map 生成；Planner；自主循环；Git Worktree | 给定一个完整需求，能自动拆解并完成至少 5 个连续 Feature |
| 第 3 周：独立验证与恢复 | Evaluator；自动化测试；证据收集；Benny；故障分类与恢复 | 人为注入测试失败、MCP 超时、Agent Hang，系统能识别并恢复 |
| 第 4 周：多 Agent 与长程 | 多 Worker；动态任务分配；任务租约；Judge；成本与质量报告 | 连续自主开发 8 小时以上，跨 Session，至少完成一个端到端功能模块 |

**Initializer（项目初始化阶段）**：第一个 Agent 不是 Coding Agent，而是 Initializer。它读取需求、建立项目结构、建立启动和测试脚本、生成 Feature List、建立进度文件、创建初始 Git Commit。之后的 Agent 才开始逐个实现功能。**不要让后续 Agent 每次重新摸索项目怎么运行、怎么测试、什么是完整功能。**

**项目启动规范：** 先完成需求分析和 Feature Map；生成任务图和验收条件；检查代码库能否正常运行；建立可重复的启动和测试脚本；记录初始 Git Commit。

**每次执行规范：**
- 每个 Worker 只负责一个明确任务，拥有独立 Workspace；
- 修改之前检查当前 Git 状态；
- 不能随意修改验收标准；
- 每完成一组修改，运行对应测试；
- 失败必须修复或记录明确的阻塞原因；
- 每次 Session 结束生成 Handoff。

**验收规范：**
- 不允许仅凭 Agent 自己的成功声明判定完成；
- 必须由独立 Evaluator 检查；
- 关键 Feature 必须通过真实操作验证；
- 每个 Bug 都要有复现证据；
- 每个修复都要有回归测试；
- 不能为了通过测试而删除或弱化原有测试。

**故障恢复规范：** 所有执行可观测；所有运行状态持久化；所有重试有次数限制；失败时先分类；恢复后对账代码和任务状态；无法恢复时自动升级给 Planner 或人工。

### 13.6 三个试点项目

| 试点 | 范围 | 目标 |
|---|---|---|
| **A：独立小型应用**（先做） | 从空仓库开始；10–20 个 Feature；前端、后端、数据库；端到端测试；连续执行 2–4 小时 | 验证 Planner、Feature List、Evaluator 和 Handoff |
| **B：AgentNexus 内部模块**（第二步） | 选一个相对独立的模块；20–50 个 Feature；使用现有 Rust 架构；OpenCode 作为主要 Worker；运行 4–8 小时 | 验证真实代码库中的自主开发与故障恢复 |
| **C：AgentNexus 多 Agent 自主开发**（第三步） | 多个 Worker 并行；动态 Planner；独立 Evaluator；自动处理 Bug；跨 Session 持续 24 小时以上 | 验证长程协作和持续开发 |

**B 优先选模块边界明确、已有测试环境、可以独立部署的功能**，不要一开始就挑战核心调度系统。

**自主等级目标：** 原文建议四级：A1 自主完成单个 Feature（人工分配、验收）；A2 自主完成多个连续 Feature（人定大目标、关键节点检查）；A3 自主推进整个项目（人负责架构、风险决策、最终验收）；A4 自主发现需求、规划、开发、发布和持续改进。**目前不应直接追求 A4。第一阶段目标是 A2：连续自主完成多个 Feature，工作 4–8 小时，中途不需要人工干预。**

### 13.7 评测指标

**不要用"AI 写了多少行代码"或"PR 数量"衡量。** 应考核：在不增加生产事故的前提下，每个人能够管理多少个自主工作的 Agent，以及这些 Agent 能独立交付多少经过验证的有效变更。

| 指标 | 定义 | 第一阶段试点目标（不是行业基准） |
|---|---|---|
| Autonomous Completion Rate | 无人工介入完成并通过验收的任务比例 | ≥ 70% |
| Task Success Rate | 所有任务最终通过验收的比例 | ≥ 85% |
| Context Continuity | 跨 Session 成功接续的比例 | ≥ 95% |
| Recovery Success Rate | 可恢复故障中成功恢复的比例 | ≥ 80% |
| Regression Pass Rate | 历史回归集通过率 | ≥ 98% |
| Agent Hang Rate | 执行中卡死的比例 | ≤ 2% |
| Human Intervention Rate | 需要人工介入的任务比例 | 持续下降 |
| Cost per Accepted Feature | 每个验收通过 Feature 的总成本 | 持续下降 |
| **Human Minutes per Accepted Feature** | 每个验收通过的功能，人实际花费的分钟数 | 持续下降 |

**分母要明确：** Autonomous Completion Rate 的分母是所有被分配的合格任务，而不是 Agent 自己挑出来的简单任务。

**其他常用指标（第 7 节、第 10.10 节）：** 执行正常退出率（≥ 99%）、需求验收通过率（≥ 95%）、自动测试有效通过率（≥ 98%）、夜间任务自动完成率（≥ 80%）、回滚率、首次验收通过率、回归缺陷率、生产事故。

**三条检查要求：**
- **Execution Success（进程正常退出）、Task Success（验收通过）、业务结果正确，三者不能混为一谈。**
- 不能只看测试通过率，要关注独立测试、需求场景覆盖，以及历史 Bug 能否被重新检出。
- 指标要**按任务类型分别统计**。文档修改和数据库并发修复不能混在一起算平均成功率。

### 13.8 晋级与人工退出规则

- **先证明质量没有退化，再扩大自主权限。** 例如某模块连续若干周满足验收通过率、回归率和故障恢复要求，才逐步放宽自动合并权限。具体门槛用自己的基线数据确定，不照搬大厂数字。
- **按数据推进，不按日历推进。** 不要因为某个月成功率高就撤掉人工，需要在足够多、足够多样的任务上积累证据。
- **人工退出的顺序：** 连续多个版本稳定通过后，逐步减少普通任务的资深开发审查；低风险任务自动合并到候选分支；中风险抽样审查、异常升级；高风险保留人工批准。
- **Eval 作为放行依据：** 每次修改后比较修改前后的整体质量。例如新功能通过率从 90% 升到 96%，但历史 Bug 回归率从 98% 降到 93%，这次修改就**不能判定为整体进步**。

### 13.9 必须避免的做法

| 做法 | 为什么错 |
|---|---|
| 把 Agent 每次修改都做成人工审批 | 人成为瓶颈，围栏设计失败 |
| 一次让 Agent 完成整个大项目 | 长程任务不可控，上下文偏离目标 |
| 把"进程退出"当作"任务完成" | 没有业务验收证据 |
| 同一个 Agent 写代码、测试、宣布通过 | 自我证明，共同盲区 |
| 测试失败后删除或弱化测试 | 用规避代替修复 |
| 失败后原样重跑相同 Prompt | 没有根因分析，只会重复失败 |
| 无限重试 | 放大负载，掩盖问题 |
| 用加权平均掩盖严重缺陷 | 安全失败也能"通过" |
| 把 AGENTS.md 当安全边界 | 指导不是强制，必须有权限和 CI |
| 用 Agent 能力替代组织责任 | 高风险决策的责任仍属于组织 |
| 团队一夜之间全面切换 | 基础设施未成熟，失败无法定位 |

### A.1 需求文件模板（第一层）

路径：`requirements/<需求编号>.md`，例如 `requirements/ANX-EXEC-001.md`。

```markdown
# ANX-EXEC-001：Agent 执行超时处理

## 1. 业务目标
Agent 执行超过允许时间后，系统必须能够结束任务、释放资源，并向用户返回明确的超时状态。

## 2. 本次范围
- Agent 执行超时检测
- 任务状态更新
- Agent 进程终止
- MCP 调用取消
- 资源释放
- 超时事件记录

## 3. 非目标
- 不修改现有 Agent 调度策略
- 不修改 Session 的数据模型
- 不修改正常任务的执行流程
- 不自动重试超时任务

## 4. 业务规则
R1：每个任务必须有独立的超时配置。
R2：超时后，任务状态必须进入 TIMEOUT。
R3：任务进入 TIMEOUT 后，不得再进入 COMPLETED。
R4：超时后必须尝试终止对应 Agent 进程。
R5：必须取消尚未完成的工具调用。
R6：必须记录超时时间、任务 ID 和原因。
R7：进程终止失败时，必须产生告警。

## 5. 验收场景
### AC-01 正常超时
Given：任务超时时间为 300 秒 / When：执行超过 300 秒 / Then：状态变成 TIMEOUT

### AC-02 正常完成
Given：超时时间 300 秒 / When：300 秒内正常完成 / Then：状态变成 COMPLETED

### AC-03 进程无法终止
Given：任务已经 TIMEOUT / When：Agent 进程无法正常终止 / Then：产生告警，不得将任务标记为已清理

### AC-04 迟到的成功响应
Given：任务已经 TIMEOUT / When：Agent 随后返回成功响应 / Then：不得将 TIMEOUT 改回 COMPLETED

## 6. 验收责任
业务验收：产品人员 / 技术验收：开发负责人 / 自动化验收：QA
```

| 涉及 3 个以上核心模块 | 必须技术负责人确认 |

**脚本** `tools/check_change_size.py`（第一版）：

```python
#!/usr/bin/env python3
import subprocess
import sys

MAX_LINES = 500
MAX_FILES = 8

def run(cmd):
    return subprocess.check_output(cmd, text=True).strip()

def main():
    try:
        diff = run(["git", "diff", "--cached", "--numstat"])
    except subprocess.CalledProcessError:
        print("ERROR: Cannot inspect staged changes")
        sys.exit(1)

    total = 0
    files = 0
    for line in diff.splitlines():
        parts = line.split("\t")
        if len(parts) != 3:
            continue
        added, deleted, filename = parts
        # 二进制或生成文件单独处理
        if added == "-" or deleted == "-":
            continue
        total += int(added) + int(deleted)
        files += 1

    print(f"Changed files: {files}")
    print(f"Changed lines: {total}")

    if total > MAX_LINES:
        print("BLOCKED: Change is too large.")
        print("Split the task into smaller changes.")
        sys.exit(1)
    if files > MAX_FILES:
        print("WARNING: Too many files changed.")
        print("Please explain the change scope.")
    print("Change size check passed.")

if __name__ == "__main__":
    main()
```

本地 Hook（`.pre-commit-config.yaml`）：


### A.8 状态机（第四层）

核心业务规则要写进程序，不能只写在文字里。示例（Rust）：

```rust
#[derive(Debug, Clone, PartialEq)]
enum TaskState {
    Pending,
    Running,
    Completed,
    Failed,
    Timeout,
    Cancelled,
}

impl TaskState {
    fn can_transition_to(&self, next: &TaskState) -> bool {
        use TaskState::*;
        matches!(
            (self, next),
            (Pending, Running)
            | (Pending, Cancelled)
            | (Running, Completed)
            | (Running, Failed)
            | (Running, Timeout)
            | (Running, Cancelled)
        )
    }

    fn transition(&self, next: TaskState) -> Result<TaskState, String> {
        if self.can_transition_to(&next) {
            Ok(next)
        } else {
            Err(format!("Invalid transition: {:?} -> {:?}", self, next))
        }
    }
}

#[cfg(test)]
mod tests {
    use super::*;

    #[test]
    fn timeout_cannot_become_completed() {
        assert!(TaskState::Timeout.transition(TaskState::Completed).is_err());
    }

    #[test]
    fn running_can_become_timeout() {
        assert_eq!(TaskState::Running.transition(TaskState::Timeout).unwrap(), TaskState::Timeout);
    }

    #[test]
    fn completed_cannot_become_timeout() {
        assert!(TaskState::Completed.transition(TaskState::Timeout).is_err());
    }
}
```

**关键点：**
- 内存中的检查不够。数据库更新必须是**条件更新**，防止并发竞争：

```sql
UPDATE tasks
SET state = 'COMPLETED', version = version + 1
WHERE id = $1 AND state = 'RUNNING' AND version = $2;
```

  影响行数为 0 时，说明状态已被其他流程改变，**不能强行覆盖**。
- 这些测试应当成为**不可随意删除的回归测试**。

**与本项目的对应**：我们当前的 `TaskStatus`（`crates/core/src/lib.rs`）有 CREATED、QUEUED、RUNNING、VERIFYING、COMPLETED、FAILED、NEEDS_HUMAN、CANCELLED，**没有 TIMEOUT**。若采用超时状态，需要在状态机中新增，并同步更新数据库和前端。

**风险分类脚本**（第一版，`tools/classify_risk.py`）：

```python
import subprocess
import fnmatch
import yaml
import json

with open("config/risk-policy.yaml") as f:
    policy = yaml.safe_load(f)

changed = subprocess.check_output(
    ["git", "diff", "--name-only", "origin/main...HEAD"], text=True
).splitlines()

risk_order = {"L0": 0, "L1": 1, "L2": 2, "L3": 3}
highest = "L0"
matched = []

for path in changed:
    for level, rule in policy["risk_rules"].items():
        for pattern in rule["paths"]:
            if fnmatch.fnmatch(path, pattern):
                matched.append({"file": path, "risk": level})
                if risk_order[level] > risk_order[highest]:
                    highest = level

if not matched:
    highest = policy["default"]["risk"]

result = {
    "risk": highest,
    "changed_files": changed,
    "matched_rules": matched,
    "human_approvals": policy["risk_rules"].get(highest, policy["default"])["approval"]["human"],
}
print(json.dumps(result, indent=2))
# 这只是初步分类器。最终审批由受保护的仓库规则强制执行。
```

**已知缺陷（使用前必须修正）：**
1. **未匹配的文件被忽略。** 只要有一个文件命中规则，其余未命中的文件就不计入风险。应当把未命中的文件按 `default` 风险处理。
2. `fnmatch` 对 `**` 的语义与 gitignore 风格不同，需要用专门的匹配库或测试用例验证。
3. 脚本的结果只能作为第一道分类器，还要叠加第二层判断（见下）。

**第二层判断**（交给独立的 Risk Agent，或人工）：是否修改公共 API；是否改变数据库结构；是否涉及认证授权；是否改变并发或异步行为；是否删除了原有测试；是否影响多个模块。**两者不一致时，采用较高风险。**

**审批与自动合并的关系：**

| 风险 | 满足条件 |
|---|---|
| L0 | CI 通过 + 审查通过 → 可自动合并 |
| L1 | CI + 审查 + 1 名人工批准 → 合并 |
| L2 | CI + 审查 + 模块负责人批准 + QA 通过 → 合并 |
| L3 | CI + 安全审查 + 2 名人工批准 → 合并；**发布仍需独立授权** |

**硬性规则：开发 Agent 的发起人不能算作独立审批人，Reviewer Agent 也不能替代人工审批。**

### A.16 任务契约示例：取消机制（第 11.3 节第 1 点）

原文的传统写法是一句话："用户取消运行中的任务后，系统应停止当前任务，并释放相关资源。" 对人可以理解，但 Agent 会漏掉大量隐含要求（只改数据库状态而不终止进程、未处理迟到响应、取消与完成同时发生的竞争）。转换后的契约：

```markdown
# Task Contract：任务取消机制

## 目标
用户取消运行中的任务后，系统必须停止该任务的后续执行，释放执行资源，并保证终态不被迟到响应覆盖。

## 前置条件
- 任务状态为 RUNNING 或 WAITING
- 任务有唯一 execution_id
- 执行引擎能定位对应的 Agent 进程和子进程

## 业务规则
1. 只有 RUNNING、WAITING 状态允许取消。
2. 取消操作必须幂等。
3. 取消后不得再调度新的子任务。
4. 已启动的子进程必须进入终止或受控清理流程。
5. 迟到的 Agent / MCP 响应不得覆盖 CANCELLED。
6. 取消必须记录操作者、时间、原因和 execution_id。

## 验收场景
| 场景 | 预期结果 |
|---|---|
| 正常取消 | 任务进入 CANCELLED |
| 重复取消 | 不产生额外副作用 |
| 取消时 Agent 正在执行 | Agent 被终止 |
| 取消后 MCP 迟到返回 | 状态不被覆盖 |
| 取消与完成同时发生 | 按明确的状态转换规则处理 |
| 服务重启后恢复 | 取消状态保持 |

## 禁止事项
- 不得只修改数据库状态而不处理实际执行进程。
- 不得直接删除执行记录。
- 不得把取消当作普通失败。
- 没有清理证据时，不得报告资源已释放。

## 交付证据
代码变更记录、状态机测试结果、进程终止测试结果、并发竞争测试结果、资源清理日志。
```

同一份需求的 YAML 结构（适合机器读取）：


**状态机与副作用：**

```yaml
state_machine:
  terminal_states: [COMPLETED, FAILED, CANCELLED, TIMEOUT]
  transitions:
    - {from: QUEUED,  to: RUNNING,   event: START}
    - {from: RUNNING, to: COMPLETED, event: RESULT_RECEIVED}
    - {from: RUNNING, to: FAILED,    event: EXECUTION_ERROR}
    - {from: RUNNING, to: TIMEOUT,   event: DEADLINE_EXCEEDED}
    - {from: RUNNING, to: CANCELLED, event: USER_CANCEL}
  invariants:
    - terminal_states_are_immutable
    - only_one_terminal_transition_is_allowed
    - every_execution_has_unique_id
```

| 事件 | 状态变化 | 必须执行的动作 |
|---|---|---|
| START | QUEUED → RUNNING | 创建执行实例、启动 Agent |
| RESULT_RECEIVED | RUNNING → COMPLETED | 保存结果、清理进程 |
| DEADLINE_EXCEEDED | RUNNING → TIMEOUT | 取消执行、清理资源 |
| USER_CANCEL | RUNNING → CANCELLED | 停止子任务、清理资源 |

**字段的业务语义（注意状态分层）：**

```yaml
field:
  name: status
  type: enum
  values: [QUEUED, RUNNING, COMPLETED, FAILED, CANCELLED, TIMEOUT]
  mutable_by: [task_state_machine]
  constraints: [terminal_state_is_immutable]
  meaning: >
    表示一次任务执行的当前生命周期状态。
    不代表整个业务需求是否验收通过。
```

> 对照本项目：`crates/core/src/lib.rs` 的 `TaskStatus` 与这里的枚举不同（我们没有 TIMEOUT，且有 NEEDS_HUMAN 和 VERIFYING）。落地前应以代码为准，对齐状态定义后再写契约。

### A.24 故障分类与恢复动作（第 12.13 节）

| 故障类型 | 识别信号 | 恢复动作 | 次数限制 |
|---|---|---|---|
| Transient | 网络波动、临时 502 | 指数退避 + 随机抖动重试 | 按工具设定 |
| Tool Failure | MCP 调用失败或超时 | 工具级重试，必要时切换工具 | 按工具设定 |
| Agent Hang | Process Heartbeat 正常，但 Agent Activity 或 Task Progress 长时间无变化 | 检查进程；确认停滞后终止并从检查点恢复 | 单次任务最多自动恢复 2 次 |
| Context Failure | 上下文溢出、偏离目标 | 新 Session + Handoff + State Reconciliation | 2 次 |
| Code Failure | 构建或测试失败 | 生成修复任务，由 Worker 修复 | 按 Feature 限制修复轮数 |
| Planning Failure | 同一任务反复尝试无法推进 | Planner 重新拆解，或升级模型 | 连续恢复失败即升级 |

**阈值（试点初始值）：** Process Heartbeat 15 秒；Agent Activity Warning 120 秒；Task Progress Warning 5 分钟；无进展诊断 10 分钟。

**不能误杀的情况：** 长时间编译、测试、索引等工具可能没有实时输出。判断依据应来自执行层记录的工具调用状态、进程活动、心跳和进展，而不是只看文本输出。

**恢复原则：** 失败后不要原样重跑相同的 Prompt。流程为：识别类型 → 提取错误日志和执行轨迹 → 判断是否可重试 → 选择恢复动作 → 恢复到最近可靠检查点 → 继续执行。
