## 推荐实施范围与做法

1. 在高风险 `crates/runtime/src/store.rs` 的既有 cfg(test) 模块内**仅新增测试函数**，不改旧断言、不改生产函数、表结构或接口。直接调用私有 write_events，确保用例确实是同一批、同一事务，不为测试新增公开 API。
2. 先在独立临时 SQLite 连接中预存 event-duplicate，再一次调用 write_events 写入 `[重复 ID, 真实会话事件 A, 真实会话事件 B]`。核对真实事件恰好两条、内容/会话归属完整、原重复 ID 只有一条且原内容不变。重复位置至少覆盖首/中/尾，并覆盖同批内部重复，避免只锁住某个顺序。
3. 再补一条公有 Store enqueue/flush 集成对照，核对 flush 后两条真实事件可读、无跨会话混入。异步队列可能拆批，因此该层不是撤销检查的唯一证据；核心反例由第 2 步确定性锁住。测试使用现有测试库/辅助函数，不更改批量大小或生产等待策略。
4. 获准后先做**根因撤销检查**：只在本次独立验证工作区将 INSERT OR IGNORE 临时恢复为旧 INSERT，保持新测试不变，得到实际业务断言失败（真实事件未完整落库或业务写入失败）；恢复既有去重后同一测试通过。保存两次命令/退出码；临时撤销不得进入最终提交。
5. 同步 CASES/features/功能地图与独立证据。修复 PR 只有新增测试和相关文档，不改夹具编号/配置或顺带修日志 code；原 R-20261125-L3 单独处理。记录关联 #286 及新测试 PR，由评审复核后决定关闭；fixer 只在总结追加合规 fix_claimed，不写 verified_fixed。

备选：只通过两次 fixture seed 或大量 enqueue 碰运气制造重复，可能因编号已经随机化、写线程拆批而测不到原回滚，不推荐。禁止借延迟、全套件单线程或重试业务断言让撤销检查通过。

## 验收（Given / When / Then）

- Given 已存重复 ID，When 同批混入两条合法事件，Then 原重复记录不覆盖，两条合法记录都入库且可按会话读取。
- Given 仅撤掉 store 去重，When 运行同一新增测试，Then 业务断言失败；恢复去重后通过，测试字节一致。
- Given 无重复与同批内部重复两个对照，When 写入/flush，Then 合法事件都在，同 ID 不重复，既有 RT-FIXC、事件保留窗口/重放测试不变并通过。
