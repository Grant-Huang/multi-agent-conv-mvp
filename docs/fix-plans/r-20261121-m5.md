## 问题与依据

[日报 M5](../review/2026-11-21.md)：同一个 client_operation_id 在 A 会话受理后，B 会话同正文仍得到 Replay，返回的 conversation_id/scope/task_id 还来自新请求，B 实际没有消息。当前 `runtime/src/store.rs::accept_desktop_request` 仍只比较 committed == text。

权威设计是 [AI Desktop DESIGN §5](../ai-desktop/DESIGN.md)：同操作不同输入 409；[历史决定 66](../DECISIONS.md) 冻结同键重放、用户消息同事务；[事件契约](../contracts/events-and-trace.md) E3 要求权威数据先提交。方案补全现有输入一致性，不改变产品需求或权限模型。

## 推荐方案与文件范围

1. 高风险 `store.rs` 查询既有操作的全部字段，将 `(conversation_id, text, scope, task_id)` 与本次服务端实际接受的值完整比较；不同则 Conflict。正文沿用已有 trim，scope/可选 ID 不新增隐式归一化；默认值仍在 HTTP 解析层应用。后续若加入附件等语义字段，也须列入不可变载荷比较，不只比较散列而忽略规范化规则。
2. Replay 始终用数据库中的 request_id/message_id/归属字段/状态/计数构造，不把本次请求内容拼进已有记录。比较与返回在同一事务快照内；不一致不新增消息、不 spawn、不移动已有任务归属。
3. `server/src/desktop_api.rs` 保留 409 operation_conflict，提示改为不同请求载荷，不能继续只说不同正文；不在错误中泄露原会话正文。后续真实租户/用户来自服务端身份解析，不接受客户端自报身份；本轮保持现有唯一键，**不自行迁移为新鉴权/租户作用域**。
4. 新增 Store 与 HTTP 参数化回归，更新 CASES/受理证据；不修改旧测试。与 M2 实施串行协调同一 accept 方法，M5 可先作为小范围独立修复，不捆绑队列迁移。

备选：把唯一键改成 conversation_id + client_operation_id 会让跨会话复用键创建第二条请求，违背本条“输入不一致 409”的验收，且掩盖错误归属；不推荐。未来按真实身份升级键作用域须另批兼容迁移。

## 验收（Given / When / Then）

- Given A/op-1 已受理，When B/op-1 同正文，Then 409，B 消息数为 0，A 的请求/消息/任务关联和 dispatch_count 不变。
- Given 原请求，When 单独修改 scope、task_id（含 None ↔ Some）、正文任一字段，Then 分别 409；输入全同则重放原 request/message ID 及数据库字段。
- Given 两个并发同键不同载荷，When 同时受理，Then 仅一个 Created、另一个 Conflict，数据库只有一条操作与一条用户消息；全同并发则一个 Created、其余 Replay。
- Given 重启后同库重放，Then 返回原库记录，不重复分流；既有 RT-ADACCEPT-01～04 的断言不变。
