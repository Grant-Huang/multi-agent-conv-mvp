# R-20261119-H2：凭证键识别必须保持线性（待批准）

风险：拟实施L2，当前仅L0方案；助手建议，未获本项具体批准。

## 问题与边界

台账P1仍open。`recognizers.py`中_KEY_PREFIX/_KEY_SUFFIX的重复与无下划线边界的起点搜索结合，使无凭证的长标识符链被反复扫描。报告中12,000字符约3.42秒，长度三倍耗时约九倍；这会占住DLP服务，连正常外发判定也超时。

按AGENTS/PREFLIGHT新增的L2事前方案批准要求，本轮不改正则或既有测试，只提供实施范围。不能用输入截断、关闭检查或异步超时包装同步正则来声称问题已解决。

## 推荐方案

1. 将“任意前后缀＋凭证词＋赋值＋值”的一个回溯表达式拆成单次词法扫描与有界键分类：先定位赋值分隔符及键/引号/值的范围，再对完整键的标识符段作有限集合判断。
2. 标识符、分隔符、空白、引号及值区间只扫描/缓存一次；重叠候选共享已计算的区间边界。特别防止`token_a_...`包含多个强词时，后缀仍被重复扫描，或`password=password=...`让值扫描重新变成二次方。
3. 强键与弱键的既有语义保持：弱key/auth仍要求值含字母和数字；中文键、Authorization、提供方格式和原文span映射保持。正则可继续用于有明确边界的简单局部匹配，不能让引擎在长token的每个下划线重新起步。
4. 与H1共享键分类器时保持两条独立验收。凭证值的完整span必须继续遮盖，不通过缩短匹配或丢弃长键的尾部换速度。
5. 保留现有256KB载荷上限。可在安全阶段边界记录耗时并在超预算时BLOCK，但它只约束已返回的阶段，不能宣称能中断持GIL的同步代码。若需要可强制中止的整请求硬期限，应另立进程隔离方案，不在本次偷偷新增服务架构/公开配置。
