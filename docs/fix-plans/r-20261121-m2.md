## 问题与设计依据

[最新日报 M2](../review/2026-11-21.md) 指出受理提交与后台 spawn 之间可中断，分流失败只 warn。同键重试走 Replay，GET 永久 accepted。当前 `server/src/desktop_api.rs::create_request`、`runtime/src/store.rs::accept_desktop_request/get_desktop_request` 仍是这一实现。

权威设计：[AI Desktop DESIGN §5](../ai-desktop/DESIGN.md#5-扩展协议与数据模型) 规定消息、操作、待派发项同事务，分流完成更新关联；[状态契约](../contracts/state-and-cancellation.md) S1/S4/S6、[事件契约](../contracts/events-and-trace.md) E3/R1 要求终态守卫、先持久化后发布、未知副作用不盲重发。服务宪章 §5 的可追查与明确报错，不新开产品主线。

## 推荐方案

1. **事务受理**：在高风险 `store.rs` 中将用户消息、操作记录及待派发记录在同一事务提交；HTTP 202 只表示持久受理。新增队列表或兼容补列须带幂等迁移，保留已有 request_id/message_id/client_operation_id。
2. **可仲裁领取**：新增私有 worker，以 request_id 唯一键和 owner/代次、有限 lease 做条件领取；手动请求、重复 POST、启动恢复都只能唤醒同一条队列。SQLite 锁内领取后释放再 await。沿用已有模型超时，加明确的队列取消和退出清理；不启动不可追踪的裸 spawn。
3. **分流结果回写**：accepted → dispatching → dispatched 或 dispatch_failed，失败带结构化 code/retryable 与 request_id，成功回写真实关联。这里 dispatched 仅表示分流已落实，不等于任务执行成功；前台直接回答也要记完成分流。条件更新阻止旧 worker 覆盖新代次或终态。公开状态/错误字段先作为本方案的一部分审批，不暗改 DTO。
4. **重启与副作用边界**：未领取 pending 可安全重领。已领取记录不能仅因 lease 到期就再次调用非幂等 `continue_after_accepted`：该方法可能已创建任务/写回复。应将 request_id 贯穿分流幂等检查点和下游持久化，在同一仲裁事务记录“已创建任务/已写回复”与关联。无法原子化的窗口明确标为待核对，不承诺“恰好一次”；这类在途恢复需要独立高风险接口方案，不得盲目重派。旧 accepted 无检查点记录也不能全部当成未执行。
5. **兼容与协同**：保留 `dispatch_count` 当前“首次受理为 1、重放不增加”的契约，领取尝试数另记内部字段；同键重试返回真实已提交记录，不重复插 user 消息。与第 1/4 线首页可靠受理工作协调唯一实施负责人，不能平行各建一套队列。范围为 store、conversation 私有接线、Runtime 启停及 desktop_api；若必须改 orchestrator，另列具体范围再批。

备选：只在错误时把 accepted 改为 failed，能改善可见性，但提交后 spawn 前崩溃仍丢任务，不作为完整修复。仅有 outbox 也只能保证可重领，不能保证下游任务只创建一次。

## 已有验收冲突

`server/tests/desktop_accept.rs::rt_adaccept_04_get_request_after_dropped_receipt` 用不可达模型，并断言立即 GET 的 status 必为 accepted。可靠失败回写可能先于 GET，保留该时序假设会变成竞态。不得加人为延迟、关 worker 或弱化断言。推荐负责人先明确测试应验证的稳定约定（202 已受理、ID 稳定、随后可观测真实终态），由有权限的人处理既有验收冲突；修复 agent 不修改已有断言。冲突解决前本方案不进入实施。

## 验收：先业务 Red，再冻结断言 Green

- Given 不可达模型，When 202 后有限时间内回读，Then dispatch_failed 含错误与原 request/message ID，而非永久 accepted；重复 POST 不重复插消息。
- Given 消息/操作/待派发项同库提交后、worker 领取前进程被终止，When 同库重启，Then pending 被领取一次，只有一条用户消息和一个逻辑分流结果。
- Given 任务已建但回执未记的崩溃窗口，When 恢复，Then 查证原关联后复用；无法查证则待核对，不能重复执行。新旧 worker 屏障交错，迟到写不覆盖终态。
- Given 多次启动和迁移，Then 老消息、已终态操作不丢失；既有 RT-ADACCEPT 正例保持业务约定，相关首页丢回执与重启集成回归通过。

批准后登记新增 CASES/features/证据，更新受影响的权威设计与 DTO，并跑全部 preflight；子进程测试 kill/wait 自己启动的服务。
