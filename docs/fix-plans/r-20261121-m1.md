## 问题与已有约束

`crates/runtime/src/agent_chat.rs::detect_mgmt_action` 将泛化的接入/停用/撤销识别成助手管理；Router route 与 Conversation 都调用 mgmt_hint，导致“给订单服务接入支付宝支付”“撤销刚才对 README 的修改”“停用旧的登录接口”不进入正常任务判断。agent_management 关闭时直接给管理提示，开启时可能覆盖模型的 delegate。

现有 `runtime/tests/agmgmt_route.rs::rt_agmgmt_01_rejects_agent_management_goals` 明确要求 Router 拦截“管理助手”“查看并修改 agent 配置”“读 config.toml 把 Cursor 接进来”“接入一个写代码的助手”。`agent_chat.rs` 的 RT-AGCHAT-12 还要求“把 zcode 停掉”等正例。直接删除 Router 拦截与冻结的正向验收冲突，因此推荐保留明确管理入口，收紧共享判定；不修改旧断言。

## 推荐改动

1. 在 `agent_chat.rs` 收紧共享 mgmt_hint/detect_mgmt_action：管理动作须有明确的本系统助手/agent/执行者或受支持产品对象及管理关系。泛化动词、刚才、修改等不能单独作为对象证据；README、业务服务、登录接口等普通对象进入正常理解。产品名按词/边界识别，不能把任意包含 pi 等短串的业务文本误认为产品对象。
2. 保留已冻结的管理配置、接入、停用、默认执行者、使用方法等正例及既有“用 Cursor 改代码”等工作请求排除。描述中提到助手但实际管理业务对象也不能一律拦截；新增组合负例。无法确定是系统管理的请求进入正常前台理解，不自动做管理写操作。
3. Router 和 Conversation 复用这一收紧后的纯判定，核对 Conversation 的两处管理分支，避免一处继续保留泛化捷径。保持 agent_management 开关原语义：明确管理请求关闭时引导、开启时进入确认流程；普通任务两种开关状态都不被强制改成管理。不能因收紧识别削弱管理写操作的确认/授权。
4. 文件范围 `agent_chat.rs`，必要时适配 `conversation.rs` / `router.rs` 的共享调用；新增测试及 CASES/功能地图，获准后记录与旧正例一致的产品决策。不增加模型调用、外部请求、公开配置或接口，不改 orchestrator/store/registry。

备选：移除 Router 的管理拦截，只在 Conversation 处理。结构更单一，但现有 RT-AGMGMT-01 约定与直接 Router 调用保护需要负责人先重新定验收；修复 agent 不可为此改旧测试。若选择此项，需要另行批准验收和权限边界，不能直接实施。
