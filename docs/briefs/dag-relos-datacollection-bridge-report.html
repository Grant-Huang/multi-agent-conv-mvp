Architecture Brief · 2026-11-06

可沉淀 DAG：把 AgentNexus、RelOS 与 data-collection 打通

本报告回答一个架构问题：AgentNexus 里的执行图（DAG / 模板）是否应完全写死在代码中？ 结论是不应写死实现，也不应让模型运行时现场编图；正确路径是把 data-collection 采集的工序草稿，经 RelOS 关系图谱沉淀与审核，晋升为 AgentNexus 可执行模板，由最前 Router 做封闭选择。

范围 AgentNexus MVP · RelOS · data-collection 对齐 DESIGN.md §9.5 / §9.6 性质 架构建议（尚未改代码）

1. 结论摘要

一句话：DAG 应从 RelOS 关系与 data-collection 工序里沉淀并晋升，不是运行时编造；AgentNexus 最前面的小 Router 只负责选择已晋升的图。

  • 不要把每一种业务流水线永久硬编码在 Rust 分支里（如长期靠 report.rs 特例扩容）。
  • 不要让对话模型在运行时发明依赖边——与 DESIGN 9.6「模型不现场编图」冲突，也难评测。
  • 要建立「草稿图 → 关系约束 → 可执行模板」三态，并以人审 / 置信度门槛控制晋升。
  • 要用统一执行引擎消费模板 JSON；新图来自晋升，而不是改编排核心。

2. 问题背景

2.1 当前现状

AgentNexus 已具备两条相关路径：

  1. 研究报告固定流水线（§9.5）：当路由同时要求 web_search 与 write_file 时，走代码控制的 规划 → 检索 → 并行写章 → 汇合；章节信封对齐 9.6 字段，但暂不接入编排器模板拆分。
  2. M4.3 模板拆分（§9.6）：设计已写入，校验层部分落地；编排器接入与 Composer 汇合仍是里程碑事项。 原则是「能串行的不拆；只有写死的模板才并行；Router 只输出 template_id / deliverable / slots_ok」。

2.2 张力

若业务图继续靠人在代码里写死，AgentNexus 会变成「报告工厂 + 少数工业模板」； 而 data-collection 已经在采集制造专家真实工作流 DAG，RelOS 已经把关系当作第一公民。 三者若不打通，L3 调度层会缺少可持续增长的工序知识来源。

关键约束：「可沉淀」≠「运行时自由生成」。可沉淀解决的是模板从哪里来；运行时仍然只执行已注册、已校验的图。

3. 三层职责

RelOS 仓库已明确 Nexus AI Platform 的分层定位，本报告在其上补齐「DAG 如何流动」：

L3 · 意识 / 调度

AgentNexus

自然语言入口、Router 选图、按模板执行、信封校验、汇合与交付。不负责发明工序知识。

L2 · 关系记忆

RelOS

实体与关系可计算；置信度、审核、演化。回答「什么能连、凭什么信、能否自动化」。

L1 · 感知 / 采集

data-collection（及 Ops）

专家会话采集真实工作流 DAG / 本体标注；执行层做动作。提供草稿图与证据，不直接驱动生产调度。

3.1 各层产出物

层主要产出对 DAG 的作用
data-collection Graph Workflow Dataset、制造运营本体字段、会话证据 产生草稿 DAG（人怎么做事）
RelOS 关系边、置信度、pending_review / active、反馈强化 给边与节点加关系约束与可信度
AgentNexus template_id、能力卡片、分支信封、执行轨迹 只消费已晋升可执行模板

4. DAG 三态生命周期

形态谁产生可否改线上执行成功标准
草稿图 Draft data-collection 专家会话整理 否，只进数据集 / RelOS pending 结构合法、有证据、可回放会话
关系约束 Constrained 挂到 RelOS 图谱，经置信度与人审 否，仍不可被 Router 选中 边类型合法、置信度门槛、无冲突环（业务环另议）
可执行模板 Executable 晋升注册到 AgentNexus 模板库 是，经加载校验后可上线 无环、能力存在、槽位够、信封字段齐、评测通过
Draft采集工序 DAG
→
ConstrainedRelOS 审核强化
→
Executable模板校验注册
→
RunRouter 封闭选择

运行日志与失败模式可回流 RelOS（哪些边经常 missing、哪些并行组合浪费槽位），形成强化信号； 但回流不得自动改写线上模板，必须再走晋升门槛——与 9.6「人不确认就不改线上模板」一致。

5. 数据飞轮与晋升契约

5.1 飞轮示意

data-collection
  专家会话 → 工作流 DAG 草稿 (+ 本体：角色/证据/异常/升级)
        │
        ▼
RelOS
  挂接实体与关系 · 置信度 · pending_review → active
        │  仅 active 且声明可执行
        ▼
AgentNexus 模板库
  template_id + capability + serial_steps + output_required + join
        │
        ▼
最前 Router（小决策模型）
  { template_id, deliverable, slots_ok } 封闭选择
        │
        ▼
固定边执行 → 信封汇合 → Composer 转述
        │
        └── 轨迹 / missing 回流 RelOS（待审强化，不自动上线）

5.2 晋升契约（建议最小字段）

从 RelOS / 采集侧导出到 AgentNexus 时，至少对齐下列映射：

源侧概念目标（AgentNexus 模板）规则
workflow_id / 版本 id（template_id） 稳定 ID；晋升时钉版本，不静默覆盖
交付物 / 业务结果名 deliverable 与 Router 输出必须一致
可并行工序簇 branches[] 互不等待才成分支；否则进 serial_steps
单路内部步骤 serial_steps 留给该路 agent，不拆成图上隐藏依赖边
角色 / 技能需求 capability 必须命中已注册能力卡片
产出字段 / 证据槽 output_required + 信封 payload 缺一路记 missing，禁止他路填补
RelOS confidence / status 晋升门槛元数据 例如仅 active 且置信度 ≥ 阈值才可注册

5.3 接口形态（概念）

POST /templates/promote
{
  "source": "relos",
  "relation_subgraph_id": "...",
  "workflow_draft_id": "...",
  "proposed_template": { /* 9.6 模板 JSON */ },
  "evidence": { "confidence_min": 0.75, "reviewers": ["..."] }
}
→ 校验：无环 / capability / slots / 字段闭合
→ 结果：rejected | pending_human | registered(template_id, version)

6. 与 DESIGN 9.6 的对齐

9.6 既有原则本方案如何遵守
模型不现场编图 Router 仍只做封闭选择题；图来自已注册模板
图是人手写的模板 扩展为「人手写 或 经人审晋升的沉淀模板」，权威仍是注册表
吃不准就不拆 template_id="" / slots_ok=no 整单退回单 agent
能力卡片只声明节点能力，不声明边 边只存在于模板；RelOS 关系用于晋升决策，不直接当运行时边源
信封缺一路记 missing，不用他路填补 晋升出的模板必须声明 output_required；执行规则不变
人不确认就不改线上模板 飞轮回流只进评测草稿 / RelOS pending，晋升需显式确认

因此，「从 RelOS 沉淀」改变的是模板供给链，不是推翻 9.6 的运行时安全边界。 第一批仍可用手工模板（quote / stop_line / release）验证 Router 准确度；沉淀通道随后接入。

7. 研究报告流水线的位置

当前 report.rs 是产品打通用的手写晋升特例：固定四阶段、内部并行、信封语义对齐 9.6， 但尚未进入编排器模板库。它证明了「代码控制固定流程 + 小模型写内容」可行。

  • 短期：保留 report 特例，继续补长度预算、检索上限等交付质量。
  • 中期：把报告流水线表达为第一张可执行模板（或「单能力内固定 serial/parallel 子图」），减少特例代码。
  • 长期：工业模板（报价、停线、放行、排故）优先走 data-collection → RelOS → 晋升；报告类可继续以产品内置模板为主。

区分很重要：检索材料可以长，最终正文贴近目标字数（如约 4000 字）是交付层预算问题； 这与 DAG 供给链正交，但同属「固定流水线可控」的收益。

8. 推荐落地阶段

P0

契约与样例（不改运行时核心）

定义 Draft → RelOS → Template 字段映射表；用 1 条制造工作流样例 + 现有 quote 模板做对照文档；明确晋升门槛（置信度、人审、版本钉扎）。

P1

AgentNexus：模板注册 API / 校验器闭环

完成 9.6 编排器接入；模板从文件或 API 注册；Router 评测集只考三字段；报告特例可并列存在。

P2

RelOS：可执行切片导出

对 active 关系子图提供「导出为 proposed_template」；带 evidence 与 reviewer；默认 pending_human。

P3

data-collection：采集端对齐导出 Schema

会话采集 DAG 直接产出可被 RelOS 摄入的草稿；闭环「采一条 → 审一条 → 晋升一条 → Router 能选中」。

P4

回流与评测

执行 missing / 耗时 / 槽位争用写回 RelOS 待审；模板变更必须走评测草稿，禁止静默覆盖生产 template_id。

9. 风险、边界与非目标

9.1 风险

  • 把关系图直接当运行时 DAG：工业关系图常含诊断联想、非执行顺序边，直接执行会并行错误路径。
  • 自动晋升无门槛：低置信度边进入模板库，Router「选对模板」也会跑出废结果。
  • 字段漂移：采集 Schema、RelOS 关系类型、9.6 信封三套词汇不对齐，导致晋升大量 rejected。
  • 特例膨胀：每加一种业务就新写一个 *_flow.rs，会绕开模板体系。

9.2 明确非目标（本阶段不做）

  • 通用动态 DAG：对话中由大模型即时生成任意依赖图并执行。
  • RelOS 在线推理结果直接触发生产写操作而不经 AgentNexus 权限与人审链路。
  • 用执行失败自动改写线上模板边（只允许进入待审 / 评测草稿）。

9.3 成功判据

  1. 至少 1 条非手工工业模板完成「采集 → RelOS active → 注册 → Router 选中 → 信封汇合」全路径。
  2. Router 评测仍只考核三字段；模板变更有版本与人确认记录。
  3. 报告类任务质量（检索上限、正文长度预算、引用可点）不因模板化回退。

10. 附录：示例映射（示意）

以 9.6 的 quote 为例，展示「沉淀后仍长什么样」——结构不变，供给来源可变：

  },
  "branches": [
    {
      "id": "damage",
      "capability": "general",
      "serial_steps": ["读测量值", "对照修复限度", "给出可修结论和工时"],
      "output_required": ["verdict", "hours"]
    },
    {
      "id": "parts",
      "capability": "general",
      "serial_steps": ["取原厂清单", "对库存和替代件", "算缺件金额"],
      "output_required": ["shortage_amount"]
    },
    {
      "id": "history",
      "capability": "general",
      "serial_steps": ["查本机维修", "查同型号返修", "给保修风险"],
      "output_required": ["warranty_risk"]
    }
  ],
  "join": { "capability": "general", "writes_file": true }
}

Router 运行时输出仍保持扁平、必填：

{
  "template_id": "quote",
  "deliverable": "报价单",
  "slots_ok": "yes"
}

最终建议：把「可沉淀 DAG」列为跨仓架构主题，P0 先冻结晋升契约与样例对照； AgentNexus 侧继续完成 9.6 执行闭环与报告交付质量；RelOS / data-collection 侧按同一 Schema 出口对齐。 如此，三个项目共享同一飞轮，而不是三套互不相认的图。
