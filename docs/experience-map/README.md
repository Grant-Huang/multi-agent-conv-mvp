| 项目 | 内容 |

## 1. 为什么要有体验地图

功能地图（[docs/feature-map/](../feature-map/README.md)、`docs/testing/features.json`）回答“产品有什么”；体验地图回答“用户怎么完成一件事”。一条旅程跨多个功能，体验偏离常发生在功能之间的接缝：每个功能单测都过，旅程照样断（例如 S1/S2/S3 入口丢失）。

体验地图是宪章体验原则的检查依据：每条 CH-U* 至少被一条旅程覆盖；每条旅程写清它守护哪些条款、哪些约束必须成立。

## 2. 旅程怎么写

每条旅程一个 `journeys/UX-xx.md`（给人看），并在 `journeys.json` 登记（给机器）。字段：

| 字段 | 含义 |
|---|---|
| `id` | `UX-01` 这种两位编号，不复用 |
| `persona` | 用户角色文件（`personas/`），写清这个人知道什么、**不知道什么**、用什么设备、多少耐心 |
| `goal` / `success` | 目标与成功标准，**写结果，不写点击路径**；探索式审查只拿到这两项 |
| `start_state` | 起始状态（含夹具数据，标“模拟”） |
| `charter` | 守护的宪章条款编号 |
| `features` | 涉及的功能编号（`features.json` 的 `id`） |
| `invariants` | 约束：必须成立、可写成确定性用例、可阻断。每条要么有 `case`（E2E 用例编号），要么标 `debt: true`（欠账） |
| `budget` | 预算（原则）：步数、整页跳转次数等上限，超出要解释，不阻断 |
| `known_deviations` | 探索式审查确认、但尚未修复的偏离，引用审查报告的 INTENT 编号 |

## 3. 三层测试

| 层 | 做什么 | 执行 | 能否阻断 |
|---|---|---|---|
| 1 确定性回归 | 把约束写成 Playwright 用例（如 `web/e2e/experience.spec.ts` 的 E2E-UX01），并用体验探针记录步数、整页跳转 | 改动界面的 PR（按改动文件 → 功能 → 旅程选取）、每晚 | 可以 |
| 2 探索式审查 | agent 只拿角色、目标、成功标准与宪章条款，用 Playwright 自主操作，边做边记录理由；每条旅程跑 3 次，报成功率与步数 | 每周、发布前 | 不能；发现先由人确认，确认后改写成第 1 层用例 |
| 3 跨版本对比 | 同一旅程与上一版对比步数、截图、页面结构；四个宽度（360/768/1024/1440）视觉审查 | 每周 | 不能 |

探索式审查的结论标“模拟用户证据”：模拟用户读得比真人仔细、耐心不同，Mock 数据也比真实数据干净；要与 CH-G3 的决策记录和真实用户反馈对照。

## 4. 校验规则（`npm run test:map`）

- 旅程编号格式正确、不重复；`document`、`persona` 文件存在。
- 引用的宪章条款在 `PRODUCT.md` 中存在；引用的功能在 `features.json` 中存在。
- 每条约束有已登记且有浏览器测试的用例，或显式标 `debt: true`。
- 没有任何旅程覆盖的 CH-U* 只打印提示，不算错误（试点期）。

## 5. 证据存放

报告与结论入库（`docs/review/product-intent/`）；截图与操作记录不入库，作为 CI 构件或报告附件保存 30 天（2026-11-25 用户确认）。
