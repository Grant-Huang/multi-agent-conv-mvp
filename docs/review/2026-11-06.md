## 🔴 高优先级

### H1. 安全联锁可以被 `patch` 命令绕过（已复现）
- **位置**：`crates/runtime/src/mom/engine.rs:453-485`（`apply_intent` 的 `ProposePatch` 分支）；HTTP 入口在 `crates/server/src/mom.rs:201-203`（`Command::Patch`）。
- **问题**：安全联锁触发后，`ingest` 会把案例设为 `stage = "BLOCKED"`，并置 `world.safety_trip = true`（`engine.rs:173`）。`ProposePatch` 只检查了 `!cancelled`、`replans < 2`、预算和 `actions.is_empty()`，**没有检查 `safety_trip`，也没有检查 stage 是否为 BLOCKED**，就直接执行 `c.stage = "ASSESS"`，然后调用 `pump`（`engine.rs:483-484`）。`approve`（`engine.rs:240`）和 `execute`（`engine.rs:281`）都只判断 `stage != "BLOCKED"`，不看 `safety_trip`。对比之下，`refresh_plan` 明确检查了 `safety_trip`（`engine.rs:346-349`），说明这里是漏检。
- **复现步骤**：S1 走到 WAITING_HUMAN → 注入 `safety_trip` 事件，案例变为 BLOCKED → 发 `patch {node:"quality", dependency:"maintenance"}`，stage 变为 ASSESS → 逐分钟推进，到 WAITING_HUMAN → `approve production` 成功 → `execute production` 成功，写出 3 条动作，stage 变为 VERIFYING，而此时 `safety_trip` **仍然是 true**。
- **影响**：违反案例自带的硬约束 "Never bypass safety interlock or quality release"（`engine.rs:669`），以及 DESIGN 的"安全联锁仍由原有安全系统执行"和 TEST_PLAN T02"安全路径优先"。现有测试 `safety_block_cannot_be_cleared_by_new_normal_observation`（`crates/runtime/tests/mom.rs:476`）只覆盖了"新观测不能解除阻断"，没有覆盖 patch。这虽然是模拟器，但这条不变量正是 MOM 设计要验证的核心安全属性。
- **建议**：
  1. 在所有会改变 stage 或计划的入口统一加守卫：`patch`、`refresh_plan`、`approve`、`execute`、`delegate`。`safety_trip == true` 时一律拒绝，并且判断依据要用 `world.safety_trip` 这个事实，不要用 `stage` 字符串。
  2. 补测试：联锁触发后，`patch` / `approve` / `execute` 都必须失败，并且不能写出任何动作。

## 🟠 中优先级

### M1. 资源预留没有到期时间，一个案例不关闭就会永久阻塞所有其他案例（已复现）
- **位置**：`engine.rs:280`（`resources_busy` 检查任意其他案例的 `reservations` 是否非空）、`engine.rs:292`（写入预留）。预留只在 `close`（`:332`）、`cancel`（`:432`）和 PARTIAL（`:297`）三处释放。
- **复现步骤**：案例 A 执行 production 后不关闭。推进到 2000 分钟后，A 仍然停在 VERIFYING，`reservations = {"tool-32":"CASE-s1-1","XY-XZ":"CASE-s1-1"}`。另一个完全无关的批次 B 批准后执行，报错 "resources reserved by another case"。
- **影响**：与 `docs/mom/DESIGN.md:236`（`resources.reserve` 返回"预留令牌、冲突和**到期时间**"）不一致。另外，检查粒度是"别的案例有任何预留"，而不是"同一资源被占用"，所以不相关的资源也会互相阻塞。
- **建议**：预留记录加上 `expires_at`，到期后在 `tick` 里释放，并记一条事件。冲突检查改为按资源键逐个比较。

### M2. 一次 production 批准覆盖 3 个写动作，与设计"分别授权"矛盾
- **位置**：`engine.rs:293-296`。拿到一个 `approvals["production"]` 后，会一次下发 `mro.transfer`、`eam.maintenance`、`mes.reschedule` 三个动作。
- **依据**：`docs/mom/DESIGN.md:254` 原文是"质量解冻、客户发送、生产停机和改计划分别授权，不能一张批准覆盖全部动作"。
- **建议**：要么按动作拆分批准范围，要么在 MOM 的 DESIGN 和 IMPLEMENTATION 里明确写出这是模拟器的简化，并登记到 `MOCK_REGISTER`。

### M3. `advance` 命令在异步处理函数里长时间持有锁，每分钟都写一次快照和事件（已实测）
- **位置**：`crates/server/src/mom.rs:179-186`（逐分钟调用 `e.advance(t)` 和 `e.run_children()`）、`mom.rs:42-48`（在 `std::sync::Mutex` 锁内执行）、`engine.rs:67-119`（每次 `update` 都克隆并序列化两次整份快照，状态有变化时写一条 `RuntimeStateChanged` 事件）。
- **实测**：4 个 S2 案例，推进 2880 分钟（48 小时，命令允许的上限），release 构建 7.3 秒，debug 构建 21.9 秒，产生约 2944 条事件。
- **影响**：
  - 这段时间内整个 MOM API（包括只读的看板）都在等锁，tokio 工作线程也被同步 SQLite I/O 占住。
  - `mom_events` 每推进 1 分钟至少多 1 行，没有任何清理机制。
  - 循环中途出错时，前面已经提交的分钟不会回滚，但接口返回的是错误，调用方看到的结果和实际状态不一致。
- **建议**：`advance` 一次推进到目标时间，在一个事务里完成，不要逐分钟提交。没有业务事件的纯时钟变化不写事件。数据库操作放进 `spawn_blocking`。

### M4. 已关闭的案例还能被取消，终态被覆盖（已复现）
- **位置**：`engine.rs:416-441`（`cancel` 不检查当前 stage）。
- **复现步骤**：S1 关闭（CLOSED）后调用 `cancel`，返回成功，stage 从 CLOSED 变成 CANCELLED，并多出一条 `CaseCancelled` 事件。重复取消也会重复写事件。
- **影响**：终态不唯一，审计记录自相矛盾。主编排器刚修过同一类问题（状态守卫），MOM 又引入了一次。
- **建议**：`cancel` 和 `close` 都只允许从非终态进入。对已经处于终态的案例，返回明确的错误或空操作结果。

### M5. 事件时间戳用的是上一次 tick 的时间，不是事件真实发生的时间（已复现）
- **位置**：`engine.rs:633-636`（`emit` 使用 `c.updated_at`）。`updated_at` 只在 `tick` 里更新（`engine.rs:825`）。
- **复现**：三条观测的发生时间分别是 497、503、511，但 `ObservationRecorded` 事件的 `at` 全部是 497。
- **影响**：看板和机器视图按时间排序、核对 SLA 时会得到错误的时间线，违背 DESIGN 里"可追溯"的目标。
- **建议**：`emit` 时传入当前虚拟时钟 `s.now`。

### M6. 下发失败后再次执行仍然返回成功（代码推断）
- **位置**：`engine.rs:283-284`。同一个 `{case}:{plan_revision}:{scope}` 下只要已经有任何动作，就直接 `return Ok(())`，包括状态为 FAILED 的动作。
- **影响**：下发失败（stage=PARTIAL）后，操作员再次点"执行"，会看到成功，但实际什么都没发生。DESIGN 第 217 行要求"副作用状态不明时先查询回执"，现在是把"已有记录"直接当成了"已完成"。
- **建议**：幂等重放时，返回现有动作的状态（或者在已有动作失败时返回错误），不要无差别返回 Ok。补一条测试："dispatch_failure 后再次执行"。
