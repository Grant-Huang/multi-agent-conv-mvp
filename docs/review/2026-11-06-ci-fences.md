## 🔴 高优先级

### H1. master 没有任何分支保护，所有门禁都可以绕过（已查证）
- **证据**：GitHub API `list_branches` 显示 `master` 的 `"protected": false`，所有分支都没有保护。
- **后果**：
  - **3 次合并没走 PR，直接推到了 master**（首父链上不是 "Merge pull request #N" 格式的提交）：
    - `259e9be` "Merge MOM blackboard workflows…"：36 个文件，+3066 行，包含 MOM 引擎和 HTTP 接口，没有对应的 PR；
    - `929301a` "Merge MOM master agent and blackboard design"：+390 行，没有对应的 PR；
    - `17e83aa` "Merge MCP capability cards…"：合并的第二个父提交是 `0a1c8a3`（本地把 master 合进功能分支之后的结果），而不是 PR #6 的头提交 `74e413c`，两者相差 12 个文件、+1326/−125 行。**这个合并后的版本从来没有在 PR 上跑过 CI**。GitHub 只是在推送之后，自动把 PR #6 标成了已合并。
  - **PR #7 在 CI 开始之前就合并了**：合并时间是 06:24:10，6 个 check run 的开始时间都是 06:25:05。
  - 这违反了 AGENTS.md 的"不得绕过 CI，不得直接推送 main"，也违反了指南 A.9 的"合并门禁：禁止直接推送 main"。`CI_GATES.md` 第 3 节写了设置步骤，但这些步骤从来没有执行过。
- **影响**：第四、五、六层全部变成了"建议"。CI 只能事后发现问题，不能阻止问题进入 master。指南第 0 节第 2 条说得很明确："指导不是安全边界"。
- **建议**：见下文"可实施的围栏" P0-1。

### H2. 风险分级和变更规模都能被"重命名"绕过，可以把 L3 改动判成 L0（已实测复现）
- **位置**：`tools/ci/common.py:93-106`（`git diff --numstat base...head`，没有加 `--no-renames`）、`tools/ci/risk_classify.py:98-118`。
- **原因**：git 默认会检测重命名，numstat 输出的路径形如 `docs/tmp/notes.md => .github/workflows/notes.yml` 或 `tools/{ci => lib}/common.py`。脚本把整串字符当成一个路径去匹配规则。
- **实测**（在草稿目录另外克隆一份仓库，本仓库没有任何改动）：
  1. 先合入一个 `docs/tmp/notes.md`（内容是一个工作流 YAML），这一步判定为 L0。
  2. 在下一个 PR 里，只把它重命名为 `.github/workflows/notes.yml`，结果：`风险等级：L0（自动合并允许）`，`变更规模：0 行，1 个文件，0 个组件 → pass`。
  3. 把 `tools/ci/common.py` 重命名成 `tools/lib/common.py`，结果被判成 L2（"未匹配任何规则"），而不是 L3。
- **影响**：新增 CI 工作流、移走 CI 策略脚本这两类改动，正是指南 6.1 规定的 L3（"CI/CD、发布机制"），却会被判成 L0 或 L2。将来按指南让 L0 自动合并时，这就是一条直接改 CI 的通道。现有的 48 个自测都没有覆盖重命名。
- **建议**：`numstat` 和 `diff` 都加上 `--no-renames`（或改用 `--name-status -z`，同时按旧路径和新路径分别判定，取较高的等级），并补两条测试："重命名进入 L3 目录"和"重命名移出 L3 目录"。

### H3. 独立审查没有落地：抽查的 6 个 PR 审查记录都是 0，作者自己合并
- **证据**：`get_reviews` 查询了 PR #2（CI 门禁本身，L3）、#3、#5（状态机，L2）、#6、#7、#9（模板运行时，L2），结果全部是 `[]`。12 个 PR 的作者和合并人都是 `Grant-Huang`。PR 从创建到合并：#7 用了 33 秒，#10 用了 2 分 12 秒，#8 用了 4 分 10 秒。
- **对照**：指南 3.4 要求"审查者必须与开发者分离"，A.12 要求"开发 Agent 的发起人不能算作独立审批人，Reviewer Agent 也不能替代人工审批"，`risk-policy.toml` 里 L2 的规则是"审查人不是作者"。现在的每日审查是在**合并之后**才运行的，起不到合并前门禁的作用。
- **建议**：见 P0-1、P1-4、P2-1。

### H4. 单人仓库里，"审批"这条围栏在结构上无法成立，需要先做决策
- **位置**：`.github/CODEOWNERS`（所有路径都只有 `@Grant-Huang`）、`docs/CI_GATES.md` 3.1 节。
- **问题**：所有 PR 都以仓库所有者的身份创建（AI 会话也用这个身份），而 GitHub 不允许作者批准自己的 PR。所以只要开启"需要 1 个批准"或"需要 CODEOWNERS 批准"，**每个 PR 都无法合并**，除非所有者使用绕过权限。而一旦允许绕过，这条规则就失去了意义。这不是配置写错了，是"一个人、一个身份"的结构决定的。
- **建议**（需要你决定，见"需要人决定的事"）：
  1. 增加第二位有写权限的审查人；
  2. 或者让 AI 开发会话改用独立的机器账号（GitHub App 或 bot 账号）提交 PR，由你作为审查人批准。这样"作者不是审查人"才真正成立，也符合指南 8.4 "每个 Agent 有独立身份和凭证"的要求。

## 🟠 中优先级

### M1. CI 依赖没有固定版本，"绿色"结果不能复现
- `ci.yml` 中 `actions/checkout@v4`、`dtolnay/rust-toolchain@stable`、`Swatinem/rust-cache@v2`、`astral-sh/setup-uv@v5`、`actions/setup-node@v4`、`actions/setup-python@v5`、`actions/upload-artifact@v4`、`taiki-e/install-action@v2`、`gitleaks/gitleaks-action@v2` **全部使用可变的标签**。指南 A.9 和 `CI_GATES.md` 第 5 节的待办里都写了要固定到完整 SHA，至今没有完成。
- Rust 工具链用的是 `@stable`，仓库里也没有 `rust-toolchain.toml`。新版 clippy 增加的 lint 会让 CI 在代码没有任何改动的情况下突然变红。
- cargo 命令没有加 `--locked`（`ci.yml` 中的 `cargo clippy --all-targets`、`cargo test --workspace`），`Cargo.lock` 过期时会被静默更新。`docs/testing/README.md` 自己要求使用 `--locked`，两份文档不一致。指南 5.3 要求"使用固定版本依赖"。
- **建议**：所有 action 固定到 SHA，并配 Dependabot 自动提更新 PR；加 `rust-toolchain.toml`；cargo 命令统一加 `--locked`。

### M2. 功能地图校验和浏览器 E2E 不在 CI 里
- `web` job 只跑 `typecheck`、`test`（vitest）、`build`。`npm run test:map`（`web/package.json:11`，检查 `features.json` 和功能地图是否一致）**没有在 CI 里运行**。可是 AGENTS.md 明确要求"同步 `docs/testing/features.json`、功能地图和证据状态"。
- 功能地图里登记了 9 个浏览器用例（Playwright，`npm run verify` / `test:e2e`），一个都不在 CI 里。指南 4.2 要求"需求 → 功能 → 代码 → 测试 → 证据"能够追踪，这条链在 CI 这一环断了。
- **建议**：`test:map` 直接加进 `web` job，只要几秒钟。浏览器 E2E 先作为每晚定时运行的 job，稳定之后再改为 PR 必需检查。

### M3. 测试被弱化的情况检测不到
- `tools/ci/change_size_check.py:53-55` 只统计 `#[test]`、`def test_`、`it(` 这类标记**行数**的增减。
- 新增 `#[ignore]`、`.skip(`、`.only(`，删除或放宽 `assert`，改断言里的期望值，都**不会被发现**。`CI_GATES.md` 第 4 节也承认它"不能证明测试被弱化"。
- 指南 5.3 要求"检查测试文件是否被不合理修改"，AGENTS.md 也把"修改测试让它通过"列为禁止事项。
- **建议**：增加内容信号，包括新增 `#[ignore]` / `.skip` / `.only` / `#[should_panic]`、净减少 `assert`、修改已有测试的断言行。命中后要求在 PR 描述里写"测试变更说明"，否则阻断。

### M4. 风险等级不阻断，L3 和 L0 的合并要求完全一样
- `change-policy` job 只输出等级（`CI_GATES.md` 第 1 节："风险等级本身不会让 job 失败"）。L3 的"需要 CODEOWNERS 批准"依赖分支保护，而分支保护根本没有开启（H1）。
- **建议**：开启分支保护和 CODEOWNERS 审查（P0-1）。在 H4 决策之前，至少让 L3 的 PR 必须带一个审批标签，并且这个标签要由非作者添加（CI 可以通过检查标签事件的操作者来实现）。

### M5. 开发 Agent 的权限没有被运行时限制（第 8 节）
- AI 开发会话拿到的 GitHub 凭证可以直接推送 master（受 H1 影响）。仓库里也没有 Claude Code hooks 或权限配置（没有 `.claude/` 目录和 settings），"不得直接推送 main"只是写在提示词里的一句话。
- 指南 8.4 和 A.13 要求"由平台服务端执行，不能只写在 Prompt 里"。
- 产品侧的情况：ACP agent 默认权限是 `AllowAll`（`crates/agents/src/acp.rs`，前几轮报告已经指出过），节点令牌没有撤销机制（前几轮的遗留问题 #9）。
- **建议**：分支保护是根本办法。另外可以加 `.claude/settings.json`，在 deny 列表里禁止 `git push` 到 master 和 `--force` 推送，作为开发体验层面的第二道防线。按指南 8.2，本地 hook 能被绕过，只能当提醒用。

## 可实施的围栏（按投入从小到大）

下面每一项都会修改 `.github/**`、`config/**` 或 `tools/ci/**`，这些都是 L3 路径，需要仓库所有者本人操作或批准。本报告只列方案，不做改动。

### P0：今天就能做，不需要写代码
1. **开启 master 分支保护**（Settings → Branches，或 Rulesets）：
   - 勾选"必须通过 PR 合并"和"禁止直接推送"，禁止强制推送和删除分支；
   - 把 `rust`、`web`、`python-websearch`、`python-tools`、`change-policy`、`security` 设为**必需检查**，并要求分支是最新的；
   - **不允许管理员绕过**；
   - 在 H4 决策之前，"需要的批准数"先设为 0，否则单人仓库无法合并任何 PR。即使批准数是 0，也能立刻堵住 H1 里的直接推送，以及"CI 没跑完就合并"的问题。
2. **更新 `CI_GATES.md` 的状态**（L1），用一个文档 PR 完成。

### P1：一两天，改动很小
1. **修复重命名绕过**（H2）：`common.py` 加 `--no-renames`，补 2 条测试。
2. **固定 CI 依赖版本**（M1）：action 固定到 SHA，新增 `rust-toolchain.toml`，cargo 命令加 `--locked`。
3. **`web` job 加上 `npm run test:map`**（M2）。
4. **新增 PR 模板和 `REVIEW.md`**（L3）。PR 模板对应指南 A.25 的 7 个部分，重点是"测试证据"和"回滚方案"。`REVIEW.md` 可以直接采用 A.10 的内容，再补上本仓库的高风险文件清单。
5. **调整 `concurrency`**（L2）：只在 PR 上启用 cancel。

### P2：一周左右，需要写一些脚本
1. **合并前的 AI 审查，先用影子模式**（H3，指南 8.6）：在 PR 上自动运行独立的审查 Agent，只发评论、不阻断。积累 2–4 周后，和人工结论对比误报率，再决定是否让它阻断合并。
2. **测试弱化检测**（M3）：在 `change_size_check.py` 里增加 `#[ignore]`、`.skip`、`.only`、assert 净减少等信号，并补对应的测试。
3. **每晚运行浏览器 E2E**（M2）：新增 `schedule` 触发的 job，跑 `npm run verify`，失败时自动开 issue。
4. **L3 审批标签检查**（M4）：L3 的 PR 必须有 `l3-approved` 标签，并且添加标签的人不能是 PR 作者。

### P3：需要先做决策
1. **独立身份**（H4，M5）：AI 开发会话改用 GitHub App 或 bot 账号提交 PR，你作为审查人批准。这一步完成后，P0-1 的批准数才能改成 1，CODEOWNERS 审查才有实际意义。
2. **L3 双人审批**（指南 6.1）：需要有第二位人工审查人。
3. **Eval 进 CI**（贯穿）：`an-eval` 需要模型。可以先用固定的模型回放结果或替身，做一个不依赖网络的回归子集。

### 需要人决定的事
- 增加第二位审查人，还是让 AI 会话使用独立的 bot 身份（决定 H4、M4 和 P3-1 怎么做）？
- 变更规模的阈值是保持 800/2000，还是收紧到指南建议的 300/500？
- L0 改动是否允许自动合并？在 H2 修复之前，**不建议开启**。
