**一句话结论**：任何会被多处提到的内容只在一个权威位置完整描述，其他文档最多一句要点加链接；规则写进研发规范第 3.1 节，`AGENTS.md` 列要点；不写进产品宪章。

## 背景

`DEV_STANDARD.md` 第 3 节已规定特性的意图和设计只在特性档案里描述，但没有覆盖研发线职责、宪章条款、契约等跨特性内容。2026-11-26 核对各线分工时，同一职责在多份文档里各写一遍，已经出现不一致。

## 问题

同一内容多处复述，改一处忘一处，读者和 agent 会按过时的描述派工或实现。

## 决策依据

1. 2026-11-26 核对发现三处不一致（已在 PR #380 修正）：
   - `DESIGN.md` 第 0.1、0.2 节复述第 5 线职责，未包含后续调整；
   - `docs/fencing/NIGHTLY_DISPATCH_PLAN.md` 的主线仍写第 3 线，而夜间监视已移交第 2 线；
   - `PLAN.md` 仍以 2026-11-22 旧决定为分工依据。
2. 用户意见（见“来源”）。
3. 写入位置：`docs/PRODUCT.md` 是产品宪章，现有条款（CH-P / U / G）都是产品原则，这条是文档与研发规则，归 `DEV_STANDARD.md`（其“地位”一栏写明是唯一研发规范）；`AGENTS.md` 是所有 agent 每次开工都读的入口，列要点才能确保执行（助手建议，用户采纳）。

## 定了什么

1. `DEV_STANDARD.md` 新增第 3.1 节，列出常见内容的权威位置：

   | 内容 | 权威位置 |
   |---|---|
   | 研发线职责 | `INTEGRATION_PLAN.md` 五线表 |
   | 特性负责线 | `DESIGN.md` 第 0.3 节“负责线”列 |
   | 宪章条款 | `PRODUCT.md` |
   | 契约 | `contracts/` |
   | 用例 | `CASES.md` |
   | 决策依据 | `decisions/` |
   | 研发规则 | `DEV_STANDARD.md` |

2. 4 条规则：
   - 非权威处最多一句要点加链接；
   - 改权威内容时同一 PR 里把复述改成引用，不属于本线的开 Issue 派工；
   - 不一致时以权威位置为准；
   - 历史记录不追改。
3. `AGENTS.md`“修改范围”加一条要点，链接第 3.1 节。

## 没选什么

| 做法 | 为什么没选 |
|---|---|
| 写进产品宪章 `PRODUCT.md` | 宪章只放产品原则，混入工程规则会稀释宪章；用户采纳推荐 |
| 只写进 `DEV_STANDARD.md` | agent 不一定读到第 3.1 节，`AGENTS.md` 需要列要点 |
| 立即在 `doc_lint` 加重复检测 | 重复描述难以机械判断，先靠规则与评审；以后可按权威位置表做定向检查（例如非权威文档出现成段的线职责描述） |

## 影响与后续

- 已按本规则修正研发线职责的三处不一致（PR #380）。
- 各线修改文档时自行遵守；产品意图审查与守护者巡检发现复述时按第 2 条处理。
- 可选：第 2 线评估在 `doc_lint` 中加入定向检查（未派工）。

## 出问题先看

- 两份文档说法不同：先查 `DEV_STANDARD.md` 第 3.1 节的权威位置表，以权威位置为准。
