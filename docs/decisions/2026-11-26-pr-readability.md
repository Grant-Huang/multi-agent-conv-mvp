| 项目 | 内容 |

| 日期 | 2026-11-26 |

**一句话结论**：
- PR 标题统一为“[第N线][风险等级] 一句白话结果（Closes #N）”，不再用分支名或内部编号当标题；
- 正文开头先写三行以内的“给审查人”，再列“需要你决定”和“怎么看效果”，技术细节放后面；
- 缩写与编号只在 `docs/GLOSSARY.md` 解释一处，未登记的不得出现在标题和“给审查人”里。

## 背景

六条研发线与审查会话都在开 PR，审查人是项目负责人一人。PR 多由 agent 撰写，习惯用内部编号和缩写。

## 问题

审查人要先查清编号、缩写、上下文才能判断要不要自己做决定，审查成本高，容易漏掉需要拍板的事。

## 决策依据

1. 用户意见（见“来源”）。
2. 2026-11-26 最近 30 个 PR 标题的事实：
   - 直接用分支名：#429“Line1 uxfix k 314”、#413“Cursor/line5 346 slice5”、#414“Line1 uxfix d 302”、#412、#410；
   - 塞满内部编号：#439“R-20261126-M1/M2”、#443“CH-G2c”，审查会话自己的 #444“GR-4-CI-BUDGET”、#435“T0～T3”；
   - 未定义简称：“convmem”“exec 资料块”“slice4a”“W2”“A2A”。
3. 原 PR 模板首节“变更说明”问的是“改了什么、为什么这样改”，没有“审查人需要做什么”。
4. 同一写法有两种含义：风险 L0～L3 与记忆层 L0～L5；严重度 P0～P3 与实施阶段 P0～P3。

## 定了什么

1. **标题**：`[第N线][风险等级] 用户能看懂的一句话结果（Closes #N）`。
   - 前半句不含内部编号与缩写，约 30 字以内；
   - 风险等级以 CI `change-policy` 为准，开 PR 时可先写预估，CI 出结果后更正；
   - 审查会话用“[审查]”代替线号。
2. **正文顺序**：
   1. 给审查人：三行以内——做了什么、为什么、需要你做什么；
   2. 需要你决定：选项、推荐、理由；没有写“无”；
   3. 怎么看效果：界面改动附截图或三步内能复现的操作；
   4. 技术细节：原模板的关联、设计一致性、非目标、风险与回滚、验证证据。
3. **术语表** [GLOSSARY.md](../GLOSSARY.md)：
   - 缩写与编号第一次出现时附一句说明或链接；
   - 未登记的不得用于标题和“给审查人”；
   - 新缩写随 PR 补登记；
   - 两组易混编号写全称前缀（“风险 L2”“记忆层 L2”“严重度 P1”“阶段 P1”）。
4. **派工 Issue** 同样适用：标题白话，正文先写给负责线的一句话目标。
5. **检查**：第 2 线在 `change-policy` 中加 PR 可读性检查（标题格式、缺“给审查人”、出现术语表以外的缩写），先警告不阻断。

## 没选什么

| 做法 | 为什么没选 |
|---|---|
| 只改模板不建术语表 | 缩写问题仍要靠审查人自己查 |
| 检查一上来就阻断 | 规则刚定，误报会卡住所有线；先警告，稳定后再议 |
| 标题沿用 Conventional Commits（`feat(scope):`） | 面向开发者，不面向审查人；类型可留在提交信息里 |
