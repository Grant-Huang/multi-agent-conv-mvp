# 决策记录（一条一个文件）

从 2026-11-21 起，新决策写成本目录下的单独文件。2026-11-21 以前的决策仍在 [DECISIONS.md](../DECISIONS.md)，它逐步冻结为历史档案。

**为什么单列**：多个分支同时往 `DECISIONS.md` 末尾追加、各自取“最大号 + 1”，合并时既冲突又撞号（42、43、59、61 各被用了两次；2026-11-21 还有分支在用已被占用的 69 号）。一条一个文件、按“日期-主题”命名，并行分支互不干扰，每条决策也能写得完整。

**写给谁看**：写给**没参加过当时讨论的新接手的人**（包括人和 agent）。只读这一个文件，就要能看懂当时面对什么问题、凭什么这样定、定了之后系统长什么样、出了问题从哪查。

**生效范围**：`AGENTS.md` 目前仍写“定下来的事统一记在 `docs/DECISIONS.md`”。修改 `AGENTS.md` 属于 L3，方案见 [文档体系整理计划](../DOC_SYSTEM_PLAN.md) 第 4 节，获批前两种写法都接受；新写的决策请用本目录。

## 文件名与引用

- 文件名：`YYYY-MM-DD-主题.md`，主题用小写英文和连字符，例如 `2026-11-21-doc-layers.md`。同一天同主题再加后缀 `-2`。
- 引用：写“决定 + 文件名”（不带 `.md`），例如“决定 2026-11-21-doc-layers”。

## 必须写清的内容

| 部分 | 要求 |
|---|---|
| 开头表格 | 日期、来源、状态、影响范围（哪些特性或文档）、相关设计（链接） |
| 一句话结论 | 一句话说清定了什么 |
| 背景 | 新接手的人需要先知道的事：当时系统是什么样、为什么这个问题现在冒出来。不假设读者参加过讨论；术语第一次出现时用一句话解释 |
| 问题 | 要解决什么，不解决会怎样 |
| **决策依据** | **凭什么这样定**。每条依据都要能核对：数据或实验结果（附数字和出处）、代码事实（文件和行号或提交）、测试或评审编号、外部资料链接、用户的明确意见（注明日期）。推断要标“推断”；没有依据的判断不能当依据 |
| 定了什么 | 具体内容，逐条写 |
| 简单设计（需要时） | 决定影响结构、接口、状态或流程时写：一张图或一张表，说明改了什么、各部分怎么配合。已经有设计文档的，写到“哪份文档第几节”，并用一两句话概括要点，不要只放链接 |
| 没选什么 | 考虑过的其他做法，以及各自没选的原因 |
| 影响与后续 | 需要跟着改的文档、代码、测试；还没做的事和谁来做 |
| 出问题先看 | 排查时从哪里下手：日志事件、开关、文件、用例 |
| 变更记录 | 被取代、补充或修订时，在这里写日期、原因和关联的决策 |

来源的写法：**用户确认**（项目负责人在对话里明确同意）、**用户采纳**（助手提出，用户照此推进）、**助手建议**（还没有明确表态，有争议时不能当成已确认）、**实验数据结论**（由数据直接得出）。

状态：**有效** / **待用户确认** / **部分生效**（写明哪部分待定）/ **已取代**（写明被哪个文件取代）。被推翻的决策不删文件，只改状态。
