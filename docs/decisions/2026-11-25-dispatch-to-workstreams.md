## 背景

用户有 5 条研发线并行开发（数量和内容以后可能变化）。审查会话此前每发现一批偏离都先问用户“要不要派卡”，增加了等待；同时也存在审查会话顺手改实现的风险（与 CH-P4“执行者不当自己的裁判”同理，见 [2026-11-25-ux01-intent-fixes-and-charter-risk](2026-11-25-ux01-intent-fixes-and-charter-risk.md)“没选什么”）。

## 问题

- 发现由谁修、怎么交接，没有固定规则。
- 研发线的数量和职责会变，规则不能写死线的名单。

## 决策依据

1. 用户 2026-11-25 的指示（见“来源”）。
2. 五线职责以 [INTEGRATION_PLAN.md](../INTEGRATION_PLAN.md) 表格为准（2026-11-25 读取）：1 AI 桌面产品入口；2 独立复跑与集成协调；3 工业业务闭环；4 执行协议与共享契约；5 内省、分层记忆与会话上下文。
3. 以往派卡方式：任务卡写在决策文件里，再由交接提示转给对应线（[2026-11-24-review-h1-h4-fix-plan](2026-11-24-review-h1-h4-fix-plan.md)：FIX-A → World Adapter 线，FIX-B → 第 4 线，FIX-C → 桌面线）。各线是本会话无法直接发消息的独立 agent（推断：分支前缀 `cursor/ai-desktop-*`、`cursor/line4-*`、`cursor/line5-*`、`cursor/convmem-*`），交接提示由用户转发。

## 定了什么

### 派卡规则

1. 审查会话（含每周守护者）**不改产品代码与产品测试实现**；可以写体验地图、约束用例（只断言已成立的行为，基线补录）、审查报告、决策和任务卡。
2. 每条发现按 `INTEGRATION_PLAN.md` 当时的研发线表定归属；**每次派卡前重新读该表**，不凭记忆。跨线的，写明主责线和配合线。
3. 归属明确的，直接派卡（写进决策文件 + 交接提示），不再逐条请用户批准；以下情况仍先问用户：要改宪章或共享契约、要改高风险文件（`AGENTS.md`“先停下来问人”）、归属不明或两条线都可以、与已批准的方案冲突。
4. 任务卡编号沿用“以主线 #1 发号为准”的约定，审查侧暂用 UXFIX-字母。
6. **派卡渠道：GitHub Issue**（用户 2026-11-25：“派发任务的方式能不能通过 GitHub 完成……不必经过我”）。每张卡一个 Issue，标签 `dispatch` + `line:N`（研发线编号）+ `severity:high|medium|low`；标题以“[第N线] 卡号”开头；正文写派工来源（决策文件）、宪章条款、要解决的问题、做法要点、验收（先 Red）、“PR 正文写 `Closes #N`”。研发线完成后由 PR 关闭 Issue；审查侧据此把欠账约束改为用例。决策文件仍保留卡片全文与依据，Issue 是派送和跟踪的载体。
7. 研发线开工前查看本线的 open Issue（`label:dispatch label:line:N`）。这一步要写进各线都读的 `AGENTS.md`“开始前”，属于 L3 改动，须用户批准后另开 PR。
8. **认领与分诊落地**（2026-11-26 补充，用户确认）：开始做时必须在 Issue 留言认领；分诊方对“已修复 / 重复”直接关闭，对“拟派”当场开 Issue。依据：2026-11-26 检查时 24 个派工 Issue 全部未关闭，除第 3 线外无一认领；第 3 线的分诊停在“建议关闭”“拟派第 1 线”，未落地（#256、#275 评论）。
9. **自动巡检与时限**：Claude 定时任务每 4 小时检查 `dispatch` Issue。认领时限 8 小时；开工进展时限 high 3 天、medium 7 天、low 不限（2026-11-26 由 48 小时改为本规则：用户定认领 8 小时；分认领 / 开工两档与开工天数为助手建议，用户在同一轮采纳）。超时只在 Issue 上提醒并推送汇总，不自动改派。依据：48 小时把“留一句认领”与“完成修复”放在同一时限，第 1 线 15 张派工在规则生效后近 12 小时仍无任何回应（#312）。
10. **一个主责、谁关闭、公告单**（2026-11-27，用户确认“按你建议做”；细则为助手建议、用户采纳）：
    - 派工 Issue 只挂**主责线**一个 `line:N` 标签，配合线写在正文“配合：第 M 线”；
    - **主责线负责关闭**：有 PR 的用 `Closes #N` 自动关闭；没有 PR 的（取证、方案、调研），贴出结论与证据后自行关闭；配合线做完自己那部分只留言、不关闭；
    - 能拆开的工作，由派单方开**总 Issue + 按线的子 Issue**（GitHub 子 Issue 关联）；子 Issue 由各线关闭，全部关闭后由总 Issue 的主责线或派单方关闭总 Issue；
    - **公告单**：标题以“[各线通知]”开头，标签 `announcement` 加全部线标签，不挂 `dispatch`，不关闭；评论超过 30 条或每月一次，开新公告单、关闭旧单并贴新链接；
    - 巡检增加两项：`dispatch` Issue 没有线标签或有多个线标签；子 Issue 全部关闭但总 Issue 仍开着。
    依据：2026-11-27 核对 40 个 open 派工 Issue——#312（公告）挂了 line:1～5 却缺 line:6，第 6 线看不到；#428 只有 `dispatch`、没有任何线标签，巡检算不到任何线；规则此前只写了“跨线写明主责与配合”，没写谁关闭。
5. 发现研发线的划分与实际工作不符（例如某类问题反复无人认领），在报告里提出调整建议，由用户决定。

## 简单设计

### UXFIX-E（扩大）：工作区按 Task ID 显示真实任务（INTENT-2026-009、014，CH-P8、CH-U2）

| 项 | 内容 |
|---|---|
| 做法 | `WorkspaceView.tsx` 任务信息（状态、业务对象、来源）与执行摘要按 Task ID 读取：真实任务取 `GET /api/tasks/{id}` 的 `status`、`goal`、`result`（摘要、产物、证据）；只有夹具任务（SMT-03 等）显示模拟内容并标“模拟”。状态词用同一张映射表，与首页卡片、受理提示一致（原 UXFIX-E 要求）。“我的工作”卡片与受理提示的“打开任务”要能看到同一份结果 |
| 验收（先 Red） | 新增 E2E：首页委派 → 等完成 → 从“我的工作”卡片进入，工作区显示该任务的目标与“已完成”，能看到产物名，不出现“质量批次 SMT-03”“桌面首页 Mock”；完成后 UX-03-I4 从欠账改为用例 |
| 不做 | 不改任务状态机与持久化（`orchestrator.rs`、`store.rs`）；不改 HTTP 接口 |

### UXFIX-H：任务完成时主动告知（INTENT-2026-015，CH-U3）

| 项 | 内容 |
|---|---|
| 做法 | 委派的任务进入完成、失败或需要用户处理时，在助理消息里加一条普通优先级消息，带“查看结果”入口；按 DESIGN 第 7 节不抢焦点、按任务去重；首页受理提示同步为完成状态或收起 |
| 验收（先 Red） | 新增 E2E：首页委派 → 去做别的事 → 完成后助理消息出现该任务的完成消息，点“查看结果”看到结果；受理提示不再显示“后台处理中”；完成后 UX-03-I5 从欠账改为用例 |
| 不做 | 不新增主动消息类型的服务端存储（若必须新增，另出方案） |

### UXFIX-I：输入为空时不代用户委派（INTENT-2026-016）

| 项 | 内容 |
|---|---|
| 做法 | 删除 `S1AskBar.tsx` 第 32 行的默认目标“继续调查并整理证据链”；输入为空时“委派任务”不可用，或提示“先说说要做什么” |
| 验收（先 Red） | 组件测试或 E2E：输入为空点“委派任务”不产生新任务；完成后 UX-03-I7 从欠账改为用例 |
| 注意 | 现有用例若依赖空输入委派，改为显式填写目标（这是测试输入调整，不是放松断言），在 PR 中写 `## 测试变更说明` |

## 没选什么

| 做法 | 为什么没选 |
|---|---|
| 审查会话自己修 | 用户明确不要；审查者不修自己发现的问题 |
| 每条发现都先问用户再派 | 用户要求直接派；只在宪章、契约、高风险文件、归属不明时才问 |
| 把研发线名单写死在规程里 | 用户说明线的数量和内容会变；改为每次读 `INTEGRATION_PLAN.md` |
| 014 交第 4 线 | 任务接口已返回真实状态与结果，缺的是桌面展示 |
| 交接提示经用户转发 | 用户要求不经过本人；转发会漏、会延迟 |
| 仓库内派工队列文件（`docs/dispatch/line-N.md`） | 要经 PR 合并才生效，状态要手工勾；Issue 可由 PR 的 `Closes #N` 自动关闭、可按标签筛选 |
