## 2. SPC 流程到运行实例的映射

### 2.1 节点逐个映射

绑定结果来自 `binding::compile`（2026-11-12 本地运行）。"界面步骤名"是给业务人员看的名称，不显示节点 ID。

| 节点 | 专家标签 | 绑定执行者 | 界面步骤名 | 运行时等待什么 | 本设计的处理 |
|---|---|---|---|---|---|
| n1 | SPC控制图打点出界 | 结构 | （触发事件，不计入步骤） | — | 由 SPC 失控事件创建事项 |
| n2 | 确认失控 | agent | 按判异规则确认失控 | Agent 产出判定与证据 | 技能：Western Electric 规则。**待专家补充**：用哪个系统取数、归属领域 |
| n3 | 如何隔离受影响产品？ | agent→人 | 决定隔离方式 | **人工决定**：停线 / 挂起受影响产品 | Agent 给出建议与依据；这一步就是截图里的"待人工确认" |
| n3a | 停线 | 人 | 停线 | 现场回执 | 仅在选"停线"时进入；另一支显示"未选中" |
| n3b | 把受影响的产品挂起来 | 人 | 挂起受影响产品 | 现场回执 | 同上 |
| n4 | 查特殊原因 | agent | 调查特殊原因 | Agent 报告 | 技能："不要先重算控制限消掉失控点"。**待专家补充**系统与领域。汇合点：只等已选中的那一支 |
| n5 | 在图上标注失控信号和采取的措施 | agent（质量，写 `spc`） | 在控制图上标注 | **动作批准** → 执行回执 | 写操作带 `action_approval` 闸门；批准不等于已写入 |
| n6 | 过程是否稳定？ | agent→人 | 判断过程是否稳定 | **人工确认** | Agent 给判断和证据，人确认 |
| n7 | 不能计算过程能力 | 无法绑定 | 暂停过程能力计算 | — | **不可执行**：显示"待专家补充"。见 §2.3 |
| n8 | 记录处理过程 | agent | 记录处理过程 | Agent 产出处理记录 | **待专家补充**系统与领域 |
| n9 | 是否必要时对受影响产品100%检验？ | 系统规则 | 决定是否全检 | 见 §2.3 风险 | 本设计按"agent→人"呈现，等专家确认 |
| n10 | 对受影响产品100%检验 | 人 | 全检受影响产品 | 现场回执 | 仅在需要全检时进入 |
| n11 | 输出失控响应记录和整改单 | 结构 | （结束：形成记录与整改单） | — | 到达结束节点**不等于事项关闭**（原则 §12） |

### 2.2 进度计数

截图写"3 / 5"。SPC 流程有两个 XOR 分支，分母不能是节点总数。

- 分母 = **本次路径上已确定要做的步骤**。未作出的决定之后的步骤按"待定"列出，不计入分母；作出决定后再计入。
- 未选中的分支显示"未选中"并说明原因，不计入分母，也不显示为完成（原则 §9）。
- 例：选"挂起"之前，进度为"已完成 1 / 已确定 2，其余待决定后确定"；不写成"1/11"。

### 2.3 必须先请专家确认的问题

1. **模板未晋升。** SPC 模板是 `needs_completion`。按原则 §9.1，"采集到流程不代表流程已批准"，待补充的模板不能当生产流程执行。本设计只允许在**模拟模式**下运行（全程标"模拟"，对应 Mock 清单），真实运行须等模板晋升为 `promoted`。
2. **n7 无法绑定。** "不能计算过程能力"更像一条约束（过程不稳定时禁止计算 Cpk），而不是一个动作。建议专家确认后改为**约束**：过程未稳定时，n8 的处理记录里不得出现 Cpk。模拟模式下 n7 显示为"待专家补充"，并自动按"已记录约束、未执行动作"通过，不显示为"已完成"。
3. **n9 的绑定可能有误。** 规则 R4 因为标签含"100%"判为系统规则，但问题本身是"是否必要时"，并没有阈值。这说明 R4 的词表把"100%"当成了阈值信号。本设计**不改绑定规则**（会改变 RT-BIND 用例结果），界面按"agent 建议、人确认"呈现，并把它列为待专家确认项。
4. **n2 能否用确定性规则。** Western Electric 规则本身是确定性的，判异可以由系统规则完成，Agent 只负责解释。请专家确认后再决定执行者。
5. **执行角色缺失。** 13 个节点全部没有 `actor_roles`。决定节点 n3、n6、n9 由谁批准，需要专家指定（例如质量工程师、班组长），否则只能用测试身份 `supervisor`，与现状一致（Mock M20）。

### 3.3 处理进展的状态与点击行为

沿用原则 §8.1 的节点点击契约，状态文字与图标同时出现，不只靠颜色。

| 运行状态 | 界面文字 | 点击后直接看到 | 下一步 |
|---|---|---|---|
| SUCCEEDED | 已完成 | 结论、证据、未完成边界、执行方 | 就地看证据；AI 可选 |
| RUNNING | 进行中 | 已有进展、开始时间、预计下一次反馈 | 按权限跟进 |
| WAITING_DECISION | 等待决定 | 决策卡（方案、前提、范围） | 批准 / 拒绝 / 要求修改 |
| WAITING_RECEIPT | 等待现场回执 | 工作项、责任人、时限 | 提交回执（附证据） |
| WAITING_APPROVAL | 等待动作批准 | 将写入的系统、对象和内容 | 批准该动作 |
| PENDING | 待开始 / 待定 | 阻塞它的上游步骤 | 进入上游步骤 |
| NOT_SELECTED | 未选中 | 未选原因、决定人和时间 | 只读 |
| NEEDS_EXPERT | 待专家补充 | 缺少什么（系统、角色等） | 模拟模式下按 §2.3 处理；真实模式不可执行 |
| FAILED / TIMED_OUT | 失败 / 超时 | 已产生的效果、原因、可否重试 | 有权限时重试或升级 |

### 3.4 协作记录规则

- 一条消息只属于一个事项；跨事项引用要显式写出事项 ID，并检查权限（原则 §10）。
- Agent 消息必须带至少一个引用（步骤或证据）。没有引用的 Agent 输出只能显示为"待核验"，不能推进步骤。
- 人在对话中说"可以"不等于批准。批准只能通过决策卡，或由对话生成一张待确认的决策卡，再由人点击（原则 §10、§11）。
- 系统消息（事件接入、状态变化）默认合并显示，只有决定、回执、失败、超时单独成条，避免刷屏（原则 §5）。
- 模型不可用时，协作记录、处理进展和决策卡照常可用；只有"问 AI"显示不可用。

## 4. 运行时设计

> 本节涉及 `engine.rs`、`model.rs` 的状态机和持久化结构。虽然不在 AGENTS.md 列出的三个高风险文件里，但它是 MOM 唯一的状态和持久化入口，**按高风险对待，实施前单独批准**。

### 4.1 数据模型（新增字段都用 `#[serde(default)]`）

`Case` 新增：

| 字段 | 类型 | 说明 |
|---|---|---|
| `workflow` | `Option<WorkflowRef>` | 模板 ID、来源流程 ID、来源内容哈希、晋升状态、运行模式（`simulation` / `production`） |
| `thread` | `Vec<ThreadMessage>` | 协作记录：`seq, at, author_kind(human/agent/system), author, text, refs[], provenance` |
| `decisions` | `BTreeMap<String, NodeDecision>` | 决定节点的选择：`node, option, actor, plan_revision, at, rationale_refs` |

`Node` 新增：

| 字段 | 说明 |
|---|---|
| `kind` | `start / activity / decision / end`，来自专家流程 |
| `label` | 界面步骤名 |
| `executor` | 来自绑定卡 |
| `branches` | 决定节点的出边：`[{option, to}]` |
| `gate` | 来自绑定卡（`approval` / `action_approval`） |
| `receipt` | 人工节点的回执与证据引用 |

`status` 新增取值：`PENDING`、`WAITING_DECISION`、`WAITING_RECEIPT`、`WAITING_APPROVAL`、`NOT_SELECTED`、`NEEDS_EXPERT`。原有 `READY / RUNNING / SUCCEEDED / UNKNOWN / FAILED` 保留。

持久化：`Case` 整体以 JSON 存在 `mom_snapshot.body`，新增字段带默认值，旧快照可直接读出，**不需要改表结构，也不需要迁移**。若评审认为仍需显式版本号，则在快照外层加 `schema_version` 并参照 `crates/runtime/src/store.rs` 补列写法。

### 4.2 实例化

1. 新事件类型 `spc_out_of_control`（来源 `QMS`，携带控制图、特性、批次、命中的判异规则）。
2. 运行时按事件类型查找已注册模板；SPC 模板来自 `binding::compile` 的输出，**由确定性代码选择**，模型只能解释，不能选择未注册模板（DESIGN.md §6）。
3. 校验：复用 `binding::validate_workflow_template`，再做实例级校验——节点数 ≤ 20（SPC 为 13）、每个决定节点的每个选项都有出边、所有路径能到达结束节点。
4. `promotion != promoted` 时：只允许 `simulation` 模式实例化，事件 `PlanAccepted` 的载荷带 `mode: simulation` 和未晋升原因；`production` 模式直接拒绝（`TemplateRejected`）。

### 4.3 推进规则

- **普通边**：上游 `SUCCEEDED` 后下游变为 `READY`。
- **决定节点**：Agent 先产出建议（`RUNNING → WAITING_DECISION`）；人选择后记录 `NodeDecision`，选中分支变为 `READY`，其余分支及只能经由它们到达的节点变为 `NOT_SELECTED`。
- **汇合**：SPC 中的汇合（n4、n8、n11）都在 XOR 之后，规则是"所有**未被排除**的上游都已完成"。`NOT_SELECTED` 不算失败，也不算完成。
- **人工节点**：`READY → WAITING_RECEIPT`，提交回执后 `SUCCEEDED`。回执只证明"人报告已完成"，核验另算（原则 §6）。
- **写操作节点（n5）**：`WAITING_APPROVAL` → 批准 → 执行（模拟写入）→ 回执 → `SUCCEEDED`。复用现有幂等键格式 `{case}:{plan_revision}:{scope}:{tool}`。
- **待补充节点（n7）**：模拟模式下记为 `NEEDS_EXPERT`，并按 §2.3 第 2 条作为约束通过；真实模式下阻塞。
- **新观测**：沿用现有 `ingest` 行为——已有外部动作时进入 `BLOCKED`，否则重新规划并使旧批准失效。

### 4.4 HTTP 接口（新增，属公开接口变更，需批准）

| 方法与路径 | 作用 |
|---|---|
| `POST /api/mom/scenarios/spc` | 用固定夹具创建一个 SPC 模拟事项（与现有 `s1`、`s2` 相同风格） |
| `POST /api/mom/cases/{id}/commands` `{"command":"decide","node","option","plan_revision","actor"}` | 记录决定 |
| `… {"command":"receipt","node","note","evidence_refs"}` | 提交人工回执 |
| `… {"command":"approve","scope":"node:n5",…}` | 动作批准，扩展现有 `approve` 的范围 |
| `… {"command":"post","text","refs"}` | 人在协作记录中发言 |
| `GET /api/mom/cases/{id}` | 现有接口，返回值增加 `workflow`、`thread`、`decisions`、`progress`（按 §2.2 计算好的计数） |

计数由后端算好再返回，前端不自行解释分支语义（原则 §9）。

### 4.5 Agent 角色（模拟）

| 角色 | 负责步骤 | 本期实现 | 替换目标 |
|---|---|---|---|
| 质量分析 Agent | n2、n3 建议、n4、n6 建议、n8 | 脚本输出，固定证据 | M18 / M19 真实模型 |
| SPC 系统工具 | n5 标注 | 模拟写入 | 真实控制图软件接口 |

"Agent 团队"只在节点详情和管理入口出现，主界面显示业务步骤和责任人。

### 4.6 超时、取消与清理

- 每个等待人的步骤有到期时间。专家流程没有 `sla_config`，模拟默认值放在新夹具 `fixtures/mom/spc/tools.json`，用现有虚拟时钟（M17）推进；到期产生提醒和升级事件，不自动替人做决定。
- 取消事项沿用现有 `cancel`：未开始的步骤标为取消；**已执行的停线、挂起不撤销**，取消后显示"需人工处理已产生的效果"（原则 §11）。
- 本期没有新的子进程。脚本 Agent 在引擎内同步运行，没有需要清理的后台任务。

### 4.7 事件（写入现有 `mom_events`）

新增事件名：`DecisionRequested`、`DecisionRecorded`、`BranchNotSelected`、`ReceiptRequested`、`ReceiptSubmitted`、`ThreadMessagePosted`、`NodeNeedsExpert`。全部带 `case_id`、`revision`。沿用 `PlanAccepted`、`DecisionApproved`、`ActionAccepted`。
