# MOM 业务工作台 UI / UE 设计原则

版本：1.0。日期：2026-11-07（America/Vancouver）。

性质：后续 MOM 主界面设计、开发和评审的约束基线；不是能力完成声明。适用于人类工作台及其 AI 会话入口，不要求将后台机器公告板改造成相同结构。

## 1. 适用与执行约定

本文中的“必须／不得”为验收约束；“建议”为默认设计，允许结合真实岗位测试调整；示意名称、布局尺寸、颜色和样例数量不构成固定规范。

- 开发前须阅读本文，并将本次涉及的规则落实到业务用例及可执行验收；测试流程遵守仓库既有约定。
- 涉及主导航、业务状态含义、审批边界或事项关闭条件的偏离，须在实现前说明理由和业务影响，并更新设计基线；不得仅因原型已经这样画就沿用。
- 本文是本轮讨论收敛后的界面基线。旧原型、[早期评估](HUMAN_BOARD_UX.md)与本文冲突时，以本文为准；旧原型未覆盖或尚未改造的能力不得视作已符合本文。
- 后端能力以代码和验证证据为准；缺口统一维护在 [Mock 清单](MOCK_REGISTER.md)，本文不另建一份实现完成台账。
- 架构、安全与执行约束见 [MOM 设计](DESIGN.md)。界面不得绕过这些约束，也不得通过图形暗示后端具备尚未实现的能力。

## 2. 用户与首要目标

主要用户是车间主管、班组长、调度、质量、设备、仓储等制造业务人员。他们具备业务知识，不应被要求理解 Agent 分工、模型路由、工具协议或 DAG 技术字段。

任何重要事项必须使用户能够找到以下六个答案：

1. 发生了什么，影响什么？
2. 谁负责，谁需要采取行动？
3. 准备怎么做，有什么前提？
4. 缺什么，为什么等待？
5. 已做到哪里，下一步和下一次反馈是什么？
6. 凭什么认定问题已经解决？

主界面按业务组织，不得按维护 Agent、物料 Agent、排产 Agent等内部执行主体划分主导航。普通用户默认看到业务动作与责任方；执行主体、工具、来源与分配依据在需要时可查。

## 3. 信息架构：三个入口，一个统一事项工作区

日常工作主导航固定为“看板、任务、资源”。同义名称应统一，不再另设与其重复的“公告板”“我的工作”“AI助手”“DAG运行”等一级业务模块。

| 入口 | 回答的问题 | 默认组织方式 | 不应承担的职责 |
|---|---|---|---|
| 看板 | 发生什么，哪些值得关注？ | 事项、风险、重要变化、决定、承诺、通知 | 展示全部底层任务、日志、指标或资源台账 |
| 任务 | 需要做什么，谁做，进展如何？ | 待处理、进行中、受阻、已完成等工作分组 | 将所有通知强制变成任务，或替代事项验收 |
| 资源 | 能不能做，缺什么条件？ | 当前状态、缺口、占用、适用约束 | 把所有维度都当作可调度资源，或将库存等同于可用量 |

基础资料维护、权限管理、历史报表、知识及模板管理仍需存在，可置于相关对象详情或按角色开放的管理入口，不强塞进三个日常列表。三个入口覆盖运营工作台，不等于覆盖整个 MOM 软件的全部配置与管理功能。

从三个入口进入同一事项，必须使用同一事项 ID、版本、责任与进展，不得分别复制业务状态。

### 3.1 范围与个人工作

“我的工作”是一种范围投影，不是第四套业务数据。建议提供“与我相关／本班组／本车间”，实际名称随组织配置。

- “与我相关”包括我执行、我负责、待我决定、影响我负责目标，以及我主动关注的事项；不得只等于分配给我的任务。
- 范围选择与业务状态筛选必须区分并保持可见；切换后保留用户选择，数据刷新不得擅自重置。
- 查看范围不能扩大权限。无权限对象的标题、计数、搜索结果及会话引用也不得泄露。
- 个人便签与私人草稿默认不进入公共看板或共享 Agent 上下文；共享须有明确操作和可见范围。

## 4. 核心业务对象与事实来源

| 对象 | 含义 | 必需业务信息 |
|---|---|---|
| 事项 | 一个待达成目标或待解决问题 | 目标、影响范围、责任人、时限、关闭标准、关联流程／任务／资源 |
| 任务 | 为事项执行的具体工作 | 动作、责任方、状态、前提、期限、结果及核验要求 |
| 资源／条件 | 执行所需能力、状态、证据及限制 | 对象标识、适用范围、可用性、占用、来源、新鲜度与缺口 |
| 决定 | 对具体方案与动作的授权或裁决 | 决策人、方案版本、动作范围、前提、时间、有效性 |
| 证据／回执 | 支持事实、执行与核验的记录 | 来源、发生／采集时间、版本、范围、验证状态 |
| 公告／承诺 | 团队共享信息或约定反馈 | 发布人／责任方、受众、有效期或到期时间、关联事项 |

看板是这些对象的投影，不维护第四套事实。现场记录与企业系统是各自领域的权威来源；共享状态服务整合引用与版本，不把 AI 总结提升为权威业务事实。

例如：“XZ 缺刀具”是资源缺口；“插单 A 因此不能开工”是事项影响；“调拨刀具”是任务。三者关联，状态变化由有依据的业务事件传播，不能要求用户在三处手动勾选完成。

## 5. 看板原则

- 以业务事项及重要变化为中心；同一事项跨人机料法环测出现时引用同一对象，不复制成多份独立事项。
- 卡片优先呈现：发生什么、影响、负责人、当前阶段、阻塞／风险、下一步、下一次反馈，以及一个明确主操作。
- 假设、已确认事实、正式决定、执行回执必须区分。相关性不能显示为已证实因果。
- 重要异常、超期、批准与业务承诺变化进入看板；普通工具日志与每次状态跳动不得刷屏。
- 通知可以只通知，不强制生成任务；需执行或确认的动作再关联工作项。
- 已读、认领、批准、执行完成、核验通过分别记录。事件消费游标不等于人类已读。
- 按风险和时限排序，避免只有时间倒序。对历史决定保留版本与当时适用范围。

## 6. 任务原则

建议默认分组：“待我处理、进行中、受阻／需协助、已完成”。其他范围下可将“待我处理”调整为“待处理”；工作分组是用户投影，不要求与底层状态机一一对应。

- 已完成默认折叠；受阻与超期不得隐藏在普通进行中列表。
- 折叠标题保留总数、异常数及可理解的摘要；默认不嵌套多层折叠。
- 每项工作显示责任、期限、当前结果／阻塞和下一步；待确认动作明确由谁决定。
- 有核验要求时，“提交完成”进入待核验，不能直接显示核验通过。简单任务是否需要独立核验由业务契约决定，不一律增加审批。
- 受理、指令下发、现场执行、收到回执与验证成功不得混用。
- 多人协同时区分唯一牵头责任与参与者；Agent 执行主体不代替人类责任分配。
- 超期、失败、退回、拒绝、取消均须说明影响与下一步；取消不抹去已发生的现场效果。

## 7. 资源与人机料法环测

资源入口同时支持“看全貌”和“看缺口”；进入具体事项后优先显示该事项所需条件，不强制跳到全车间台账。

| 维度 | 重点 | 必须区分 |
|---|---|---|
| 人 | 班次、技能资格、在岗、负荷、责任交接 | 有人、具备资格、已确认可投入 |
| 机 | 状态、能力、占用、维护、释放条件 | 空闲、可用、适合本工艺、已预留 |
| 料 | 批次、齐套、库存、在途、冻结、替代 | 在库数量、可用量、已预留、已交接 |
| 法 | 工艺、作业规范、参数、版本、偏离批准 | 可查阅、受控有效、适用于当前设备／产品 |
| 环 | 区域温湿度、洁净、能源、安全等 | 有读数、读数新鲜、范围合格、现场已确认 |
| 测 | 检验任务、方法、量具校准、检测能力、结果 | 有检测能力、已检、结果通过、已授权放行 |

“法”通常是约束，“环”通常是运行条件，“测”同时含资源和证据，不得全部套用资源预留状态。量具、检验员等对象只维护一份事实，通过多个维度投影，避免重复预留。

### 7.1 Tab 与展开列表

- Tab用于同一入口内的聚焦维度切换；建议资源提供“全部、人、机、料、法、环、测”。
- “全部”显示各维度摘要与缺口，不堆叠六张全量台账；异常组优先展开。
- 具体事项用上下展开列表综合检查条件：维度摘要 → 缺口 → 责任与处理入口。
- 看板的人机料法环测主要用于筛选及影响标签；任务主要按工作状态分组。不得机械复制六套一级导航。
- 不适用、未知、过期、异常、正常须分别表示。无异常记录不等于已证实正常。

### 7.2 多事项资源争用

- 以事项列表、资源时间泳道或冲突清单表达争用；不将全厂全部节点混成一张图。
- 区分业务依赖、共享证据与资源竞争；读取同一报告不代表争用同一设备。
- 预留要有对象、容量、时段、状态及失效依据；未确认释放时间不得绘制为已承诺空档。
- 显示等待原因、受影响事项、调整代价和下一步责任人。安全、质量、授权硬约束优先，不能用赶工或人工点击绕过。
- 排程的“最优”须有目标、约束和验证依据。没有证明时使用“建议／可行候选”，不宣称全局最优。

## 8. 统一事项工作区与最短操作链

用户点开事项后，应在一个上下文中查看情况、处理进展、决定、资源缺口与结果。工作区可采用页面、抽屉或模态形式，具体选型按屏幕和任务复杂度验证，不强制特定容器。

- 总览先回答六个业务问题，细节逐步展开；不得先展示整条系统技术信息链。
- 跨入口引用定位到目标对象／任务／条件，不能只跳到一个笼统首页再让用户搜索。
- 返回保留来源入口、筛选、范围和滚动位置；不得因刷新、会话展开或详情关闭而丢失定位。
- 一条主操作必须指向下一业务动作，避免含糊的“处理”“继续”而不说明效果。

### 8.1 DAG 节点点击契约

| 节点状态 | 默认打开内容 | 直接提供的下一步 |
|---|---|---|
| 已完成 | 结论、实际完成内容、证据、未完成边界及责任方 | 就地查看记录／通俗解释；AI为可选辅助 |
| 等待条件 | 缺失条件清单、责任、反馈时限、业务影响 | 处理具体调拨／维修／检验等动作 |
| 等待决定 | 具体方案、比较、前提与批准范围 | 批准、拒绝或要求修改 |
| 进行中 | 已有进展、最近反馈、预计下一次更新 | 按权限跟进；不可伪造精确完成时间 |
| 等待上游 | 具体阻塞对象及其状态 | 直接进入阻塞项处置 |
| 失败／超时 | 已产生效果、原因证据、重试／补偿条件 | 有权限的重试、恢复、转交或升级 |
| 未选中／跳过／取消 | 原因、选择依据及是否产生过效果 | 查看记录；不得默认当作已完成 |

点击“维护初筛已完成”必须直接看到初筛结论，不再要求先问AI。点击“等待刀具”必须进入调拨缺口的处置，不先进入资源总览。解释和证据在当前节点工作区内可达，不串联多个无关页面。

## 9. DAG 是基本处置模式，不是主导航

复杂事项按 DAG 组织依赖、并行、关卡与核验；普通查看、发布通知、提交已有回执不必另起一张 DAG。普通用户界面使用“处理进展／处置流程”等业务名称，DAG技术细节按需开放。

- 默认阶段摘要，必要时展开业务泳道及依赖图。图与列表引用同一运行实例，不另造展示状态。
- 并行必须可见；AND等待全部必需结果，XOR只选择满足条件的一路，OR等待本次选中的分支集合。未知条件不等于false；未选中不等于失败。
- 必需、可选、超时降级及汇合策略须来自执行契约，不能由前端或模型临时解释。没有对应后端语义时须标明未支持。
- 独立调查可并行，但不能以未验证结论绕过安全节点；读工具安全降级不代表写操作可继续。
- 重试保留尝试记录；重规划保留图版本、变更原因和批准有效性，不在历史图上覆盖成“从未发生”。
- 图需区分计划、运行、已完成和未选分支，长图支持缩放／定位或列表替代；不能只依赖颜色，也不能只用技术ID加依赖文字。

### 9.1 流程选择及来源链

目标链路为：data-collection采集过程与业务记录 → RelOS组织关联及证据 → 主Agent结合当前事件选择适用DAG → 运行时校验 → 实例执行。

- Agent自主选择不能等同于获得执行授权。模板注册状态、输入／输出契约、适用范围、版本、权限及安全关卡仍由确定性机制控制。
- RelOS线索与data-collection记录须可追溯；采集到流程不代表流程已批准，存在关系不代表因果成立。
- 无匹配或校验失败时显示待补充／不可执行，并给出下一步；不得将生成草稿直接表现为生产流程。
- 普通用户默认看到选中的业务流程和当前进展；“为什么选它”按需展开，展示简短选择依据、候选排除原因、证据及校验结果。
- 流程依赖图与决策审计链分别表达“如何执行”和“为何这样选／由谁授权”；不得以模型内部思维链充当业务依据。

## 10. 确定性界面与 AI 会话

确定性界面负责事实、状态、证据、权限及执行入口；AI负责解释、比较、检索、拟议方案和辅助整理。二者共享事项标识与版本，不维护两套工作流。

- 底部提供稳定、紧凑的单一会话入口；展开后不得再同时保留另一套可输入AI栏。
- 宽屏可展开可调宽侧栏，小屏切换会话工作区；比例不写死，必须验证DAG、表格与决策卡仍可用。
- 收到回复不自动抢焦点、放大面板或推动流程图。展开／关闭保留业务定位、会话历史与草稿。
- 输入前明确当前事项、关联节点或方案；跨事项引用须显式且遵守权限，不悄悄沿用上一事项上下文。
- 回复优先说明原因、变化、影响与下一步，以引用定位确定性对象，不重复输出整张台账或工具JSON。
- 完成结果和已知解释必须直接可看，不能为了阅读已有数据强制调用模型。
- 会话中提出的动作须进入与按钮相同的授权、校验、幂等和回执链路；自然语言不得成为绕过门禁的入口。
- 模型不可用时，已有事实、任务、证据及已支持的确定性处置仍可访问；需要AI的新增分析明确不可用，不假装已完成。

## 11. 决策、安全与执行回执

- 决策卡必须给出：事项、方案版本、具体动作、作用对象、影响、风险、前提、排除范围及批准后的下一步。
- AI可以讨论取舍，但不能自行扩大批准范围。含糊的“可以”在有歧义时必须澄清，不默认批准多个候选或多个事项。
- 对不满足硬约束的方案不提供可执行批准入口；可保留作为排除方案并说明原因。
- 方案、资源或证据版本变化后，重新校验原批准有效性；重要变化须重新授权，不沿用旧批准。
- 授权人有权限才可提交；批准不等于指令已发出，发出不等于受理，受理不等于执行完成，完成不等于核验通过。
- 重复点击、网络中断、超时和部分成功不得重复产生外部动作。界面显示提交中、结果未知、待查询或补偿状态，不把超时解释为未执行。
- 不承诺通用回滚。物理加工、停机、发货等已产生效果的动作，按业务补偿或后续处置处理。

## 12. 双层闭环、交接与关闭

任务闭环：受理／认领 → 执行 → 提交结果 → 按契约核验；失败进入返工、重试、转交或升级。

事项闭环：明确目标及验收条件 → 分析与决定 → 执行 → 验证业务结果 → 关闭、继续处置或明确移交。

- 全部任务完成不自动等于事项目标达成；DAG跑完也不自动等于业务解决。
- 关闭前检查目标、风险、承诺、核验证据，以及是否存在未移交工作；关闭须有依据与责任。
- 可分离的剩余工作建立关联事项并明确接责后继续跟踪，不能在关闭时静默丢弃。
- 交接须包含未完工作、风险边界、下一次承诺及交接责任；已读不等于接责，接班确认不等于业务关闭。
- 人类反复介入的纠正应沉淀为可检验规则、回归用例、受控流程或知识；不得只积累聊天文字，也不得未经验证自动晋升为生产规则。

## 13. 真实、模拟及异常体验

- 界面必须区分设计样例、模拟执行、真实接入未验收、真实验收通过。混合来源时在记录／动作级标识，不只依赖全局横幅。
- 不得以“实时”“已接入”“已冻结”“已发出”等文案描述尚无证据的能力或动作。
- 数据展示适用范围、来源和更新／发生时间；加载中、无数据、未知、过期、无权限及错误分别呈现。
- AI根因和收益估算标为假设／估算，列明依据及待验证项；未经校准的置信分数不当作因果概率。
- 实时刷新保留用户阅读位置和未提交输入；过期版本提交时校验并说明差异。
- 原始JSON、工具参数全文、内部状态码默认折叠到诊断层；中文业务状态、图例、文字与图标配合，不靠颜色单独表达。
- 关键操作可用键盘完成，焦点可见；弹层关闭返回触发位置。表格和长图可在自身区域滚动，手机主页面不得无意横向溢出。

## 14. 场景验收基线

后续每次变更选取相关行形成可执行断言；完整主界面发布须覆盖全部适用行。不适用项须说明原因，不得用原型截图替代集成验证。

| ID | 场景 | 必须满足的业务断言 |
|---|---|---|
| UI01 | 三入口进入同一事项 | 状态、责任、版本一致；返回保留范围与定位 |
| UI02 | 切换个人／班组／车间 | 可见范围清晰，权限不被筛选绕过，个人便签不泄露 |
| UI03 | 多维筛选 | 同一事项不重复建档；资源摘要可聚焦，人机料法环测含未知和不适用 |
| UI04 | 已完成节点 | 一次点击直接看到结果；就地可查证据与解释，不强制问AI |
| UI05 | 等待条件 | 一次点击看到缺口、责任和对应处理入口，不要求重新搜索台账 |
| UI06 | 任务分组 | 已完成可折叠；受阻、超期仍可发现；提交与核验分开 |
| UI07 | S1并行研判与改排 | 必需汇合、方案关卡、刀具和首件条件可辨；未知根因不写成事实 |
| UI08 | 模板选择 | data-collection／RelOS来源可查；候选草稿不可执行；未支持链路明确标识 |
| UI09 | 方案批准 | 版本、范围与前提明确；硬约束不可绕过；变更后重新校验 |
| UI10 | 指令超时或重复提交 | 不重复外部动作；结果未知可查，不能误报成功或未执行 |
| UI11 | 多事项争用资源 | 可见冲突、影响和下一步；未确认时间不被承诺；无重复预留 |
| UI12 | AI与界面协同 | 单输入入口、事项隔离、节点引用；会话关闭回原位；模型故障不阻断已有事实查看 |
| UI13 | S2客户投诉 | 冻结以回执为准；4小时回复、24小时阶段报告与8D关闭分开 |
| UI14 | 业务关闭与移交 | 任务完成不自动关闭事项；剩余工作有人接责；交接不抹除风险 |
| UI15 | 混合真实与模拟 | 动作级可辨来源；无回执不宣称成功；过期／无数据／无权限不显示为正常 |
| UI16 | 桌面、Pad、手机与键盘 | 关键路径可完成，无重复面板、意外横向溢出或焦点丢失 |

建议以主管、班组长、质量、维修和仓储等岗位开展无引导可用性测试，记录任务成功率、误批准、查找时间、返回次数及口述理解。具体性能和可用性门槛在场景验收计划中明确，不凭示例人数或布局比例宣称生产可用。
