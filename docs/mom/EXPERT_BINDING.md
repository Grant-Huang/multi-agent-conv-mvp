# 专家工作流节点绑定与模板晋升（E1-C 方案 B）

把 data-collection 中"专家确认"的工作流图编译为**带节点绑定的工作流模板**：每个节点由谁做、属于哪个领域、能用哪些工具、加载哪些技能、受什么闸门约束。

- 只做确定性的编译、校验和统计，不调用模型，**不接入编排器执行**。
- 代码：`crates/runtime/src/mom/binding.rs`
- 测试：`crates/runtime/tests/promoted_templates.rs`（RT-BIND-01..10）
- 数据：`fixtures/mom/expert/workflows.json`（9 条，来源与脱敏说明见同目录 README）
- 结果：`docs/mom/results/expert_binding/report.json`（统计）；完整模板 `templates.json` 用下面的命令生成，不入库

重新生成结果：

```bash
cargo run -p an-runtime --example promote_expert -- fixtures/mom/expert/workflows.json docs/mom/results/expert_binding
```

## 1. 为什么不直接晋升为 §9.6 并行模板

§9.6 的原则是"能串行做完的留在一个 agent 里，只有几路互不等待才套并行模板"。9 条已确认流程中，分叉几乎都是判断节点的条件分支，并行边（`parallel`）为 0。所以按 §9.6，**0 条可以晋升为并行模板**。

串行流程的去处应该是：一个领域 agent，加上技能（步骤和判断规则），再以人工审批作为闸门。因此要晋升的是"工作流模板 + 节点绑定"，而不是"并行模板"。

## 2. 绑定卡与规则

每个节点生成一张绑定卡，包含以下字段：

| 字段 | 含义 |
|---|---|
| `executor` | 执行者，见下表 |
| `domain` | 所属领域 |
| `tools` / `write_tools` | 可用工具 / 其中有写操作的工具 |
| `skills` | 加载的技能 |
| `gate` | 闸门 |
| `inputs` / `outputs` | 输入 / 输出 |
| `rules` | 命中的规则编号 |
| `needs_expert` | 需要专家补充的内容；为空表示绑定已完整 |

`executor` 的取值：

| 取值 | 含义 |
|---|---|
| `agent` | 信息类工作，由领域 agent 执行 |
| `human` | 物理动作或签字，由人执行并回执 |
| `system` | 确定性规则或系统自动动作 |
| `agent_then_human` | agent 给出判断和证据，由人确认 |
| `structural` | 开始、结束、合并等结构节点 |
| `unbound` | 无法绑定 |

规则按优先级排列，先命中先用：

| 规则 | 条件 | 绑定 |
|---|---|---|
| R1 | 审批节点 | `human`，闸门类型 `approval`。审批人取执行角色，时限取 SLA，升级对象取超时边指向的节点。**永不交给 agent 或 system** |
| R2 | 机制是设备/量具；或者没有系统机制、标签含物理动作、且标签不以信息动作开头 | `human` 工作项（物理操作不能由软件替代，见 MOCK_REGISTER） |
| R3 | 机制是系统，且在工具清单内；或者有角色或对象链接、标签是信息类动作 | `agent`。有写操作（上传、下达、解锁、签字、标注……）时列入 `write_tools`，并加 `action_approval` 闸门 |
| R4 | 判断节点里有明确阈值或关键词（数字、%、±、"关键词"、"超过"等）；或标签含"自动" | `system`：确定性规则，或系统自动动作 |
| R5 | 判断节点没有明确规则 | `agent_then_human` |
| R6 | 有控制依据（标准、SOP、图纸等） | 挂为技能 |
| R7 | 执行角色映射到领域（检验员、IPQC、IQC、质量经理→质量；维修工→设备；计划员、车间调度→计划；操作员、班组长→生产；收货员、采购→采购物流）；没有角色时，用工具的默认领域 | 设置领域；agent 节点定不下领域时，要求专家补充 |
| R8 | 系统不在工具清单；或无角色、无链接、看不出动作 | `unbound`，写明原因，**不猜** |

**分段规则**：A→B 是普通边或交接边，A 只有这一条出边，B 只有这一条入边，且 A、B 都是同一领域的 agent 时，二者合并为一段。人工节点、审批节点和判断节点各自单独成段；条件边保留为段与段之间的路由。

**校验规则**（`validate_workflow_template`）：

1. 每个节点恰好属于一段；
2. 段间路由无环；
3. 工具都在清单内；
4. 有写操作就必须有批准闸门；
5. 审批节点必须由人执行；
6. 多节点段只能由同一领域的 agent 组成。

**晋升判定**：

| 结果 | 条件 |
|---|---|
| `invalid` | 校验失败 |
| `needs_completion` | 有任一节点需要专家补充 |
| `pending_expert_confirmation` | 绑定完整，但专家尚未逐个确认 |
| `promoted` | 专家已确认 |

## 3. 结果（2026-11-07，9 条专家确认流程）

工作节点共 114 个，不含 23 个结构节点。按执行者分布：

| 执行者 | 节点数 | 占比 |
|---|---|---|
| agent | 30 | 26% |
| agent_then_human（agent 判断，人确认） | 18 | 16% |
| system（确定性规则 / 系统自动） | 7 | 6% |
| human（物理动作 41、审批 12） | 53 | 46% |
| unbound | 6 | 5% |

各条流程的情况：

| 流程 | 工作节点 | agent | agent→人 | system | human | unbound | 需专家补充 | agent 段 | 晋升 |
|---|---|---|---|---|---|---|---|---|---|
| 销售订单转生产需求 | 8 | 7 | 1 | 0 | 0 | 0 | 7 | 5 | needs_completion |
| 来料检验（IQC）基本流程 | 9 | 1 | 2 | 0 | 5 | 1 | 2 | 1 | needs_completion |
| 01_IQC_来料检验 | 29 | 5 | 3 | 4 | 16 | 1 | 3 | 5 | needs_completion |
| 02_FAI_首件检验 | 9 | 1 | 1 | 0 | 6 | 1 | 1 | 1 | needs_completion |
| 03_工序扫码 | 7 | 2 | 2 | 0 | 2 | 1 | 3 | 2 | needs_completion |
| 04_设备预防保养 | 16 | 4 | 3 | 1 | 7 | 1 | 5 | 4 | needs_completion |
| 05_SPC失控响应 | 11 | 4 | 2 | 1 | 3 | 1 | 4 | 4 | needs_completion |
| 09_日排程下达 | 6 | 4 | 1 | 0 | 1 | 0 | 2 | 4 | needs_completion |
| 10_复合工序+异常 | 19 | 2 | 3 | 1 | 13 | 0 | 2 | 2 | needs_completion |

晋升漏斗：

| 阶段 | 条数 |
|---|---|
| 专家确认流程 | 9 |
| 通过模板校验 | 9 |
| 绑定完整 | 0 |
| 可套 §9.6 并行模板 | 0 |
| 待专家确认绑定 | 0 |
| 已晋升 | 0 |

主要发现：

- **需要专家补充的节点共 29 个，占工作节点的 25%。** 其中 22 个是"信息类工作但没有链接系统"：专家说清了做什么，但没说用哪个系统做。7 个缺少执行角色，无法定领域。6 个完全无法绑定。可见现有采集方式缺少机制信息（M），应在 data-collection 的确认环节补问"用什么系统完成"。
- **agent 工作是碎片化的。** agent 段平均只有 1.07 个节点，最长 3 个；只有 1 段由多个节点合并而成。原因是人工动作、审批和判断节点频繁打断信息工作。在这些流程中，多 agent 的价值主要在于**在人工步骤之间衔接与准备**，而不是长链自动化。
- **审批全部落在人工闸门上**（12/12）。有写操作的节点共 4 个，全部带批准闸门。41 个节点挂上了来自控制依据的技能。

## 4. 局限

- **R2、R3 的动作词表是在这 9 条流程上调出来的，它们只能算开发集。** 规则的泛化效果须在 E1-A 补采的新流程（独立测试集）上评估。
- 写操作的识别依赖词表，可能有遗漏。例如"记录在收货检验报告上（ERP）""打特批单"目前没有判为写操作，这正是需要专家逐个确认绑定的原因。
- 工具清单只到系统粒度（如 `erp`），没有细到具体接口；工具都是仿真工具，未连接真实系统。
- 9 条流程中有 7 条由同事按真实经验编写，2 条来自员工真实口述，样本小。结果只能写成"可行性与问题分布"，不能当作绑定准确率。

## 5. 论文可写 / 不可写

- 可写："9 条专家确认流程、114 个工作节点，经确定性规则绑定：agent 26%、agent 判断加人确认 16%、确定性规则 6%、人工 46%（含 12 个审批闸门全部由人完成）、无法绑定 5%；25% 的节点需要专家补充，主要缺少系统机制；没有流程满足 §9.6 并行条件。"
- 不可写：模板已接入执行；绑定已经专家确认；绑定规则的准确率（尚无人工标注的金标准）。
