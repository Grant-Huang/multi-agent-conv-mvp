| 相关 | [文档体系整理计划](../DOC_SYSTEM_PLAN.md)（2a 阶段）；[决策写法](../decisions/README.md)；[共享契约](../contracts/README.md) |
| 模板 | [特性档案](feature-dossier-template.md)、[交接说明](handoff-template.md)、[版本说明](release-template.md)；迁移步骤见 [迁移指南](migration.md) |

## 1. 要解决的问题

一个特性的“为什么做、要什么、怎么做、做到哪、在哪个版本里”现在散在设计文档、决策、PLAN、CASES、功能地图、证据等多处，靠人工互相引用，改一处忘一处，就会出现多路不一致（例子见 [decisions/2026-11-21-doc-layers](../decisions/2026-11-21-doc-layers.md) 的决策依据）。

本规范的目标：**每个特性有且只有一个入口文档；需求、设计、实现、质量、版本五个环节各有唯一的位置和编号，并且能用机器检查链条有没有断。**

## 2. 五个环节各放在哪

| 环节 | 唯一位置 | 编号 | 谁来维护 |
|---|---|---|---|
| 意图与需求 | 特性档案 `docs/features/<特性>/README.md` 的“意图”“需求”两节 | 特性 ID（沿用 `features.json` 现有 32 个 `id`）；需求 `REQ-<特性>-NN` | 提出需求的人；改动须用户确认 |
| 设计 | 特性档案的“设计”一节；太长时拆成同目录子文档，档案里保留要点和链接 | 章节锚点 | 实现该特性的会话 |
| 跨特性约定 | [docs/contracts/](../contracts/README.md)，特性档案只引用 | 契约内的不变量编号（如 A1、S3） | 改动须出方案、用户批准 |
| 实现 | 代码；特性档案“实现入口”一节列路径；PR 正文写需求编号 | 提交、PR | 实现者 |
| 质量 | 用例在 [testing/CASES.md](../testing/CASES.md)；每条需求挂用例编号；证据在 `docs/testing/evidence/` | `E2E-*`、`RT-*` | 实现者写，评审核对 |
| 版本 | git tag `vX.Y.Z` + `docs/releases/vX.Y.Z.md` | 语义化版本号 | 用户打 tag；版本说明由登记表生成 |
| 为什么这样定 | [docs/decisions/](../decisions/README.md)，一条一个文件；特性档案“决策”一节列出相关文件 | 文件名 | 做决定的会话；来源如实标注 |
| 进度 | [PLAN.md](../PLAN.md) 只放里程碑勾选，写需求编号或特性 ID，不复述设计 | — | 各会话 |

**不再允许的写法**：在计划、任务卡、决策、宪章里重新描述某个特性的意图或设计。需要时写一句要点并链接到特性档案。

## 3. 特性档案

每个特性一个目录 `docs/features/<特性 ID>/`，入口是 `README.md`。模板见 [feature-dossier-template.md](feature-dossier-template.md)。必备小节：

1. **意图**：为什么做、为谁做、服务宪章哪一条、不做什么。
2. **需求**：表格，每行一个 `REQ-<特性>-NN`，写验收标准、状态（提出 / 已确认 / 已实现 / 已发布 / 已废弃）、对应用例编号、引入版本。
3. **设计**：结构、接口、状态、数据；引用的共享契约逐条列出。
4. **实现入口**：主要代码路径、配置项、接口路径。
5. **质量**：用例与证据位置；已知缺口。
6. **版本历史**：哪个版本引入、改过什么（由版本说明汇总）。
7. **决策**：相关决策文件列表。
8. **来源**：迁移时由哪些老文件并入（见第 7 节）。

档案目录下可以有子文档（例如 `protocol.md`、`ui.md`），但都必须从 `README.md` 链接，不能单独作为入口。

## 4. 登记表：`docs/testing/features.json`

沿用现有登记表，每个特性补几个字段，让链条可以被机器检查。现有字段（`id`、`document`、`sources`、`coverage`、`cases`、`runtime_cases`、`note`）保持不变。

| 新字段 | 含义 | 例子 |
|---|---|---|
| `dossier` | 特性档案路径 | `"docs/features/world-adapter/README.md"` |
| `status` | 设计中 / 开发中 / 已发布 / 已废弃 | `"开发中"` |
| `requirements` | 需求列表：`id`、`title`、`status`、`cases`、`since` | `[{"id": "REQ-world-adapter-01", "title": "绑定远程 DES 世界", "status": "已实现", "cases": ["RT-WADES-01"], "since": ""}]` |
| `contracts` | 引用的共享契约 | `["identity-and-approval", "state-and-cancellation"]` |
| `decisions` | 相关决策文件名 | `["2026-11-21-industrial-capabilities-in-desktop"]` |

校验（扩展 `web/verification/check-map.mjs`，随 `npm run test:map` 运行）：

- `dossier` 文件存在；档案里出现的 `REQ-` 编号与登记表一致；
- 每条状态为“已确认”及以后的需求至少挂一个存在的用例编号；
- `contracts`、`decisions` 指向的文件存在；
- `status` 为“已发布”的需求必须有 `since` 版本号，且该版本的版本说明存在。

## 5. 一次改动怎么走

| 改动类型 | 必须做的 |
|---|---|
| **新需求或行为变化** | ① 在特性档案“需求”加一行（状态“提出”），用户确认后改“已确认”；② 改档案“设计”一节；触及契约先改契约（须批准）；③ 在 CASES 写用例，看到业务断言 Red；④ 实现到 Green；⑤ 更新登记表与档案状态；⑥ PR 正文写需求编号和“设计一致性” |
| **修 bug（不改需求）** | PR 写所属需求编号或用例编号；附回归测试；设计不变时不改档案 |
| **纯重构** | PR 写所属特性；不改需求和用例断言 |
| **新特性** | 先建档案目录并在 DESIGN 第 0.3 节登记一行，写明为宪章哪一条服务；再按“新需求”走 |
| **做了取舍** | 按 [决策写法](../decisions/README.md) 记一条，档案“决策”一节加链接 |

PR 正文“关联”一节写：特性 ID、需求编号、用例编号。

## 6. 版本

- 版本号用语义化版本 `vX.Y.Z`，在 `master` 上打 tag，由用户执行。
- **何时发版**：里程碑准出时（例如 World Adapter M1、AI 桌面 C2），或用户指定时。
- 每个版本有一份 `docs/releases/vX.Y.Z.md`（模板见 [release-template.md](release-template.md)）：包含的特性和需求、用例与证据状态、已知问题、升级与回滚说明。主体由登记表生成，人工补充说明。
- 特性档案的“版本历史”和登记表的 `since` 随发版更新。
- 已有 tag：`v1.0.0`（2026-11-17 论文实验版本，指向 `0d0133c`）。建议在开始迁移前打一个基线 tag，作为新规范下的第一个版本（版本号待用户定）。

## 7. 老文件的迁移规则

详细步骤见 [migration.md](migration.md)。要点：

- **一个特性一个 PR**，先试点 World Adapter，再并行迁移其余特性。
- 每篇老文件归入四类之一：**并入档案**（内容进入档案某节）、**拆分**（按特性拆到多个档案）、**保留为子文档**（太长，作为档案子文档）、**归档**（原型、调研、过时内容，移到探索区或标“历史”）。
- 老文件**不直接删除**：改为一段跳转说明（“本文已并入 …，以下为历史版本”），外部链接不断。
- 档案“来源”一节列出“老文件 → 新位置”对照表。
- 热点文件（`CASES.md`、`PLAN.md`、`features.json`）只做最小改动：补字段、换链接，不重排。
- 迁移只搬运和整理，不改需求含义；发现矛盾时记入档案“待决定”，由用户裁定。

## 8. 交接

团队在检查点交接、或会话要结束时，用 [handoff-template.md](handoff-template.md) 写交接说明，放在该分支草稿 PR 的正文里。新会话从交接说明和特性档案开始，不靠对话记忆。

## 9. 机器检查（规范批准后逐步加入）

| 检查 | 在哪里 | 何时加入 |
|---|---|---|
| 档案必备小节、新档案已在 DESIGN 第 0.3 节登记 | `tools/ci/doc_lint.py` | 试点完成后（先警告） |
| 登记表新字段与需求 ↔ 用例链接 | `web/verification/check-map.mjs`（`npm run test:map`） | 试点时 |
| PR 正文写特性 ID 和需求编号 | `tools/ci/doc_lint.py` | 试点完成后（先警告） |
| 发版时版本说明存在、需求 `since` 一致 | 发版脚本或 CI | 首次按新规范发版时 |

所有新检查都先警告、约一周后再阻断，和 [decisions/2026-11-21-doc-rules-enforcement](../decisions/2026-11-21-doc-rules-enforcement.md) 一致。`tools/ci/` 与 `.github/` 属 L3，每次改动须用户批准。
