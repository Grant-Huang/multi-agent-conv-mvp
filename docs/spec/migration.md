# 老文件迁移指南

把现有文档整理进特性档案的步骤。规则见 [研发对齐规范](README.md) 第 7 节。**一个特性一个 PR**，先试点再推广。

## 1. 开始前

1. 确认负责该特性的团队已到检查点：进行中的分支已合并，或已在草稿 PR 写好 [交接说明](handoff-template.md)。
2. 从最新 `master` 开分支。
3. 列出该特性的全部相关文件：`features.json` 中该特性的 `document`、`sources`；DESIGN 第 0.3 节该行的“权威设计”“计划与进度”；在 `docs/` 中搜索特性名和代码路径。

## 2. 逐篇分类

为每篇老文件填一行，写进档案的“来源”一节：

| 分类 | 什么时候用 | 怎么处理老文件 |
|---|---|---|
| 并入 | 内容属于本特性的意图、需求、设计、质量 | 内容移入档案对应小节；老文件改为跳转说明 |
| 拆分 | 一篇文件讲了多个特性 | 各部分移入对应档案；老文件改为跳转说明并列出去向 |
| 保留为子文档 | 内容属于本特性但太长（如协议细节） | 移到 `docs/features/<特性>/` 下，档案链接它；老位置留跳转说明 |
| 归档 | 原型、调研、过时方案、已完成的任务卡 | 开头标“历史”或“探索区”并写一句结论；不再作为依据 |

计划和任务卡（如 `WA_M1_TASKS.md`）：已完成的归档；进行中的保留在原位，只把其中的需求和设计描述换成指向档案的链接。

## 3. 写档案

1. 按 [特性档案模板](feature-dossier-template.md) 建 `docs/features/<特性>/README.md`。
2. **意图**：从设计文档、决策、宪章中提炼，注明来源。
3. **需求**：从设计文档的验收条款、CASES 的用例、任务卡的准出条件中整理出 `REQ-<特性>-NN`；每条挂上已有用例编号。原文没有明确验收标准的，状态写“提出”，列入“待决定”。
4. **设计**：搬运并去重；跨特性的内容改为引用共享契约。
5. 其余小节按模板填写。

## 4. 改登记表和索引

- `features.json`：该特性补 `dossier`、`status`、`requirements`、`contracts`、`decisions` 字段；其他字段不动。
- `DESIGN.md` 第 0.3 节：该行“权威设计”改为档案路径。
- 宪章、决策、计划中对老文件的链接：改为指向档案（同一个 PR 内完成）。

## 5. 检查

- 链接检查：`python3 tools/ci/doc_lint.py --base origin/master` 无 `broken-link`。
- `cd web && npm run test:map` 通过（登记表校验扩展后，同时检查需求与用例的链接）。
- 对照“来源”表，确认每篇老文件都有去向、没有内容丢失；发现矛盾记入档案“待决定”，不自行裁定。
- PR 正文附“老文件 → 新位置”对照表，由用户或评审确认后合并。

## 6. 不做的事

- 不删除老文件（只改为跳转说明）。
- 不改需求含义、不改用例断言。
- 不在同一个 PR 里迁移多个特性。
- 不重排 `CASES.md`、`PLAN.md`、`features.json`。
