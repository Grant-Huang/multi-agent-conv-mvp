# 决策记录

本项目所有决策统一记在这里，用简单的话写清楚：**定了什么、为什么、落在哪里、怎么验证**。目的是方便以后回顾，出问题时也能查到"当初为什么这样做"。

## 怎么记

- **按主题分节**：每条决策有固定编号，格式为"主题-序号"，例如 `DES-15`，便于在提交说明、PR、评论中引用。
- **每条写四项**：
  - 决定：定了什么；
  - 原因：为什么这样定，有数据就写数据；
  - 落在哪里：对应的代码、文档、PR 或提交；
  - 验证：用哪个测试或检查确认它一直成立，没有就写"无"。
- **只追加，不改旧条目**：推翻旧决策时新写一条，写明"取代 XXX-NN"，并在旧条目末尾补一句"已被 XXX-NN 取代"。
- **未定的事项放在主题末尾的"待决定"**，定下来后移成正式条目。
- **详细设计不写在这里**，只放链接。

## 车间仿真（DES）

用例编号见 [CASES.md](testing/CASES.md)，证据在 `docs/testing/evidence/mom-des-*.md`。

### 名词速查

| 说法 | 意思 |
|---|---|
| DES | 离散事件仿真。这里指"模拟车间"：按物理规律模拟设备磨损、振动、质量和订单，产生报警事件 |
| P0 / 固定剧本 | 论文里的三事件场景：08:17 插单 500 件、08:23 CNC-XX 振动报警、08:31 Line-B 的 CPK 降到 1.1 |
| 场景模式 | 让随机事件满足某种结构的约束，例如并发簇（短时间多个扰动）、诱饵（看着相关其实不相关）、资源竞争 |
| 标准答案 | 仿真内部知道的真实根因和真实关联，只给审核用，agent 看不到 |
| 案例（Case） | MOM 里处理一件事的单元，按（场景、批次、客户、设备）归并事件 |
| 协同事项 | 同一产线短时间内多个报警时，合并成一个"产线级"的案例统一决策 |
| A/B/C 方案 | A 继续用报警设备；B 做完本批再停机维修；C 立即停机维修 |
| Red → Green | 先写会失败的测试（Red），确认后再写实现让它通过（Green） |
| 模拟工厂 | 阶段⑤a 起，仿真拆成独立服务 `an-des`，可以通过 MCP 挂载 |

### 一、方向与范围（2026-11-17）

**DES-01 自己写仿真，不直接集成开源项目**
- 决定：在现有 MOM 仿真的基础上，用 Rust 自己写离散事件仿真；借鉴 prodsys 等项目的建模方式，但不引入它们的代码。仿真同时用于产品演示和论文实验，要求完整闭环：事件 → agent 处理 → 人审批 → 执行 → 仿真世界随之改变 → 核验。
- 落在哪里：设计见 DES_CLOSED_LOOP.md。
- 验证：闭环由 RT-DES-08～11 覆盖。

**DES-02 不影响另一条实验线**
- 原因：另一条线在做机制验证实验，可能用到原有的"脚本式事件队列"。
- 决定：DES 用独立入口 `create_des_simulation`，不改脚本仿真的接口和行为。
- 验证：RT-DES-05（DES 不影响脚本仿真）；原有脚本仿真测试一行未改，全部通过。

**DES-03 测试的目的**
- 决定：事件时间不固定，让多个随机、混合的事件同时出现，用来检查系统和 agent 的响应机制，以及人与 agent 的协作机制。P0 只是其中一个例子，不是最终目的。处理结果需要审核：先由 AI 审核，再报告给人确认。
- 验证：RT-DES-16（各场景模式满足约束）、RT-DES-12～14（审核）。

**DES-04 直接用 master 上的 MOM 服务和界面**
- 决定：仿真能力要能在人与 agent 的对话中被调用和报告，将来也可以作为制造桌面（人在环）的提示来源。
- 落在哪里：`crates/server/src/mom_sim.rs`（HTTP 接口）。
- 验证：HTTP-DES-01～04。

**DES-05 五个基础决策（D1～D5，都按推荐）**
- D1：处理方案给 A/B/C 多个选项，由人选择。验证：RT-DES-06、RT-DES-08。
- D2：执行之后，同一来源的复检数据算"核验证据"，不当作新问题。验证：RT-DES-09。
- D3：批量实验里的审批由"模拟审批人"按策略完成。验证：RT-DES-15。
- D4：要有"传统 MOM"作对照组，用来比较 AI-Native 的效果。验证：RT-DES-15。
- D5：按阶段推进：①开环内核 → ②工具读取与 what-if → ③闭环执行 → ④审核与批量实验 → ⑤界面。

**DES-06 事件要符合规律，不能纯随机**
- 决定：
  - 设备退化：主轴磨损用 Gamma 过程，刀具寿命用对数正态分布，振动分区按 ISO 20816-3。
  - 质量：用模型 Cpk。
  - 根因由因果机制推出，所以标准答案是"算出来的"，不是"标上去的"。
  - 各项参数都是建模假设，已登记到 Mock 台账 M27、M28。
- 落在哪里：`crates/des/src/physics.rs`、`scenario.rs`。
- 验证：RT-DES-01～03、16、17。

**DES-07 案例归并与事件种类（D6、D7）**
- D6：保留原有的案例归并规则，相关案例之间加关联链接。验证：RT-DES-18。
- D7：阶段①只用现有的三类事件（插单、振动、质量）。

**DES-08 两项变更已批准（A1、A2）**
- A1：Mock 台账新增 M27、M28，台账条数的测试断言从 24 改为 26。
- A2：新增仿真相关的 HTTP 接口和快照字段。

**DES-09 AI 审核用哪个模型（M1、M2）**
- M1：新增可选配置 `[models].mom_reviewer`。没配时用 MOM 主模型 `[llm].model`；两者都没有时只做规则检查。
- M2：审核模型和被审的主模型相同时也允许，但报告上要标注"非独立审核"。原因：模型容易偏爱自己生成的内容。
- 验证：RT-DES-19。

**DES-10 工作流程**
- 决定：每个阶段先写用例和失败测试，用户确认后再实现；修改已定稿的断言必须先经用户同意。
- 验证：每个阶段的证据文件里都有 Red → Green 记录。

### 二、阶段②～④

**DES-11 推送顺序（阶段③）**
- 决定：先合并 #81（阶段②），再推送阶段③。

**DES-12 取消"每案例每小时观测数上限"（阶段④写用例时）**
- 决定：用户同意不做这个限制。

**DES-13 发现局限后，采用 A+B 结合方案（阶段③b）**
- 原因：每种模式各跑 20 个随机种子实测：
  - P0 固定剧本 20/20 进入决策；
  - 并发簇 72 个报警案例只有 4 个进入决策；
  - 其他模式都是 0。

  原因是原模板要求一个案例同时收到三类事件，而随机事件大多分散在不同案例里。
- 决定：
  - A：按报警类型选模板，分为只有振动、只有质量、两者都有三种；
  - B：同一产线 60 分钟内有 2 个及以上案例时，建立协同事项，在事项上统一决策。成员案例只做诊断；关闭事项时成员一起关闭。
- 用户确认的四点：
  - 事项复用案例结构；
  - 触发条件为同线、60 分钟、至少 2 个；
  - A/B/C 方案作用于整组报警设备；
  - ③b 先于阶段④实现。
- 落在哪里：设计 §6.8；`crates/runtime/src/mom/des/coordination.rs`。
- 验证：RT-DES-25～29。

**DES-14 审查问题 R-20261117-M1、L1 在本分支修**
- 问题：
  - M1：仿真重放太频繁，性能差；
  - L1：HTTP 接口阻塞了异步线程。
- 决定：在本分支修复（提交 a9b3d45）；关闭原修复 PR #84、#85，因为它们基于旧代码、已经冲突。
- 验证：RT-DES-22、22b、23、24。

**DES-15 已请人决策的案例怎么加入协同事项：方案 A**
- 原因：单个报警案例收到报警后会立刻请人决策。几分钟后同一产线又来报警时，它已经在等人决策了。按原测试"成员从不请人决策"，这类案例进不了事项，协同事项几乎形成不了：资源竞争模式 seed 1–10 中为 0/10。
- 候选方案：
  - A：撤回请求后加入；
  - B：每个报警先等几分钟再决策；
  - C：维持原规则，放宽测试。
- 决定：采用 A。已请人决策、但还没执行的案例，加入事项时撤回原决策请求（记 `DecisionWithdrawn` 事件），旧审批作废，之后只做诊断。用户批准修改 RT-DES-26 的这条断言。效果：seed 1–10 中有 8 个能形成"多设备 + 有推荐方案"的事项。
- 验证：RT-DES-26、27。

**DES-16 ③b 实现中的修订**
- 决定：
  - P0 固定剧本不启用新机制，保证论文场景的行为逐事件不变。
  - 计划模型中，设备维修完会恢复生产。原来修完就不再参与生产，导致多台设备同时报警时所有方案都赶不上交期。
  - 已报告的报警在维修或检验之前一直算"报警中"，即使读数暂时回落。
  - 事项排产时，取交期未到、最早到期的插单；没有插单时按 500 件、8 小时估算。
- 验证：RT-DES-28（P0 不变）、RT-DES-27。

**DES-17 阶段④批量实验的处理**
- 决定：
  - 传统策略要经过 3 次部门交接，决策时证据常常已经过期，引擎会拒绝审批，这是合理的安全检查。处理办法：证据过期时先刷新计划，再按新方案决策；刷新后已无可行方案的计为"延误"，并单独统计在 `expired_decisions` 列。这正是决策延误代价的数据。
  - 模拟审批人沿用夹具审批人 `supervisor`，因为引擎只认它。
  - 没有配置审核模型时，AI 审核接口只返回规则结果，并标注"AI 审核不可用"。
- 验证：RT-DES-15、HTTP-DES-04。

### 三、阶段⑤a：独立的模拟工厂（MCP）

**DES-18 把仿真做成可挂载的独立引擎**（2026-11-17）

**DES-20 工具名用下划线，不用点号**（2026-11-18，用户确认）
- 决定：工具名写成 `equipment_status` 这样，不写成 `equipment.status`。
- 原因：MCP 规范允许点号，但 Anthropic 和 OpenAI 的工具名规则都是 `^[a-zA-Z0-9_-]{1,64}$`，带点号的名字会被拒绝。为了方便其他系统挂载，取两者都能接受的写法。
- 验证：RT-DESF-01 检查每个工具名都匹配 `^[a-z][a-z0-9_]{0,63}$`。

### 排查提示（踩过的坑）

| 现象 | 原因 | 处理 |
|---|---|---|
| CI 的 change-policy 报"改动过大"，但 PR 描述里明明有"大改动说明" | CI 读的是推送那一刻的 PR 描述；编辑描述不会触发 CI；在 Actions 里重跑也沿用原来的描述 | 下次有真实内容的推送时才会按新描述判断；不要推空提交 |
| CI 的 rust 作业只显示部分失败用例 | CI 跑测试没加 `--no-fail-fast`，前面一失败就停了 | 本地加 `--no-fail-fast` 看全部结果 |
| 仿真刚开始就报警，或刀具报警太频繁 | 早期没有"开局受控"假设和预防性换刀 | 已加入开局受控假设、对数正态刀具寿命和预防性换刀 |
| 用滚动窗口估算的 Cpk 产生假报警 | 估算值波动大 | 改用模型 Cpk（设计 §4.2 修订） |
| 执行维修后查询结果和预期不一致 | 维修可能在场景时长之后才结束 | 仿真会继续推演到查询时刻（RT-DES-08） |
| 本地编译报磁盘满 | 构建缓存（target）可达 25 GB | 运行 `cargo clean`；本地检查可加 `CARGO_PROFILE_DEV_DEBUG=0` 去掉调试信息（不影响测试行为，没写进仓库配置） |
| 批量实验里传统策略没有决策 | 交接延迟让证据过期，刷新计划后已无可行方案 | 这是预期结果，计入 `late` 和 `expired_decisions` |
| P0 场景的行为和以前不一样 | 新机制误作用到 P0 | P0（`Pattern::Script`）的事件不带 `simulation` 标记，不启用报警模板和协同事项；RT-DES-28 保护 |
| AI 审核接口返回 "no reviewer configured; rules only" | 真实审核模型还没接入，`mom_reviewer` 配置目前不生效 | 见"待决定"中的 R-20261118-L2 |

## D-009

**DLP 接口 D1 定稿（9 项）**

- 日期 / 状态：2026-11-18 / 已采纳（AgentNexus 侧确认）
- 决定：
  1. 三个工具的返回统一为 `{api_version, status, data, error}`，并提供结构化返回和格式说明（output schema）。
  2. `task_id` 由编排器提供，模型碰不到。
  3. 通道只能是 `email / slack / external_api / file_upload / mcp / agent`。新增 `agent`，用于“发给外部助手”。
  4. `vault_ref` 改名为 `request_id`，每次都返回。
  5. **`egress_commit`（把审批结果和实际发送的内容绑定）这次不做。** AG.5 由 Rust 侧用一次性凭证保证“展示的内容就是发送的内容”，强制拦截时再加。

  7. 单次内容上限 256 KB，超出就拦截。
  8. 返回里带接口版本号 `1.0`。
  9. Rust 侧按格式说明校验返回，校验不过就当作失败，不外发。
- 为什么：统一格式、方便校验；把可信信息（身份、任务）留在宿主手里。
- 影响：和最早的草案（`docs/dlp/CONTRACT.md`）不兼容，草案已标注“已被取代”。
- 怎么验证：`tests/test_d1_interface.py`；Rust 侧 RT-EGR-06（返回格式不对时不外发）。

## D-015

**识别前就拦下的数据不计入识别准确率**

- 日期 / 状态：2026-11-18 / 已采纳
- 背景：目的地没登记的请求会被直接拦截，根本不做识别。旧的评测脚本仍把这些请求里的实体算作“漏识别”，让识别率看起来偏低（开发集中有 76 个实体是这样被误算的）。
- 决定：这类请求（目的地未登记、通道不合法、内容超限等）不计入实体识别指标，仍然计入决策准确率。报告里单独列出条数。
- 为什么：让识别率只反映识别能力，不被其他原因干扰。
- 影响：之前报告的 1000 条实体指标偏低，以修正后的数字为准。
- 怎么验证：`tests/test_benchmark_metrics.py`
- 相关：`bench/run_benchmark.py`

## D-016

**还原后的内容能否写进文件；写代码类内容是否只拦密钥**

- 日期 / 状态：2026-11-18 / **待决定**（需要用户拍板）
- 背景：AG.5 侧早先的草案（`docs/dlp/CONTRACT.md`）写了两条“已确认原则”，与当前实现不一致：

  - 第 2 条：增加按用途（例如 `coding`）区分的策略，只拦凭证，不替换标识符。
- 影响：功能默认关闭，所以目前不影响任何行为；开启 `enforce` 前需要定下来。
- 相关：`docs/dlp/CONTRACT.md` 顶部说明
