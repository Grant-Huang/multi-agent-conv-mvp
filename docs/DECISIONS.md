# 设计决策记录

这里用大白话记下"为什么这样做"，方便以后回顾和排查问题。每条包括：

- **定了什么**
- **为什么**
- **没选什么**：考虑过但放弃的做法
- **出问题时先看哪里**

条目按时间倒序排列，新的在上面。决策变了就加一条新的，旧条目标为"已被 #编号 取代"，不删。

细节以 `docs/PLAN.md`、`docs/DESIGN.md` 和各证据文件为准，这里只写结论和理由。

## #9 握手检测：进程一启动就退出时，要能看到它的错误输出（2026-11-18，修复方案待批准）

- **现象**：缺 node 的助手偶尔会被报成"握手失败"，而不是"缺少运行需要的程序"。CI 上出现过一次。本地 400 次检测里有 5～15 次分错。
- **原因**：助手打印"找不到 node"后立刻退出。这时我们正往它的输入里写握手请求，会遇到"管道已断开"（Broken pipe）。这个报错有时比"进程退出 + 错误输出"先到，我们就按没有错误输出来分类了。和 ACP 库的版本无关：退回 5.0.0 也一样。
- **试过但无效**：用库的回调自己留一份错误输出。出错返回时，库往往还没读到错误输出，连接一结束，读取也跟着停了，事后再等也拿不到。
- **定了什么**：待批准。拟改为自己启动子进程、自己读错误输出，见 PLAN 和对话中的方案。
- **出问题时先看哪里**：回归用例 RT-AGCAT-10（`crates/agents/tests/acp_probe.rs`），8 个并发检测、连续 50 轮。

## #8 AG.5 第 3、4 层这次先不做的两件事（2026-11-18）

- **定了什么**：帮手给出的"修改配置请求"这次不转成确认卡，只显示文字；也不支持从对话里发起排查、把结论写回会话，只在「助手」页签里用。
- **为什么**：第 4 层是第一次真正把本机内容发出去。先把"预览、同意、发送、还原、撤销"这条路做扎实，范围越小，越容易查清楚。
- **以后要做时**：修改请求必须走现有的提议校验和确认卡；含 Token 的修改请求一律视为不合格（Token 还原后的值不能写进配置）。

## #7 没有配置 DLP 时，第 3 层诊断包照样显示（2026-11-18）

- **定了什么**：诊断包经过本机的确定性处理后照样显示，并注明"未经外发脱敏检查"。确定性处理是指：家目录换成 `~`，环境变量只留名字，用户名和主机名替换掉。第 4 层（发给外部助手）则必须配置了 DLP 才能用。
- **为什么**：第 3 层是系统不往外发、由用户自己决定复制给谁；第 4 层是系统替用户发出去，必须有 DLP 把关。
- **出问题时先看哪里**：诊断包里出现了不该有的个人信息，先看 Rust 侧的确定性处理是否漏了哪一类，再看是否配置了 DLP。

## #6 D1 外发脱敏接口定稿（2026-11-18）

- **定了什么**：AgentNexus 调用用户自己写的 `tools/dlp-egress` 工具，接口见 `docs/dlp/CONTRACT.md`。其中：
  - 9 项改动全部采纳，包括统一返回格式、`task_id` 由我们给、结构化返回加 schema 校验、载荷上限 256 KB 等；
  - 补了两处缺口：一是新增用户名、主机名、IP、路径中的个人部分这几类实体；二是写代码类的外发只拦密钥、不做替换。
- **为什么**：
  - **DLP 工具单独配置（`[dlp]`），不放进普通 MCP 工具里**：还原工具能把占位符变回原文。如果模型能调用它，被注入的内容就可能借它把敏感信息取回去。单独配置能从源头保证模型看不到这三个工具。
  - **出任何问题都不发**：配置缺失、超时、返回格式不对、版本不对，统统当作"不能发"。宁可不发，也不裸发。
  - **暂不做 commit 接口**：我们自己保证"给用户看的就是要发的"。同意凭证只能用一次，并绑定内容摘要；发送时用服务端存的那份，不接受界面传回来的内容。
  - **在工具修好嵌套 JSON 漏检之前只发纯文本**：避免撞上已知漏洞（代码审查 R-20261118-H1）。
- **没选什么**：让 Agent 自己调用 DLP。Agent 可能被注入，不能让它决定"发不发、还原不还原"。
- **出问题时先看哪里**：日志事件 `egress.evaluated`，里面有决定、原因代码和各类实体的计数，不含原文。

## #5 外发脱敏按用途区分处理（2026-11-17）

- **定了什么**：
  - 排查、问答类：把个人信息换成可还原的占位符。
  - 写代码类：只拦密钥，不做替换。
  - 还原只用于"给人看"的内容，不用于写进文件或仓库的内容。
- **为什么**：写代码时如果把名字换成占位符，帮手写回来的代码就带着占位符，会坏掉。给人看的内容还原了才看得懂；写进文件的内容如果还原，就绕过了把关。
- **边界**：这是配合式的，只有主动调用 DLP 的路径才会脱敏。外部助手自己读文件、自己发给它的模型服务，我们看不到也管不到。强制拦截放到 D5 再设计。

## #4 助手排查分四层，前两层完全在本机（2026-11-17）

- **定了什么**：
  - 第 1 层：已知问题规则库，确定性判断，不调用模型。
  - 第 2 层：本机只读体检。只运行写死的命令（登录 shell 打印 PATH、`node --version`），每条 5 秒超时，结束时清理整个进程组。凭证文件只看在不在，绝不读取内容。
  - 第 3 层：诊断包，交给用户自己复制。
  - 第 4 层：发给另一个助手帮忙查，每次都先完整预览、逐次同意。
- **为什么**：大部分接入失败是"没装、没登录、PATH 不对、Node 版本低"这类固定原因，规则就能答，又快又不外发。只有规则答不了的，才考虑往外发，而且每次让用户看清楚、点同意。
- **没选什么**：
  - 直接让模型读错误输出来诊断：会外发、慢，而且说不准。
  - "以后都同意"的选项：一次同意不能代替以后每次的判断。
- **出问题时先看哪里**：
  - 规则没命中：日志 `agent.diagnose_unmatched`，只记分类和错误输出长度。
  - 体检卡住：检查是否走了 5 秒超时。用例 RT-AGDIAG-03 覆盖了这种情况。

## #3 在对话里管理助手的开关默认关闭（2026-11-17）

- **定了什么**：`[conversation] agent_management` 默认关闭。评测达到 96%（90 条最多错 3 条），并且原有路由评测不下降，才考虑默认打开。
- **为什么**：打开后，前台判断的输出格式会多出"管理助手"这一类，可能影响所有对话的判断准确率。
- **现状**：第二轮评测 83.3%，没有达标。失败原因的拆分见 `evals/ROUND3_GUIDE.md` 的背景一节。
- **出问题时先看哪里**：关掉这个开关就恢复原来的行为。

## #2 某个角色没有可用助手时，不改派给别的角色（2026-11-16）

- **定了什么**：写代码的助手全停了，任务也不会转给通用助手。由主助手用普通用户能看懂的话说明情况，错误码放在最后的括号里。
- **为什么**：不同角色的权限和能力不一样，悄悄改派可能让任务在不合适的环境里执行。说清楚，让用户自己决定。

## #1 接入助手：确定性工具 + 人工批准 + 托管文件（2026-11-16）

- **定了什么**：
  - 模型只负责理解用户想做什么。
  - 实际修改由写死的代码完成：先生成提议，用户确认后凭一次性凭证生效。
  - 修改写进单独的 `agents.managed.toml`，保留 10 个历史版本，可以撤销。
  - `config.toml` 永远优先。
  - 环境变量只允许写成 `${VAR}` 引用，不存明文。
- **为什么**：让模型直接改配置文件，一句被注入的话就可能改掉权限。确定性代码加上人工确认，出错可以撤销，也能审计。
- **没选什么**：让一个"主 agent"自己修改本机配置去发现和配置其他 agent。
- **出问题时先看哪里**：
  - 「助手」页签里的"撤销上一次修改"；
  - 托管文件损坏时，启动不受影响，也不会被覆盖。日志事件为 `agent.managed_invalid`。
