## 1. 目标

1. 产品主线不偏：有一份很少变化的产品宪章，新主线、新特性开工前要说明为宪章里的哪个目标服务。
2. 设计一致：跨特性共用的约定（身份与审批、状态与取消、事件与追踪）只写一次，各特性引用，不各写一套。
3. 保持柔性：只有宪章和共享契约是“改动要你确认”的刚性层；特性内部设计、实验走普通 PR。
4. 不给正在推进的团队添乱：先加新文件，少动热点文件；新规则只管新内容；规则先警告、后强制。

## 4. P5 方案（L3，待用户批准；获批前不改这些文件）

涉及 `AGENTS.md`、`.github/pull_request_template.md`、`.github/workflows/ci.yml`、`tools/ci/`，都属于 L3：先说明理由，用户批准后才改，合并须 CODEOWNERS 批准。

**理由**：`AGENTS.md` 是所有 AI 编码 agent 每次开工都读的入口，新的阅读顺序和决策写法只有写进去才会被一直遵守；PR 模板和 CI 是唯一能机械地守住边界的地方。

### 4.1 `AGENTS.md`：两处小改

“开始前”第 1 条改为（原句保留，前面加阅读顺序）：

> 1. 按顺序读：`docs/PRODUCT.md`（产品宪章：做什么、不做什么、不能破的原则）→ `docs/DESIGN.md` 第 0 节（系统全景与产品特性设计索引）→ `docs/contracts/` 中与本任务相关的共享契约 → 本任务所属特性的权威设计（见第 0.3 节）。再读 `docs/PLAN.md`（当前里程碑）；排查问题或改动已有设计前，先看决策记录（`docs/decisions/` 与 `docs/DECISIONS.md`）。

“决策记录”第 1 条改为：

> - 定下来的事记在 `docs/decisions/`，一条一个文件，写法见该目录的 README；`docs/DECISIONS.md` 是 2026-11-21 以前的历史档案，只给旧条目标「已取代」，不再追加新条目。

“修改范围”加一条：

> - 新特性或新主线开工前，先在 `docs/DESIGN.md` 第 0.3 节登记，写明为 `docs/PRODUCT.md` 哪一条服务；改动触及共享契约或宪章时，先出方案、经用户批准。

### 4.2 PR 模板：加一节“设计一致性”

```
## 设计一致性
- 属于哪个特性（DESIGN 第 0.3 节）：
- 是否触及共享契约（docs/contracts/）：否 / 是（哪一份、哪一条）
- 是否偏离产品宪章（docs/PRODUCT.md）：否 / 是（须先有用户确认的决策）
```

后两项答“是”时，`change-policy` 提示需要先出方案。

### 4.3 CI：新增 `tools/ci/doc_lint.py`，先只警告

| 检查 | 范围 | 过渡期 | 之后 |
|---|---|---|---|
| 相对链接和锚点有效 | 本次新增或改动的 `.md` | 警告 | 阻断 |
| `docs/decisions/` 新文件的命名和开头表格（日期、来源、状态） | 新增文件 | 警告 | 阻断 |
| 往 `docs/DECISIONS.md` 追加新编号条目 | 本次 diff | 警告 | 阻断 |
| `DECISIONS.md` 出现重复编号 | 本次新增的编号 | 警告 | 阻断 |
| 新增的设计文档没有在 DESIGN 第 0.3 节登记 | 新增文件 | 警告 | 警告 |
| PR 正文缺“设计一致性”一节 | 非纯测试 PR | 警告 | 警告 |

接入方式：在 `change-policy` 作业里加一步，过渡期用 `continue-on-error`，约一周后去掉。脚本按现有 `tools/ci/*.py` 的写法，带单元测试，用 Python 标准库实现。

### 4.4 风险与回滚

- 风险：规则改为阻断后，还没改用新写法的分支会被拦；过渡期和警告信息就是为了避免这种情况。
- 回滚：三处改动各自独立，单独 revert 即可；CI 检查可先回到“只警告”。
