## 1. 两条原则

1. **并行开发，确定性集成**：待合并 PR 是在制品，集成验证是瓶颈工序。不因某条线有空闲算力就不断开新任务；控制在制品，而不是追求每个 agent 满负荷。测试时**冻结版本、不冻结开发；隔离环境、不隔离协作**。
2. **集成竞争要有协调机制**：多个 PR 各自变绿，合并后可能互相冲突或语义不兼容。合并必须排队、对“最新主干 + 本 PR”的组合做验证，而不是对各自过时的基线。

## 2. 现状与问题（2026-11-26 核对 `master` 的 `a5f9c04` 之后）

| 现象 | 事实 | 后果 |
|---|---|---|
| 每个 PR 都跑全量 | `.github/workflows/ci.yml` 对所有 PR 跑 `cargo fmt`、`clippy`、`cargo test --workspace`、web、python、`security`，纯文档 PR 也一样 | 每个 PR 约 10 分钟以上，CI 成为瓶颈 |
| 高风险改动合并前无 E2E | 浏览器 E2E 只在 `nightly-e2e.yml`（每天 10:30 UTC） | 高风险问题合并后才发现 |
| 合并竞争 | 分支保护要求分支与主干同步（`scripts/enable_branch_protection.sh` 中 `strict: true`） | 每合并一个 PR，其余 PR 都要更新并重跑；2026-11-26 #409 因此重跑两次 |
| 在制品无上限 | 没有规则限制待合并 PR 数量 | 积压越多冲突越多 |
| 平台限制 | 仓库为个人账号下的公开仓库（GitHub 搜索接口 `owner.type = User`）。GitHub 原生 Merge Queue 据助手了解只对组织名下仓库开放（**推断，未能在本环境打开 GitHub 文档核实**） | 先自建简易队列；是否迁到组织另行决定 |

## 3. 在制品控制（P0）

| 规则 | 初值 |
|---|---|
| 每条线同时处于“待合并”（非草稿、未合并）的 PR | 最多 **3** 个 |
| 过渡 | 规则生效时已超限的 PR 不需关闭；超限的线先不开新 PR，把手上的合掉（2026-11-26 统计：全仓非草稿 17 个，其中第 1 线 10 个） |
| 全仓待合并 PR | 只数风险等级 **L1～L3** 的：超过 **12** 个时，各线暂停开新开发任务，转去评审、修复 CI、消除冲突，直到回落到 12 个以下。L0（文档、评测数据）不计入全仓数，因其 CI 分流后很快、绿后由本线自行合并，几乎不占集成资源；但计入每线 3 个 |
| 草稿 PR | 不计入，但草稿超过 3 天未更新的由巡检提醒 |
| 例外 | `severity:high` 缺陷修复、CI 修复、安全修复不受上限约束，PR 正文写明“在制品例外：原因” |

执行：各线开工前自查（`AGENTS.md`“跨线分工”）；派工巡检每 4 小时统计各线与全仓数量并在汇总中提示超限。

## 4. 合并队列与集成 agent（P0 规则、P1 自动化）

### 4.1 合并条件

| 风险等级（以 CI `change-policy` 给出的为准，不自判） | 合并方式 |
|---|---|
| L0 | CI 全绿后**由作者所在线自动合并**（或开启 GitHub auto-merge） |
| L1 | 1 位审查人批准后合并；独立审查身份就绪前由用户批准 |
| L2 | 审查人不是作者；合并前须通过 T2 集成验证（含浏览器 E2E，见第 5 节） |
| L3 | CODEOWNERS（用户）批准；合并前须通过 T2，涉及 CI 的还要跑一次 T3 |

### 4.2 冲突与过期处理（任何线对自己的 PR）

1. 把 master 合进自己的分支（不 rebase、不强推，不动别人的分支）。
2. 冲突消除后重跑提交前自检，等 CI 再次全绿。
3. 冲突涉及 `AGENTS.md`“先停下来问人”中的文件，或需要在两种行为之间取舍的语义冲突：停下来，在 PR 里说明并请第 2 线或用户裁决。

### 4.3 简易合并队列（P1，第 2 线实施）

在原生 Merge Queue 可用前，由**集成 agent**（第 2 线的定时任务或常驻会话）按队列顺序合并：

```
排队条件：非草稿 + 等级允许合并（第 4.1 节）+ CI 全绿 + 已批准（如需）
循环：
  取队首（severity:high 修复优先，其余按进入队列的时间）
  → 若落后主干：合并 master 进 PR 分支 → 等 T2 结果
  → 绿：合并；红：踢出队列并在 PR 留言原因，通知作者所在线
  → 下一个
```

集成 agent 的职责：冲突检测与机械性冲突的修复（如同时改了同一张索引表的不同行）、语义审查（两个 PR 合在一起是否违背共享契约或宪章）、队列状态汇总。它不批准任何 PR，不改 L2/L3 的业务逻辑。

## 5. CI 分层（P0 分流，P3 增量）

| 层 | 触发 | 内容 | 目标耗时 |
|---|---|---|---|
| **T0 本地自检** | agent 推送前 | `AGENTS.md`“提交前自检”；P3 后可只跑受影响 crate 的测试 | 几分钟 |
| **T1 Fast CI** | 每个 PR、每次推送 | 按路径分流：只改文档与评测数据（L0 路径）→ 只跑 `change-policy`、`security`（密钥扫描）；改了 Rust → fmt、clippy、受影响 crate 测试（P3 前为全量）；改了 `web/` → web 作业；改了 Python 工具 → 对应作业 | 5 分钟内 |
| **T2 Integration CI** | 进入合并队列（对“最新主干 + 本 PR”） | workspace 全量测试、web 构建、契约测试；**L2、L3 或带 `full-ci` 标签的 PR 加跑浏览器 E2E（`npm run verify`）** | 15 分钟内 |
| **T3 Full CI** | 每晚定时；L3 改动 CI 时合并前 | 完整 E2E、`cargo audit` / `npm audit`、路由评测；全部通过后打基线 tag | 不限 |

**增量测试的依据**：只用 Cargo workspace 的 crate 依赖图（`cargo metadata`）判断“改了哪个 crate → 测它和依赖它的 crate”；更细粒度的影响分析不可靠，不用。依赖图无法判断时（如改了根 `Cargo.toml`、`config/`、共享夹具）一律跑全量。

## 6. 定时任务分层

| 节奏 | 任务 | 负责 |
|---|---|---|
| 每 4 小时 | 派工巡检（含第 3 节在制品统计）；P1 后集成 agent 处理队列 | 巡检定时任务；第 2 线 |
| 每天 | T3 夜间全量 → 通过则打基线 tag `baseline-YYYYMMDD`；每晚评审 agent 增量审查 | 第 2 线；评审 agent |
| 每周 | 守护者体验地图走查；第 6 线真实环境走查（基于最新基线 tag）；围栏周检 | 守护者定时任务；第 6 线；第 2 线 |
| 每两周 / 每月 | 第 6 线长程测试 24 / 72 小时、升级演练（基于基线 tag）；七层围栏月检 | 第 6 线；第 2 线 |

## 7. 冻结版本，不冻结开发

- 测试一律基于**基线 tag**（最近一次 T3 全绿的提交），不基于移动中的 master。第 6 线长程测试、第 2 线验收复跑、守护者走查都在报告里写明所用 tag。
- 基线期间发现的问题按 tag 复现，再判定是否在 master 上仍存在。
- 开发照常合并进 master，不因测试而冻结。

## 8. 变更范围声明（P2）

- 派工 Issue 与 PR 正文增加“变更范围”：预计修改的 crate 或目录、触及的共享契约、依赖哪些未合并的 PR。
- 第 2 线据此排序与预判冲突：两个 PR 声明的范围重叠时，后开工的一方先等待或在 Issue 上协调。
- P3 后由 CI 比对声明与实际改动，超出声明时提示。

## 9. 分阶段实施

| 阶段 | 内容 | 实施 | 风险等级 |
|---|---|---|---|
| P0 | 在制品上限与 L0 自动合并、冲突自行处理写入 `AGENTS.md`；巡检加在制品统计；`ci.yml` 按路径分流（T1） | 规则：本设计 PR；CI：第 2 线 | L3 |
| P1 | 集成 agent 与简易合并队列；夜间全绿打基线 tag | 第 2 线 | L3 |
| P2 | 变更范围声明进入派工模板与 PR 模板 | 审查会话改派工模板；第 2 线改 PR 模板 | L0 / L3 |
| P3 | 基于 crate 依赖图的增量测试；L2/L3 合并前 E2E（T2） | 第 2 线 | L3 |
