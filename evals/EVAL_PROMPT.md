# 路由评测说明（交给本地 Claude 执行）

把下面「评测 prompt」整段发给本地的 Claude Code，它会按步骤跑评测并写出报告。
跑之前请先把 `<…>` 里的内容换成实际值。

---

## 评测 prompt

```text
请对 AgentNexus 的"前台判断 + 路由"做一次评测，评测对象是新模型 <模型名称，例如 Qwen3.x-30B-A3B Q5_K_M>。
评测方法和要求见 evals/EVAL_PROMPT.md，请先完整阅读该文件（特别是「标注口径」和「注意事项」两节），然后按其中的「执行步骤」进行。

背景：
- 上一次评测（旧提示词 + 27B Q5 模型，evals/routing-v1.jsonl，26 条）：动作准确率 76.9%，角色 62.5%，类别 50.0%，
  格式重试 0，出错 0，延迟 P50 35.1s / P95 84.3s（当时直接回答的内容和判断一起生成，所以很慢）。
- 这次的代码改动：提示词改为按优先级的硬规则、Turn Controller 能看到工具清单、说明了默认代码仓库；
  判断和回答拆成两步（判断只输出动作）；新增审查模式配置 [conversation] review_requests。

要求：
- 评测过程中不要修改任何代码、提示词和数据集；发现问题只记录、只提建议。
- 怀疑标注本身有问题时，单独列出，不要计入模型错误的归因；「标注口径」一节中列为"待确认"的样本，请在报告里单独给出模型的实际表现。
- 评测时 [llm] temperature 设为 0；如果模型带思考（thinking）模式，在报告里注明是开还是关。
- 报告写到 evals/reports/<日期>-<模型简称>.md，最后在对话里给我一段 10 行以内的结论。
```

## 执行步骤

### 0. 记录环境（写进报告开头）

- 模型文件名和量化方式；llama.cpp 版本（`llama-server --version`）和启动参数（上下文长度、`--parallel`、是否 `--jinja`）
- `config.toml` 中的 `[llm]`（`base_url`、`model`、`temperature`、`structured_mode`、`max_retries`）和 `[models]`
- 机器型号、内存
- 代码版本：`git log --oneline -1`

评测时把 `[llm] temperature` 设为 `0`（默认是 0.2），减少随机性带来的波动；评测完记得改回来。如果因故保持 0.2，请在报告里注明，并更重视第 4 步的稳定性结果。

另外记录：模型是否带思考（thinking）模式、评测时是开还是关（见「注意事项」第 3 条）。

### 1. 冒烟测试

```bash
curl -s http://127.0.0.1:8098/v1/models
cargo run --release --bin an-eval -- config.toml evals/routing.jsonl --limit 3 --label smoke
```

3 条都能跑完（不论对错）再继续。这一步同时起到**预热**作用：模型刚加载时第一次请求明显偏慢，预热后再跑正式评测，延迟数据才准确。如果出现 `E_LLM_HTTP` 或格式重试很多，先排查 `structured_mode`（见 README「小模型调优建议」）。

### 2. 与上次对比（同一套 26 条）

```bash
cargo run --release --bin an-eval -- config.toml evals/routing-v1.jsonl --label <模型简称>-v1set
```

注意：
- 这次的提示词也改了，所以和上次的差异 = 模型差异 + 提示词差异，报告里不要把提升全部归给模型。
- v1 集里审查类样本的期望是按 reviewer 模式标的，所以这一步要在 `review_requests = "reviewer"`（默认）下跑。
- **角色、类别准确率的统计口径变了**，和上次的数字不能直接比，见「注意事项」第 1 条。

### 3. 主评测（v2，90 条，三种审查模式各跑一次）

```bash
cargo run --release --bin an-eval -- config.toml evals/routing.jsonl --review-mode reviewer --label <模型简称>
cargo run --release --bin an-eval -- config.toml evals/routing.jsonl --review-mode direct   --label <模型简称>
cargo run --release --bin an-eval -- config.toml evals/routing.jsonl --review-mode auto     --label <模型简称>
```

三种模式只有审查类样本（标签 `review`）的期望不同，其余样本期望相同。

### 4. 稳定性

再跑一次 reviewer 模式，对比两次逐条结果（`evals/results/*.jsonl` 的 `pass` 字段）。两次结果不一致的样本列为"不稳定"。

### 5. 延迟（直接回答的体验）

评测工具只测"判断"和"路由"的耗时，不测生成回答。请另外在界面里手动问 3 个应直接回答的问题（例如"解释一下 Rust 的所有权机制"），记录：

- 从发送到看到第一个字的时间
- 回答全部显示完的时间
- 文字是否逐步显示（流式是否生效）

### 6. 审查回答的质量（direct / auto 模式）

在 `review_requests = "direct"` 下，在界面里实际问 `rev-01`、`rev-04`、`rev-06` 三个问题，评价直接回答的质量：是否找到了关键问题、有无明显错误、是否给出修改建议。再在 `reviewer` 模式下问同样的问题，对比独立审查的结果和耗时。

### 7. 逐条分析错误

对每个 `pass = false` 的样本，打开 `evals/results/<…>.jsonl` 中对应的那一行，看 `raw_outputs`（模型原始输出）、`got_task_goal`、`got_question`，按下表归因：

| 归因 | 含义 | 典型表现 |
|---|---|---|
| A 规则缺失或边界模糊 | 提示词没有覆盖这种情况，或规则之间界限不清 | 模型的选择在提示词里"说得通" |
| B 信息缺失 | 模型缺少做出正确判断所需的信息 | 追问一个系统其实已经知道的东西 |
| C 优先级冲突 | 同时命中多条规则，模型选了优先级低的 | 应派发却直接回答，且回答本身没错 |
| D 模型能力 | 规则清楚、信息完整，模型仍然判断错误 | 忽略明确规则、理解错用户意思 |
| E 标注争议 | 期望本身值得商榷 | 单独列出，说明理由 |
| F 系统问题 | 格式失败、超时、程序错误 | 有 `error` 字段 |

## 标注口径（评测前请先确认）

### 通用口径

| 口径 | 说明 |
|---|---|
| 必须交给后台 | 精确计算、当前日期时间、读写工作目录中的文件、改代码仓库——即使模型自己会做 |
| 直接回答 | 闲聊、常识、概念解释、建议讨论、在对话里给示例代码（不写入仓库） |
| 不该追问 | 文件路径、输出格式、测试命令、代码风格等执行者能自行确定的细节 |
| 该追问 | 不知道要处理哪个对象（"把它改好""帮我分析一下数据"），或有两种完全不同的理解 |
| L1–L4 | L3 = 只生成文档（保存用的 `write_file` 不算"需要工具"）；L4 = 需要读数据 / 计算 + 生成文档；只检查 general 的样本，coding / reviewer 不检查类别 |
| 工具 | 只检查"期望的工具都被选上"，多选了工具不算错（例如统计时额外选了 calculator） |
| 风险 | 只读 = low；写文件或改代码 = medium；删除、对外发送、生产环境 = high |
| 跟进 | 与进行中任务无关的新请求（即使同为 coding）不算跟进 |
| 审查 | 基础期望对应 reviewer 模式；direct / auto 下的期望写在 `by_review_mode`；需要读文件的审查交给 general、读仓库的交给 coding（Reviewer 不能读文件） |

## 注意事项

1. **统计口径与上次不同。** 新的评测工具只在"动作判断正确"的样本上统计角色、类别、工具、风险准确率；旧工具会把"动作判错"的样本也计为角色错误。所以上次的"角色 62.5%、类别 50.0%"不能和这次的数字直接比较。要对比，请看**整体通过率**，或用新工具在 v1 集上重跑（第 2 步）。
2. **审查类样本的期望随模式变化。** 三种模式各跑一次（第 3 步），不要只看一种模式的总分。
3. **思考模式。** 如果模型带思考模式（输出 `<think>…</think>`），在 `json_schema` 格式约束下它可能无法正常输出思考内容，判断质量可能受影响；关闭思考通常更快。请注明评测时的设置，有条件的话两种都跑一次 reviewer 模式做对比。
4. **评测不需要启动任何 agent。** 评测工具使用内存数据库，只调用模型做判断和路由。本机没有安装 Codex 时，Policy 会拒绝 coding 任务，但模型选择的角色仍然照常计分。
5. **延迟。** 判断延迟包含格式重试的时间。第一条样本可能因模型加载而偏慢，冒烟测试（第 1 步）可以起到预热作用。评测工具不测生成回答的时间，回答体验请按第 5 步手动测。
6. **重复运行。** 每次运行都会在 `evals/results/` 生成新文件，文件名带时间、`--label` 和审查模式，不会覆盖旧结果。
7. **发现标注错误时**：评测过程中不要改数据集。在报告「标注争议」一节写明，确认后再改 `evals/make_dataset.py` 重新生成，并在报告中注明评测用的是哪个版本的数据集（`git log --oneline -1 -- evals/routing.jsonl`）。
