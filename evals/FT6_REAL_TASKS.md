# FT.6 真实任务抽查指南

日期：2026-11-19。对应 `docs/DECISIONS.md` 第 45 条。

## 1. 要回答的问题

FT.6 让前台写任务描述（`task_goal`）时不再扩写。路由评测只能检查"派给谁、什么类别"，看不出**执行者拿到更短的描述后，活干得好不好**。这份指南用 6 个真实任务，对比开关关闭和打开时的执行结果。

## 2. 准备

1. 在 FT 分支的最新代码上运行（本分支的 PR 合并后）：

   ```bash
   git fetch origin claude/serene-cerf-lpx1bs && git checkout claude/serene-cerf-lpx1bs && git pull
   ```

2. 在工作目录（`config.toml` 里 `[agents.general] workspace_dir` 指定的目录）准备两个文件，供第 2、3 个任务使用：
   - `notes/meeting.md`：随便一段会议纪要，有 3～5 条要点；
   - `data/defects.csv`：几行"产线,缺陷数"数据，例如 `产线A,12`。

3. 每个任务都跑两遍：
   - **关闭**：`config.toml` 的 `[conversation]` 里写 `concise_task_goal = false`，启动服务；
   - **打开**：改成 `concise_task_goal = true`，**重启服务**后再跑一遍。

   启动命令：

   ```bash
   cargo run --release --bin agentnexus
   ```

   然后打开 http://127.0.0.1:8787 。每个任务都**新开一个对话**，避免受前面任务的影响。

## 3. 六个任务

| 编号 | 怎么发（一条消息，除非另有说明） | 主要看什么 |
|---|---|---|
| T1 普通文档 | 写一份介绍瀑布式开发过程的文档，保存成 Markdown 文件 | 关闭时前台常会自己加章节要求；打开后描述应该短，文档质量是否明显下降 |
| T2 读文件做总结 | 读取 notes/meeting.md，总结一下会议要点 | 打开后是否仍然读了文件；有没有多出你没要求的东西（例如另存一份报告） |
| T3 读数据 + 写报告 | 读取 data/defects.csv，统计各产线缺陷数，写成分析报告保存到 reports/defects.md | 统计是否正确；报告是否保存到你指定的位置 |
| T4 多轮指代 | 先发"帮我看看 notes/meeting.md 里写了什么"，等它回复后再发"把那份纪要整理成待办清单保存下来" | **最关键**：打开后描述里是否把"那份纪要"补全成 `notes/meeting.md`；执行者能否找到文件 |
| T5 贴内容审查 | 帮我审查这段代码有没有问题：（下一行起贴 20～40 行你手边的真实代码） | 贴的代码是否完整进入任务；审查意见质量是否下降 |
| T6 写网页 | 做一个展示各产线缺陷数量的网页，用柱状图显示 | FT.3 时这类任务被扩写得最长（24 字扩成 7 条要求）；打开后页面是否仍然可用 |

## 4. 每个任务记录什么

前台派任务后，对话里会显示"明白，我来根据您的要求做：……"，冒号后面就是 `task_goal`。

| 记录项 | 怎么填 |
|---|---|
| 任务描述字数 | 数一下"明白，我来根据您的要求做："后面那段话大概多少字 |
| 描述是否完整 | 是 / 否。否的话写缺了什么（例如没写文件名、指代没补全、贴的内容不全） |
| 有没有自行添加的要求 | 有 / 无。有的话写是什么（例如加了日期、指定了技术栈） |
| 执行结果 | 好 / 一般 / 差，一句话说明原因 |
| 从发送到看到"明白，我来…"大约几秒 | 粗略即可 |

可以照下面的格式记，复制两份，分别填"关闭"和"打开"：

```text
T1 关闭：字数=  完整=  自加要求=  结果=  秒数=
T2 关闭：……
```

## 5. 怎么判断

- **通过**：打开后 6 个任务里，"描述是否完整"全是"是"，"执行结果"没有一个比关闭时差一档以上。
- **要改提示词**：T4 指代没补全，或 T5 贴的内容不全。这两类属于方案 A 明确要求保留的东西，出问题说明规则没写清楚。
- **方案不成立**：多数任务的执行结果明显变差。这时考虑方案 B，把原话和对话一起交给执行者（要改 `orchestrator.rs`，属于高风险改动，需要另出方案）。

把记录发回给我即可。
